# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is **not** a conventional software project — it's a working folder for building and maintaining a single deliverable:

- **`tnved_checker.html`** — the page: markup, styles and the login screen, and nothing else. No build step, no package manager, no framework.
- **`server/private/base.js`** (~12 MB) — the base: every legal database, hard-coded as JS constants, and every function that reads them (`findX()`, `renderHtml` which builds the result cards, `calcWarnings`, `lkPrefRates`, `BATCH_REQS`…), ending with `ENGINE_API`, the list of what a browser may ask. This is the deliverable — checking Kyrgyz Republic / EAEU customs (ТН ВЭД) codes against import/export bans, licensing, certification, veterinary/phytosanitary/sanitary control, technical regulations, export control (dual-use/NKS), duty rates and more. **It runs only on the server and is never sent to a browser.**
- **`server/private/checker.js`** (~270 KB) — the application's interface: pages, calculators, card post-processing, the assistant page, the admin panel and the shared helpers (`esc`, `norm`, `fmtCode`, `docLink`…). Until 14.09.2026 the two files were one inline `<script>` inside the page; until 17.09.2026 they were one `checker.js`. **Where anything below speaks of editing or checking a database constant or a `findX()` "in the inline script" or "in checker.js", it means `base.js`.** `checker.js` is served only through the authenticated route `/api/checker.js` and `base.js` not at all — **never publish either as a static asset.** How the two talk (`engine()` → `/api/engine`), the limits, checks and deployment order are in [server/CHECKER.md](server/CHECKER.md); the static-path blocks that keep both unreachable are in `server/nginx.conf`.
- **`server/`** — a small Node/Express + PostgreSQL backend added in the "accounts/admin" phase, providing real (server-verified) login and an admin panel for creating/editing/disabling user accounts. See "Backend (`server/`)" below.
- The rest of the repo is **source material**: official legal texts (`.md` files — tax code, Единый перечень, government resolutions, etc.) that get manually parsed and encoded into the app, and **`session.md`**, a running Russian-language changelog of what was done, why, and what's still unverified. `session.md` remains the narrative record of past work — why something was done and what is still unverified — so append to it when you make a substantive change. Since the review of 05.09.2026 the repo also has **real git history** (it previously had none): commit `eade5b8` preserves the working set as it had been staged, including 15 legal source `.md` files that by then existed only in the git index and not on disk. Those files are recoverable with `git checkout eade5b8 -- <path>` if they are ever needed again. Since 12.09.2026 there **is** a remote, and it is not GitHub: `vps` = `ssh://root@65.109.170.170/srv/git/tnved.git`, a bare repository on the same VPS that serves the site, mode 700 and outside Nginx's root (`/opt/tnved`), so it is unreachable from the web. `git push vps main` after a commit — 103 commits and 19.6 MiB at the time it was created. It exists because the history had no copy anywhere off the working machine; it is a backup and a rollback path, **not** a collaboration remote and not something Codemagic builds from. There is also `origin` = `git@github.com:tshalabaev/customsassist.git`, **private**, created the same day once the owner completed the device-code login; it carries the same history and is the remote Codemagic builds from. Two remotes, two purposes: push to both (`git push origin main && git push vps main`) — GitHub is the collaboration and CI remote, the VPS mirror is the backup that survives a GitHub outage or a lost account.

**SSH to GitHub uses its own key, deliberately.** `~/.ssh/id_ed25519_github` (`SHA256:c3YED5BB…`) is separate from `id_ed25519` (root on the Hetzner VPS) and `id_ed25519_checkts` (root on 167.233.142.113), and `~/.ssh/config` pins github.com to it with `IdentitiesOnly yes`. Reusing a server deploy key for the account would make one stolen file both a root shell and a GitHub login. Note what the two credentials can and cannot do: the SSH key reaches repositories that already exist but cannot create one — `git push` to a missing repo answers `Repository not found`, GitHub has no push-to-create. Creating a repository needs the `gh` API token, which is a separate login (`gh auth login --web` prints a one-time code for https://github.com/login/device; the code expires in about 15 minutes, so restart the flow rather than re-offering a stale one).

**Never run `sed -i` on `tnved_checker.html`, `server/private/base.js` or `server/private/checker.js` from Git Bash** — it rewrote every line ending of the page (+1585/−1579 for a six-line change, 16.09.2026). Edit them with a Node script that writes back exactly the bytes it read, and confirm with `git diff --numstat` that the line counts match the change. **The editor's exact-string replacement is not safe on these files either.** On 17.09.2026 one such edit rewrote all 2,502 CRLF line endings of `checker.js` to LF (+2573/−2504) and turned the escape `\u0000` inside a regular expression into a literal NUL byte, after which grep called the file binary. After any edit check `git diff --numstat` and grep the new code for escapes; if the endings were rewritten, restore them line by line from `git show HEAD:` rather than committing the phantom diff.

**`.gitattributes` sets `* -text` and must stay that way.** A related trap in patch scripts: a helper that retries an anchor with CRLF only when the LF form is not found will, for a single-line anchor, match on the first try and insert a multi-line replacement with bare LF — count LF-only lines against the previous commit after such an edit. `tnved_checker.html` (~0.6 MB since the split), `server/private/base.js` (~12 MB) and `server/private/checker.js` all have *mixed* line endings (some large one-line data literals contain CRLF inside them), and every edit to it is an anchored exact-string replacement. Git's `core.autocrlf` would rewrite those bytes on checkout, breaking anchors and producing a whole-file phantom diff. This was caught during the review: the first attempt at committing the file silently stripped 7,466 CR bytes.

**`AGENTS.md` is generated from this file, never edited by hand.** It is the same text for Codex with two header lines changed (`# AGENTS.md` and «guidance to Codex (Codex.ai/code)»). Hand-maintained, it fell a day behind — without the `sed -i` rule — within a week. After editing `CLAUDE.md`, regenerate it in the same commit and confirm that `diff AGENTS.md CLAUDE.md` shows exactly those two lines.

**Wording: the adjective is «кыргызский», never «киргизский».** This applies to every Russian string the project writes — card text, `SOURCE_AUDIT` notes, comments, `session.md`, commit messages — and matches the official name used by the acts themselves (Кабинет Министров Кыргызской Республики). Likewise write «Кыргызстан», not «Киргизия». The two exceptions are species names transcribed from the act itself — «Береза киргизская» (*Betula kirghisorum*) and «Усач-киргизобия» (*Kirgisobia bohnei*) in `SPECIES_DB` — which must keep the act's spelling or they stop matching a search by name.

Beyond `server/`, there is no other service and no CI. Opening `tnved_checker.html` by double-clicking it (`file://`) shows the login screen and nothing more: the page holds no data, and every `fetch('/api/...')` fails immediately under `file://`. It has to be served over http(s) from the same origin as the backend — Nginx serves the page and proxies `/api/*` to `server/`.

**Since 14.09.2026 the login gate controls who can read the reference data, not only who can use the tool.** That is the opposite of what held before: while the databases sat inline in the page, "view source" handed them to anyone who opened the address. They now live in `server/private/checker.js`, which Nginx does not serve and the local Express serves only from an explicit public-file list — serving the whole repo root is no longer allowed. What the gate still cannot do is take data back: whatever a signed-in user has already received is in their browser, and a copy they saved stays theirs.

**Since 17.09.2026 a signed-in user no longer receives the base either.** Until then `/api/checker.js` carried every database, so any account — including a three-day trial registered with a real mailbox — could save the whole base in one request. The owner asked for exactly that to stop («чтобы никто не смог скачать мою базу»). The base now lives in `server/private/base.js`, which only the server executes (`server/src/services/base.js` runs it in one vm context with `checker.js`), and the browser asks for one answer at a time through `engine(fn, ...args)` → `POST /api/engine`. What this buys is honest to state: data shown to a user can always be copied by a user, so the goal is that copying the base means a long, visible enumeration tied to one account — `routes/engine.js` counts distinct heading positions, tree groups and name queries per account per Bishkek day, mails the active admins at 300 and refuses at 800 (`ENGINE_LIMITS`). **A new database follows the same split:** constant, `findX()` and card in `base.js`; anything the interface needs outside the cards goes through a new `ENGINE_API` entry that validates its own arguments, never through a direct reference from `checker.js`, which throws `ReferenceError` in the browser and only there. The split itself was mechanical (acorn over the syntax tree, 34 interface functions rewritten to `engine()`) and verified against the previous file: 2 079 `render` queries and 7 160 other answers identical byte for byte. Details, the reasoning behind the limits and the deployment order that must ship the six files together are in [server/CHECKER.md](server/CHECKER.md).

There is no build/lint/test tooling. The workflows that stand in for them, established over prior sessions:

node server/tests/checker-access.test.js     # браузерный: вход, загрузка, поиск; базы нет в checker.js

node server/tests/auth-loader.test.js

node server/tests/admin-invitation.test.js
node server/tests/assistant.test.js           # AI-помощник без сети
node server/tests/lookup-filter.test.js       # справка: направление, страна, фильтр
node server/tests/login-enumeration.test.js   # вход не выдаёт, есть ли адрес

The browser test needs `PLAYWRIGHT_MODULE` pointing at an installed `playwright-core`; it drives the system Edge, touches no live database and sends no mail. Prior sessions left an install at `%TEMP%/pw_check/node_modules/playwright-core`; without the variable the browser tests print SKIP or pass only their offline part, which is how the broken registration button of 14–17.09.2026 went unnoticed. One more test is not in the list because it needs a database: `TEST_DATABASE_URL=<disposable db> node server/tests/reset-password.test.js` (concurrent resets have one winner, sessions end, replay is rejected); without the variable it fails on its first line, which is a precondition, not a regression. The full list and the deployment order live in [server/CHECKER.md](server/CHECKER.md).

Note: `python3` here resolves to the Windows Store alias, which does **not** see git-bash POSIX paths like `/tmp/...` — write scratch files to a Windows-style path (or the session scratchpad dir) instead, and read them back with the `Read` tool, not by printing to the bash console (the console mangles Cyrillic output; files round-trip correctly).

**Runtime smoke-test** a function or DB after editing it. The shortest way is the server's own loader: `require('./server/src/services/base').load()` returns `ENGINE_API`, `renderHtml`, `ETT_DB`, `calcWarnings` and a few more, and `ENGINE_API` reaches everything the browser can ask. For anything else, read `server/private/checker.js` **and then** `server/private/base.js` (in that order: the base's top level calls the interface's helpers at load) and run both inside one Node `vm` context with minimal DOM stubs (`document.getElementById`, `classList`, `innerHTML`/`value`/`textContent` getters/setters, etc. — the top-level script calls a few `render*Panel` functions immediately on load, so it throws without stubs). Expose the globals you need via `this.__x = x;` appended to the script source before `runInContext`, since top-level `const`/`let` in a vm context aren't reliably visible as properties of the sandbox object otherwise. This is how new/changed lookup functions and DB entries get verified end-to-end without a browser.

**Browser check** (for UI/rendering changes): the three post-processing passes cannot be checked with the `vm` stubs — `querySelectorAll` returns `[]` there, so `buildResultSummary` builds nothing. Nor do you need the backend: assemble a **standalone page** from the app's real `<style>`, the real result markup obtained by calling `renderHtml(q).html` inside the `vm`, and the post-processing functions cut out of the file by name (`compactifyCards`, `enhanceResultCards`, `buildResultSummary` plus `esc`, `trunc`, `focusResultCard`, `SUM_TAG_COLOR`, `SUM_FLAG_ORDER`, `ALERT_TAG_SEL`) — every one of them is declared at top level and closes with a brace at the start of a line, so `function <name>(` … first `
}` cuts them cleanly. Open that page in the system Edge and check it at 1280 and 420 px. **When you find horizontal overflow, name the element that causes it** before blaming your change: list everything whose `getBoundingClientRect().right` exceeds `clientWidth`. **That list names every victim, not the cause — rank it by width.** On 10.09.2026 it was read as «`span.notes-ico` in the ЕТТ list rows»; the icon is 15 px wide and was merely pushed out by its neighbour `.ett-row .er`, which at 783 px was the real cause (11.09.2026). ## Backend (`server/`)

A small Express + PostgreSQL app providing session-based login and an admin API (`/api/auth/*`, `/api/admin/*`) for `tnved_checker.html`. See the plan at the time it was added for the full design rationale (RLS-equivalent access model, why sessions instead of JWT, CSRF approach, etc.) — this section just covers day-to-day commands.

**Local dev:**
```bash
cd server
npm install
cp .env.example .env   # fill in DATABASE_URL (a local Postgres) and SESSION_SECRET
psql "$DATABASE_URL" -f migrations/0001_init.sql
npm run create-admin -- you@example.com "some-password"   # one-off first admin
npm run dev
```
`server/src/index.js` exports `app` and only listens (and starts the class-decisions and НБКР background loads) under `require.main === module`, so `tests/api-boundary.test.js` drives the real middleware order — Origin check, session, the 15 MB `/api/assistant` body parsed only for a signed-in user, 400/413 instead of 500 for bad bodies — with the database and session store stubbed. It also serves the page itself so `http://localhost:3000/` works standalone for local testing without Nginx in front — but **only from an explicit list of public files plus the icons.** Pointing `express.static` at the repo root, as it did until 14.09.2026, would serve `server/private/checker.js` and every backup HTML next to it, which is exactly what the split was for.

**Deploy (VPS):** install Node LTS + PostgreSQL, create the DB/role and apply `migrations/0001_init.sql`, deploy `server/` and run `npm ci --omit=dev`, run `create-first-admin.js` once, run the app under a systemd unit (`ExecStart=node server/src/index.js`, `EnvironmentFile=` pointing at a production `.env`), and put Nginx in front: serve `tnved_checker.html` as static content at `/`, reverse-proxy `location /api/ { proxy_pass http://127.0.0.1:3000; }`, and terminate TLS there (Let's Encrypt via `certbot --nginx`, which needs a real domain pointed at the VPS — a bare IP can't get a cert).

**Addresses (since 11.09.2026).** The only address is **`https://customsassist.trade`**; `www` 301-redirects to it, and both names are covered by one Let's Encrypt certificate. The temporary `65-109-170-170.sslip.io` was switched off the same day at the owner's explicit request, in the belief that the consequence was severe — that the app version in the stores pointed at that origin and could not load until its user installed 1.1. **On 12.09.2026 that belief was checked and did not hold:** `kg.tnved.checker` returns 404 from the Google Play listing endpoint and 0 results from the iTunes lookup API, while a control request for `com.whatsapp` returns 200 — so there is no public production release in either store, and switching the origin off stranded nobody. What this does *not* rule out is a Play Console draft, a closed/internal test track or a TestFlight build, none of which appear in those public endpoints; only the consoles themselves settle that. Its Nginx block and certificate are gone; what remains is a default server that answers HTTP with a 301 to the canonical address and rejects the TLS handshake on HTTPS, so a stale bookmark still lands somewhere sensible and nobody is served a certificate for the wrong name.

`APP_ORIGIN` therefore holds a single value again, but `server/src/index.js` still **parses it as a comma-separated list** — keep that, it is what makes the next origin move survivable. Note the matching trap it created once: `routes/auth.js` builds the password-reset link, and a list cannot be pasted into a URL, so the canonical address for links comes from `publicOrigin()` (explicit `PUBLIC_ORIGIN`, else the first entry). The CSRF check stays fail-closed: no `Origin` header and an unlisted one both get 403 — including `https://www.customsassist.trade`, which is fine precisely because www never serves the page, it redirects first.

The same domain also fronts a **different project on a different server**: `ts.customsassist.trade` → 167.233.142.113 is «Учёт транспортных средств», an Nginx + Gunicorn/Django app in its own repo, reached over SSH with the `id_ed25519_checkts` key. Two things about it are worth knowing before touching that host: Django answers **400 DisallowedHost** for any hostname missing from `ALLOWED_HOSTS`, so a new name needs `ALLOWED_HOSTS` *and* `CSRF_TRUSTED_ORIGINS` in `/opt/checkts/.env` plus `systemctl restart checkts`; and its catch-all `:80` block redirects everything to the old sslip.io name, so a new domain needs its own `:80` block or it loses its hostname on the first request. The zone file and the whole move are documented in [dns/](dns/).

**Deploying a change to `tnved_checker.html` alone** (no `server/` change): back up the current file on the VPS, `scp` the new one to `tnved_checker.html.new`, compare its md5 with the local file, check the syntax of the page's first bare `<script>` **on the server** with `new vm.Script(...)`, exactly as `checker-access.test.js` does (not only locally — that is what catches a corrupted transfer; the application code itself is `server/private/checker.js` and is deployed by the order in `server/CHECKER.md`), then `mv` it into place and `chown tnved:tnved`. Nginx serves this file as static content, so **no `systemctl restart tnved`** — the restart is only for `server/`. Verify by `curl`ing the site and checking that the served bytes have the same md5 and contain the new text. Editing the file without this step does not count as finished work: a fix once sat in the repo for a session while the user was looking at the old page.

**Mail: one branded template, and the brand is «Customs Assist KG».** `services/email.js` exports `renderEmail({title, intro, actionUrl, actionText, outro, footNote})` — a table-and-inline-styles layout, because mail clients strip `<style>` and do not do flex or grid. Both letters (verify address, reset password) go through it, so a change lands in one place. Three rules baked into it: the logo is linked from `https://customsassist.trade/email-logo.jpg` (Nginx serves any file in `/opt/tnved`, and it is a **JPEG** — WebP is still not safe in mail), the brand name is printed as text under the logo because Gmail and Outlook block remote images by default, and the action URL is repeated as selectable plain text under the button in case a client mangles the link.

**Email verification exists since 12.09.2026** (migration `0006`). Registration was sending nothing at all before that, which is how `esenbek@exampl.com` — a typo'd domain — got into the users table. The policy started **soft** — account created, logged in and usable immediately, with an amber bar offering a resend — and was **made hard on the same day** (migration `0007`), because the owner pointed out the obvious hole: a soft gate means registering with a made-up address gives full access, which is exactly how `esenbek@exampl.com` came to be using the service. Now `/register` **does not create a session** at all (it returns `{email, needsVerification:true}`) and `/login` answers `403 email_not_verified` until the address is confirmed.

Four consequences of that switch, each of which had to be handled rather than discovered later:

- **Existing accounts were grandfathered, deliberately.** Ten of fifteen users were unverified and eight of them had registered on 03.09.2026, before verification existed — they had never been sent a letter. Locking them out for failing a requirement that did not exist would have been unfair and would have produced a wave of support requests, so migration `0007` marks every pre-existing account verified. The timestamp it writes is `now()`, not `created_at`: it records the date of the decision to grandfather, not a confirmation that never happened — do not write a fact into data that did not occur.
- **Resend needs an unauthenticated route.** With no session until confirmation, the in-app `#verifyBar` resend is unreachable for the people who need it. `POST /resend-verification-public` takes `{email}`, answers `{ok:true}` identically every time (same anti-enumeration reasoning as `/forgot-password`), and is protected by an IP rate limit plus the two-minute per-user cooldown already inside `issueVerification` — no captcha there on purpose, since a third widget for a button that only mails an address already in the database buys nothing.
- **The refusal is checked after the password**, next to the subscription check and for the same reason: checking it earlier would let a login probe reveal which addresses are registered but unconfirmed.
- **The trial still counts from registration**, by the owner's choice, so a slow letter eats into the three days. If that ever becomes a complaint, the fix is to set `subscription_expires_at` at confirmation instead.

The UI gained a fifth auth view, `authViewVerify`, reached both from a successful registration and from a `403 email_not_verified` login. The in-app amber bar is kept even though no unverified session can now exist — an admin-created account could still be unverified, and a dead branch that costs nothing is better than one whose absence is discovered by a user. Tokens mirror `password_reset_tokens` — sha256 of the token only, single use, 24 hours (a day, not an hour: a registration mail may be opened in the evening).

**A new user column has to be added to the auth middleware's SELECT too.** `email_verified_at` was written by the verify endpoint and `/api/auth/me` still answered `emailVerified:false`, because `middleware/auth.js` loads the user with an explicit column list. The end-to-end test caught it; a UI-only check would not have.

**Captcha is Cloudflare Turnstile, and it is off until two keys exist.** `services/turnstile.js` verifies a token against `challenges.cloudflare.com/turnstile/v0/siteverify`; `/register` and `/forgot-password` call it. The design decision that matters: **`isEnabled()` keys off `TURNSTILE_SECRET_KEY`, and when that is unset verification returns `{ok:true, skipped:true}`** — so the code ships and runs exactly as before until the owner pastes the keys into `.env` and restarts. The public sitekey reaches the browser through `GET /api/auth/config` rather than being baked into `tnved_checker.html`, which is what makes turning the captcha on a one-line `.env` edit instead of an edit and redeploy of the page.

Five things worth knowing before touching it:

- **Turnstile does not require the domain to be proxied through Cloudflare.** The DNS records here are DNS-only and that is fine; only the Cloudflare account matters. Do not "enable the proxy" on this account of the captcha.
- **The token is single-use, so verify it last.** In `/register` the captcha check sits *after* field validation and *before* `bcrypt` — validating first means a typo'd password does not burn the token and force the user to solve again; verifying before bcrypt means a bot does not cost a hash.
- **In `/forgot-password` the check happens after the response is already sent**, alongside the rate-limit check, for the reason documented there: that endpoint answers `{ok:true}` identically and immediately for every address so it cannot be used to enumerate accounts. A failed captcha therefore just means no mail, never a different answer.
- **Failure of the verification request itself is treated as a failure (fail closed).** An attacker cannot make our outbound call fail, so the only real cost is a Cloudflare outage blocking signups — which is logged and visible, unlike a captcha that silently lets everyone through whenever a third party is down.
- **`success: true` is not the end of the check.** The siteverify reply carries `hostname` and `action`, and both are compared: the sitekey is public, so a token minted on someone else's page with the same key, or on the neighbouring form, would otherwise be accepted. Each widget sets `action` (`register` / `forgot-password`) and the allowed hostnames are derived from `APP_ORIGIN`. Both comparisons are guarded on the field being present, so a reply that omits one cannot cause a false rejection. Note that the **test keys report `hostname: "example.com"` and no `action`** — so with test keys in place the hostname check rejects everything, which is correct and is how that code path was proven (`turnstile: hostname mismatch: example.com` in the journal).
- **A captcha cannot be solved by your test harness, and that is the point.** With the real key, Managed mode showed «Подтвердите, что вы человек» to the automated browser and Playwright could not click inside Cloudflare's iframe. Do not read that as a defect — verify the negative paths (absent, forged, replayed token) automatically, exercise `hostname`/`action` with test keys, and leave one real registration to a human.
- **Render the widget only for the view that is open.** The first version rendered both at init, which starts two challenges inside `display:none` blocks and risks the token expiring (300 s) before the form is submitted. `tsRenderVisible()` runs after the script loads, because by then the user may already have opened a form while the script was still loading.
- **The widget renders into a shadow DOM.** A test that counts `iframe` elements under the container finds zero and looks like a failure; check `turnstile.getResponse()` or the container's size instead. Render is explicit (`render=explicit`) because the auth views live in `display:none` blocks and an auto-rendered widget there comes out with zero size.

Cloudflare publishes test keys that make the whole path checkable without the owner's account: sitekey `1x00000000000000000000AA` with secret `1x0000000000000000000000000000000AA` always passes, `2x…AB`/`2x…AA` always fails, `3x…AA` returns `timeout-or-duplicate`. One caveat found by using them: **the "always passes" secret accepts any non-empty string, not only the dummy token**, so it cannot be used to prove that forgeries are rejected — the `2x` key proves that.

**Network exposure and backups (17.09.2026).** Node listens on `127.0.0.1` only: the port used to be bound on all interfaces with only UFW in front, and with `trust proxy` a direct request could forge `X-Forwarded-For` and walk past every per-IP limit. Nginx sends `Strict-Transport-Security: max-age=31536000` without `includeSubDomains` (`ts.customsassist.trade` is another server and another project). **`add_header` is not inherited by a `location` that has its own `add_header`**, so the header is repeated in `location = /` and `location = /tnved_checker.html`; check it on `/`, the page, the manifest and an `/api/` route after any config change. The database is dumped daily by `tnved-db-backup.timer` (`pg_dump -Fc`, 14 days, `/var/backups/tnved-db/`); the script's source is `server/tnved-db-backup.sh`, installed as `/usr/local/bin/tnved-db-backup.sh` — edit the repo copy and install it, not the other way round. **Every run restores its own dump** into a throwaway `tnved_restore_check` and compares the row counts of `users`, `admin_audit_log` and `assistant_log` with the live database (restored may be lower, never higher; zero users fails), then drops it; the journal line reads `restore check ok: users=13/13 …`, and any failure fails the unit. **A failed unit mails the site's active admins**: `tnved-db-backup.service` and `tnved.service` carry a drop-in `alert.conf` with `OnFailure=tnved-alert@%n.service`, and the template `server/tnved-alert@.service` (installed in `/etc/systemd/system/`) runs `scripts/alert-admins.js <unit>` as `tnved` with `SupplementaryGroups=systemd-journal` — without that group `journalctl` shows `tnved` nothing of other units. The letter goes through the same Resend key and `renderEmail` template as the site's mail and carries the last 25 journal lines. For the API this fires only when `Restart=on-failure` gives up, not on every crash. `--dry-run` prints the recipient count without sending; the whole chain was proven on 17.09.2026 by a throwaway unit running `/bin/false` (deleted afterwards). Recipients come from the database, so with PostgreSQL down there is no letter — but then the site is down too. That the check can fail was proven, not assumed: a dump truncated to 6 KB is rejected by `pg_restore --exit-on-error`. **Off the server**, the Windows scheduled task `tnved-db-backup-pull` on the owner's machine copies every dump to `%USERPROFILE%\tnved-db-backups` at 12:00 (Bishkek time, after the 03:30 UTC dump) with `StartWhenAvailable`, so a day the machine was off is caught up at next boot. The task runs `server/pull-db-backups.ps1` from the repo, which keeps local copies **30 days** — the period `privacy.html` promises, together with 14 days on the server — and deletes old ones only when a copy younger than two days exists, so an unreachable server or a stopped dump timer never ages out the last copies there are. **A backup is storage of user data too:** the first version kept local copies forever, which contradicted the policy's right to deletion; a new copy location, retention period or recipient goes into `privacy.html` in the same commit. It uses the same root key the machine already holds for deploys, so it adds no new trust relationship.

**The VPS itself (17.09.2026).** SSH takes keys only — `/etc/ssh/sshd_config.d/10-hardening.conf` sets `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `X11Forwarding no`, `MaxAuthTries 3`. No account had a password, so nothing could log in that way, but the port was accepting the attempts; check `sshd -T` after any OpenSSH upgrade, because a drop-in file named later than `10-` or a cloud-init file could win. Security updates now reboot the machine themselves when a kernel or libc needs it, at 22:00 UTC = 04:00 in Bishkek (`/etc/apt/apt.conf.d/52-tnved-auto-reboot`, `Automatic-Reboot "true"`): before that the 7.0.0-31 kernel had been installed and waiting for 19 days. The first reboot was done by hand the same day at the owner's word («можешь перезагружать сколько хочешь»): every unit is enabled and the API was listening again 30 seconds after the command, so a nightly reboot costs about half a minute. Neither file lives in the repo — they are system configuration; recreate them from this paragraph on a new server.

**Account enumeration: a decision, not an oversight (17.09.2026).** Login spends a bcrypt comparison on every path — unknown and disabled addresses compare against a dummy hash of the same cost — so neither the answer nor its timing says whether an address exists (`tests/login-enumeration.test.js`). Registration still answers `409 email already exists` on purpose: it sits behind Turnstile and a per-IP limit, and «Такой email уже зарегистрирован» is worth more to a real user than hiding it would be. Closing it would mean answering «check your mail» to everyone and mailing the existing owner instead — do not half-do that, and do not "fix" login back to an early return.

**Schema/migrations:** there's no migration framework — `migrations/*.sql` files are applied by hand with `psql -f`, in order, once each. Add new migrations as new numbered files rather than editing an already-applied one.

**AI-помощник (`/api/assistant`, с 16.09.2026) отвечает по базе, а не по памяти модели.** `services/assistant.js` берёт контекст базы из `services/base.js` (тот же, что отвечает браузеру через `/api/engine`) и даёт модели три инструмента, построенных на функциях сайта: `search_base` вызывает тот же `renderHtml()`, что собирает карточки (новая база, подключённая в `render()`, попадает к помощнику сама), `calc_payments` — `itemDuty`/`vatFreeHits`/`customsFeeGoods` калькулятора по курсу НБКР, `group_notes` — примечания к разделам и группам из `private/tnved-notes.json`. Модель — DeepSeek через совместимый с Anthropic API; ключ и модель только в `.env` (`AI_API_KEY`, `AI_MODEL`), промт — `src/assistant-prompt.md` (`docs/assistant-prompt-brief.md` — исходный бриф владельца на 30 КБ, из которого промт сжат; он не загружается сервером).

**Главный урок: всё, что можно решить на сервере, решай на сервере, а не просьбой в промте.** Правила вида «не называй меры вывоза», «не пиши про недействующие записи», «не выдумывай ставку НДС» flash-модель соблюдает через раз; детерминированная правка выдачи — всегда. Поэтому `search_base` сам отсеивает карточки по направлению и стране (те же правила, что `lkFilter` справки), вырезает недействующие строки ТРОИС и переписывает счётчик «4 из 35 записей» в «(4)» (модель читала его как 35 действующих), убирает преференциальные карточки при ставке ЕТТ 0%, ставит впереди строку «НДС при импорте: 12% / 0%» из логики калькулятора (без неё модель написала «20%»), подставляет текст «дополнительного примечания ЕАЭС N к группе NN», когда наименование кода на него ссылается (без него модель сочинила «договорную цену»), и отдаёт кандидатов по наименованию с **полными** названиями (на сайте они обрезаны до 110 знаков, а 8517 13 и 8517 14 различаются только хвостом). После ответа сервер проверяет его сам (известными считаются коды из выдачи инструментов и из реплик **пользователя**, но не из прошлых ответов модели: историю присылает браузер, и код, выдуманный в прошлом ответе, до 17.09.2026 проходил проверку в следующем): 10-значный код, которого не было в выдаче инструментов, вызывает один повторный раунд и затем пометку «не подтверждено базой»; markdown-ссылка на адрес, которого не было в выдаче, превращается в текст (модель придумала «[ЕТТ](https://customs.gov.kg)»). Страна может прийти ISO-кодом («KZ») — `lkCountry` его не понимает, отсюда таблица `ISO_COUNTRY`.

**Выдача для модели короче выдачи для человека, а код из вопроса ищет сервер (17.09.2026).** У товарной позиции (2710, 8418, 8504, 8544) выдача упиралась в 40 тыс. знаков и обрезалась с хвоста, а в порядке сайта последними стоят карточки льгот по НДС — вопрос «какие льготы по НДС на 8418» получал выдачу без них. Теперь `search_base` при ввозе убирает экспортный контроль, запреты вывоза и односторонние меры других стран (кроме ввоза из самого государства ЕАЭС), всегда — истёкшее, «преференция не предоставляется», «госрегистрация не требуется», пояснение процедуры ТРОИС, перечни стран ЕСТП и отметки о сверке; ставки соглашений без названной страны отдаёт строкой. По теме последней реплики пользователя (`TOPICS`: НДС и льготы, акциз, пошлина и вес, преференции, квота, запреты, сертификация, контроль, ТРОИС, стоимость) нужные карточки идут первыми, а сверх 18 тыс. знаков (30 тыс. без темы) остальные с конца сжимаются до строки «• теги — заголовок — ставка», а не обрезаются; `full: true` отдаёт всё. На 12 кодах выдача стала на 43% короче (327 → 186 тыс. знаков). **Если в последней реплике есть 10-значный код из ЕТТ и не названы ни страна, ни направление, поиск выполняется до первого вызова модели** (и примечания группы, если спрашивают о примечании) и подставляется в переписку как её вызов — это на один раунд модели меньше; если API такую переписку отвергнет (400), вопрос идёт прежним путём, с принудительного поиска. Страну и направление из свободного текста сервер не разбирает, а только замечает («из Китая», «из китая» — по основе слова через `lkCountry`, «США», «вывезти») и тогда оставляет их модели. **`\b` рядом с кириллицей не работает и здесь**: первая версия тем не находила «вес» и «кг». Прогон на настоящем API после выкладки: 14 из 15, вопросы с кодом без страны — одним поиском за 2–5 с; по ответам исправлено ещё три вещи. `keepKnownLinks` пропускал голую ссылку `https://cbd.minjust.gov.kg/`, потому что она начинает каждый адрес реестра, — теперь адрес должен быть в выдаче целиком. `full: true` модель ставила в первый же поиск — в описании и промте «только при повторном». ТРОИС — пять знаков, если вопрос не о знаке. Второй прогон — 13 из 15: `fetch failed` через 30 секунд (тот же вопрос минутой позже прошёл, поэтому сетевой сбой до ответа теперь повторяется один раз) и ковёр, отнесённый моделью к 5702 вместо 5701 при уточняющем вопросе, — разброс модели, а не выдачи.

Несколько вещей проверены на настоящем API и легко ломаются: **первый раунд принуждает поиск через `tool_choice:{type:"tool",name:"search_base"}` — `{type:"any"}` DeepSeek молча игнорирует**; `thinking:{type:"disabled"}` обязателен, иначе `deepseek-v4-pro` отвергает принудительный tool_choice (400); **выдача по одному коду — до 31 тыс. знаков**, обрезка на 14 тыс. отрезала сертификацию, и модель уверенно писала, что её нет (лимит 40 000 — не уменьшать, не измерив выдачу); правило «без воды» держится только наверху промта и в последней строке системного сообщения. Ответ идёт потоком NDJSON (шаги, затем итог), поэтому в nginx у `location = /api/assistant` стоят `proxy_read_timeout 300s` и `proxy_buffering off`. Вопросы пишутся в `assistant_log` (миграция `0008`; удаление пользователя стирает его журнал каскадом, как обещает `privacy.html`, и вместе с ним его расход в отчёте для счёта — окно удаления в админке об этом предупреждает и предлагает «Отключить») с оценкой 👍/👎 — журнал в админке; из-за этого и из-за передачи вопросов в DeepSeek обновлена `privacy.html`, которая прежде обещала «не логируем запросы» и «не передаём третьим лицам». **Любое новое сохранение или передачу пользовательских данных сверяй с `privacy.html` в том же коммите.**

**Инвойс в PDF и сканы (17.09.2026).** PDF разбирается в браузере библиотекой pdf.js 6.3.289 — она лежит в `vendor/pdfjs-6.3.289/` (legacy-сборка, `cmaps` для китайского текста, JS-декодеры JBIG2/JPEG2000; Apache-2.0) и отдаётся со своего сервера, потому что CSP не пускает скрипты с чужих адресов; WebAssembly выключен (`useWasm:false`), иначе CSP пришлось бы разрешить компиляцию кода. Грузится только при первом вложенном PDF, путь — абсолютный от `location.origin` и вычисляется внутри функции: `checker.js` исполняется из `blob:`-адреса (относительный `import()` разрешался бы от него), а на сервере в vm `location` нет вовсе — константа на верхнем уровне уронила загрузку базы. Страница с текстовым слоем уходит модели текстом, скан — изображением; пределы и путь страниц — ниже, «Документы в чате». **Страница, отсканированная боком, поворачивается сама** (`aiSideways`: полная вариация профилей тёмных точек по строкам и столбцам, порог 0,8 и не меньше 2% тёмных точек; откалибровано на реальных сканах и синтетике) и кнопкой ↻: на реальном инвойсе, положенном боком, DeepSeek прочитал 7–8 сумм из 21, после поворота — 21. Увеличивать разрешение бесполезно: модель сама сжимает изображение примерно до тысячи токенов. **Каждое изображение сначала переписывается отдельным вызовом** — без вопроса, промта и инструментов, параллельно, — и модель рассуждает по расшифровке, а не по картинке: в общем разговоре (вопрос, три страницы, поиск) итог того же инвойса читался как «563 478,40» вместо 583 478,40 в трёх прогонах из четырёх, и расчёт уходил с таможенной стоимостью на 20 тыс. USD меньше; отдельное чтение страницы давало 21 сумму из 21 во всех прогонах. Сверху — инструмент `sum_check`: точная сумма строк в копейках против напечатанного итога; при расхождении модель считает по сумме строк (строки таблицы читаются надёжнее итога) и называет обе цифры. После этого итог и расчёт верны в обоих контрольных прогонах; вопрос по трём страницам стоит около 0,9 цента. Попутно закрыта утечка: вложения прежнего пользователя не сбрасывались при выходе и могли уйти с вопросом следующего в том же окне — теперь они сбрасываются, когда страница помощника строится заново. Тест `assistant-browser.test.js` собирает настоящие PDF (с текстом, напечатанный браузером с китайским и русским текстом, скан ровный и боком, битый) и проходит их под CSP сайта.

**Другие PDF: решение по каждой странице, а положение страницы — у модели (17.09.2026).** Владелец спросил, как сделать, чтобы ошибок не было и в других PDF; каждое правило ниже проверено замером, а не взято «на всякий случай». **Текст или изображение решается для каждой страницы**: пакет документов часто склеен из электронного инвойса и сканов, и прежний порог «в среднем 40 знаков на страницу» отдавал такой файл текстом, молча теряя сканы. Страница идёт изображением, если текста меньше 40 знаков, если он нечитаем (`aiTextBroken`: больше 5% управляющих знаков и знаков частной области или больше 30% латиницы-1 — кириллица шрифта без таблицы символов, «Ñ÷¸ò» вместо «Счёт») или если это слой распознавания поверх скана (`aiPageImages`: невидимый текст, режим 3 или 7, и изображения на 30% страницы и больше — качество чужого распознавания неизвестно, а чтение изображения проверено); текстовая страница, где изображения занимают 30% и больше (таблица, вставленная снимком), идёт и текстом, и изображением. Площадь изображений считается по списку операций pdf.js с матрицей преобразования. **Текст страницы собирается по положению** (`aiPageText`): строка — по высоте с допуском 0,6 кегля (верхний индекс «м³» не отрывается), внутри строки — слева направо, между ячейками « | » (промежуток больше двух кеглей или больше 0,8 между числами — иначе «15,50 1 860,00» сливается в одно число). Порядок строк — как записаны в файле, потому что так текст многострочной ячейки идёт подряд; но таблица, записанная генератором по колонкам, в таком порядке приходила модели кашей (все номера, потом все количества, потом суммы), и её признак — две и больше серии по три и больше строк из одного числа; тогда строки сортируются сверху вниз. Признак «скачки вверх» не годится: высокие многострочные ячейки реестра ТРОИС дают те же скачки, и сортировка их перемешивает — сравнение шло на пяти актах ЕЭК и синтетике, новая сборка нигде не хуже прежней. **Страница вверх ногами** — самая опасная ошибка: реальный инвойс, перевёрнутый на 180°, модель «прочитала» как правдоподобную таблицу, где не сошлась ни одна из 21 суммы, и ничем не выдала, что страница перевёрнута. Признаки по изображению (выравнивание краёв строк, резкость базовой линии) ошибались на 15% из 94 страниц — хуже, чем всегда поворачивать боковой лист по часовой; просьба отметить поворот в самой расшифровке — 17 из 22; отдельный вопрос «правильно или перевёрнут» с одним изображением — 22 из 22 (сканы, таблицы ЕЭК, китайский инвойс, каждое ровно и вверх ногами), около 1 000 токенов. Поэтому сервер спрашивает положение параллельно с чтением, а перевёрнутую страницу возвращает браузеру, и тот рисует её заново повёрнутой (до вечера 17.09.2026 браузер присылал копию на 180°, `alt`; этот путь остался только для вкладок, открытых до выкладки); тот же вопрос исправляет боковой лист, повёрнутый не в ту сторону. **Плотная страница не хуже**: синтетический скан инвойса на 55 строк модель прочитала 55 из 55 и целиком, и половинами — сама плотность строк не беда; полосы (ниже) нужны мелким цифрам. **`sum_check` принимает строки** (`rows`: количество, цена, сумма) и проверяет количество × цену в каждой с допуском на округление цены. Сквозной прогон на настоящем API (перевёрнутый инвойс и ровная CMR): переворот распознан, итог 583 478,40 и платежи 6 327 123,07 сом верны, а в строке 19 модель прочитала «8 × 4 260,35» вместо 6 × 41 260,35 — проверка назвала эту строку пользователю, при верных сумме строки и итоге; 0,63 цента вне часа пик. Тесты: `assistant.test.js` (копия при перевороте, копия при сбое чтения, строки `sum_check`) и `assistant-browser.test.js` (таблица по колонкам, пакет текст + скан, слой распознавания, кодировка, вставленная таблица, поворот копии — всё настоящими PDF под CSP).

**Документы в чате: страницы читаются при прикреплении, трижды, и остаются в диалоге (17.09.2026, вечер).** Владелец попросил «на большее количество листов» и «чтобы 100% было». Пределы: до 60 страниц в файле, 12 файлов за вопрос, 30 файлов и 300 тыс. знаков документов на диалог (контекст DeepSeek — 1 млн токенов, ответ — до 384 тыс., api-docs.deepseek.com, 17.09.2026). Изображения внутри вопроса упирались в 15 МБ и минуту ожидания, поэтому **страница-изображение отправляется сразу при прикреплении**, по одной и не больше трёх разом (`POST /api/assistant/read`; в nginx у него свой `location` — 8 МБ и 180 с), и возвращается текстом, а вопрос несёт только текст. Каждая страница — запись `assistant_log` с `kind = 'read'` (миграция `0011`, выкладывается до перезапуска API) и своей стоимостью; лимит вопросов считает только `kind = 'question'`, лимит страниц — 20 на каждый вопрос тарифа (у Базового 60 в день и 2 000 в месяц); журнал в админке показывает вопросы, а страницы — отдельной колонкой расхода и счёта. **Документы уходят с каждым вопросом диалога** и стоят в первой реплике перед её текстом: уточнение «а вес позиции 5?» видит документ, а одинаковое начало переписки DeepSeek берёт из кэша (в живом прогоне уточняющий вопрос по пакету из 12 страниц стоил 0,05 цента). Чип документа открывает прочитанный текст, чтобы пользователь сверил расшифровку с оригиналом. Кроме PDF и фото читаются Excel (все листы, `readXlsxSheets`; калькулятор по-прежнему берёт первый), CSV (UTF-8 или windows-1251 — `fileText`: Excel в русской локали пишет CSV именно так) и Word (`readDocx`: абзацы и таблицы); на `.doc` и `.xls` — просьба сохранить в новом формате.

**Страница читается трижды, и числа сверяются** (`readPage`, `reconcileReadings`): основное чтение — двумя полосами из отрисовки в 2 400 px (`aiShots`, разрез по самой светлой полосе у середины без учёта линеек таблицы), ещё два — целиком в 1 600 px. Всё это выведено замерами на реальном инвойсе на 21 строку. Модель ужимает изображение примерно до 1 144 токенов пропорционально площади, так что крупнее рисовать страницу целиком бесполезно, а полоса вдвое меньшей площади читается крупнее. JPEG 0,95 вместо 0,85 — итог верен в 3 прогонах из 4 против 1. Пересжатие (поворот готового JPEG) даёт ошибку почти в каждом прогоне, поэтому перевёрнутая страница рисуется заново из PDF. Одно чтение давало верными суммы, итог и строки 1–4 в 2–3 прогонах из 4, сверка трёх чтений — в 16 сочетаниях из 16 на сохранённых ответах модели; основой должно быть самое чёткое чтение (с чтением целиком в основе — 5 из 16). Число подтверждено, если его прочло ещё одно чтение; неподтверждённое заменяется тем, в чём сошлись два других; нерешённое и важное — суммы и веса, количества и коды без ведущих нулей — уходит пометкой «[Не подтверждено повторным чтением: …]», не больше 12 пунктов: без этого фильтра список артикулов «000506» заслонял настоящие расхождения. **Большинство бывает неправо**: количество «6» в строке 19 две модели из трёх читают как «8». Это ловит `sum_check` («количество × цена ≠ сумма»), а когда сумма строк сходится с итогом, он велит считать по итогу — иначе модель отказывалась считать платежи. Живой прогон пакета из 12 страниц (текст, этот инвойс вверх ногами и боком, плотный скан, китайский инвойс, CMR, акты ЕЭК): чтение около 40 секунд и 4,1 цента вне пика (одно чтение — 1,35), суммы перевёрнутого инвойса 21 из 21 (при одном чтении — 16), плотного скана 55 из 55, платежи верны. **Положение страницы определяет Google Vision, а не модель (18.09.2026).** У каждого слова Vision отдаёт рамку, и первые две её вершины задают направление чтения; большинство голосов даёт угол поворота точно на четыре стороны (`visionTurn`). Замер на пяти настоящих страницах во всех четырёх положениях — 20 снимков из 20 при согласии 85–100% слов, тогда как модель различает только «прямо или вверх ногами» (22 из 22), а четыре положения — 39 из 44, путая «влево» и «вправо». Поэтому Vision спрашивается **первым**, до чтений: повёрнутая страница возвращается браузеру за 1,4 секунды и бесплатно, вместо трёх чтений и вопроса о положении на 40 секунд, которые потом выбрасывались. Браузер рисует её заново под нужным углом (`shoot(turn)`, 0/90/180/270; у PDF — поворотом самой отрисовки, у фото — поворотом холста по четверти, чтобы JPEG кодировался один раз). Порог нужен: при менее чем 20 словах или согласии ниже 70% поворот не возвращается — на почти пустой странице геометрия ничего не значит. Вопрос модели о положении остался запасным путём на случай, когда Vision недоступен. `AI_READ_SINGLE=1` в `.env` — одно чтение, втрое дешевле. **Третье мнение — Google Cloud Vision (18.09.2026).** Страница уходит и на распознавание Google (`OCR_GOOGLE_SA` — путь к ключу служебного аккаунта; `/opt/tnved/server/.vision-sa.json`, владелец `tnved`, права 600, в репозитории закрыт `.gitignore`). Ключ служебного аккаунта — не пароль к API: доступ даёт токен в обмен на JWT, подписанный закрытым ключом (`googleToken`, node:crypto, без google-auth-library); токен живёт час и кэшируется. Vision **подтверждает числа, но не решает за модель**: его текст идёт сплошняком, без строк таблицы, поэтому число считается подтверждённым, если Vision видел его где угодно на странице. Так верное «6» в количестве устояло против двух чтений модели, читавших «8». Требовать согласия Vision ещё и на замену нельзя: на плохо читаемой странице он сам пропускает число, и в живом прогоне из-за этого остался неисправленным итог «583 476,40». Замеры на реальном инвойсе: сам по себе Vision прочёл страницу целиком верно (21 сумма из 21, итог, цена 41 260,35 — та, которую модель путает с 4 260,35) за 1,1 с; со сверкой трёх чтений модели всё верно в 16 сочетаниях из 16 против 8 из 16 без него, а пометок «сверьте с оригиналом» в живом прогоне стало 12 и 4 на страницу вместо 36 и 14. Цена: 1 000 страниц в месяц бесплатно, дальше $1,50 за 1 000 (плюс НДС 12% — Google обслуживает клиентов в Кыргызстане); проекту нужен платёжный аккаунт, без него Vision отвечает 403 «requires billing to be enabled» и помощник просто читает без него. Изображения Google обрабатывает в памяти, не хранит и не использует для обучения — и назван в `privacy.html`. **Четвёртое мнение — Google Document AI, и только при расхождении (18.09.2026).** Процессор Custom Extractor «AssistKG Document Extractor» (регион eu, `OCR_DOCAI_PROCESSOR` в `.env` — «eu/6d6d7c780082ca2c» или полный путь; ключ тот же `OCR_GOOGLE_SA`) читает страницу не текстом, а полями: номер и дата счёта, стороны, строки таблицы с кодом, весом, местами и суммой. Он дорог и медленен — 3 цента и около 30 секунд на страницу против 0,5 цента и 40 секунд у трёх чтений модели, — поэтому вызывается, только когда сверка чтений оставила нерешённым важное число; его числа подтверждают сверку, как Vision, а разбор приписывается к расшифровке блоком, которому модели велено верить при расхождении с таблицей. Замер на реальном инвойсе: 37 с, 0,033 $, 21 строка, и он назвал пользователю то, что раньше уходило молча (в строке 7 напечатано 6 849,00, модель читает 8 849,00). **В развёрнутую версию вшит свой снимок схемы, и правка схемы в консоли до неё не доходит** — это проверено: у версии `invoice-cmr-foundation-v1` в `line_item` не было `unit_price`, хотя в схеме набора данных он стоял. Поэтому «в ответе нет поля» — это про версию, а не про качество чтения: сравнивай `documentSchema` версии (`GET …/processorVersions/<id>`) со схемой набора данных (`GET …/dataset/datasetSchema`, только v1beta3). Новая версия делается из текущей схемы за полминуты и без обучающих примеров — `processorVersions:train` с `baseProcessorVersion` (модель-основание) и `documentSchema`, затем `:deploy` и `:setDefaultProcessorVersion` — **и обязательно перечитай процессор после переключения**: 18.09.2026 вызов не выполнился (скрипт был уже удалён), ошибка утонула в цепочке команд, и бой несколько часов работал на старой версии, тогда как записи уверяли в обратном; старая версия остаётся развёрнутой и служит откатом, но занимает место (и, если Google берёт плату за хостинг версии, деньги), поэтому её стоит снять с развёртывания, когда новая себя показала. **Схема набора данных правится по API** (`GET/PATCH …/dataset/datasetSchema`, только v1beta3) — поля добавляются к существующим, переименовывать и удалять их не нужно и Google может не дать. Так в `line_item` добавлены **`hs_code`** (код ТН ВЭД, напечатанный в строке инвойса) и **`country_of_origin`**, а в `invoice_details` — `currency`: код и страна решают ставку и преференцию, то есть идут прямо в расчёт. Версия `invoice-cmr-foundation-v3` с ними читает тот же инвойс на 21 сумму из 21 (у версии без них — 19 из 21) и даёт в каждой строке `hs_code 853710980019` и `country_of_origin GERMANY`. **Количество Google заполняет через раз, а сумму и цену за единицу — почти всегда**, поэтому `docaiRead` считает количество делением: 247 562,10 ÷ 41 260,35 = ровно 6 — то самое, что модель читает как «8». Роль Document AI API User даёт только `:process`: `processors.get` и `processorVersions.list` отвечают 403, и схему приходится читать по самому ответу — а **ответ приходит деревом**, строки таблицы лежат внутри `invoice_details`, и разбор на один уровень показывает «поле line_item», пряча поля строки. Псевдонимы версий (`default`, `stable`, `rc`) могут указывать на разные снимки схемы, поэтому сравнивать надо не их, а ответ без версии с ответом по её номеру. Document AI назван в `privacy.html` вместе с местом обработки (ЕС). **Главные деньги здесь — не страницы, а хостинг: развёрнутая своя версия стоит $0,05 в час, то есть $36,50 в месяц и $438 в год, звали её или нет** (цена прочитана со страницы cloud.google.com/document-ai/pricing 18.09.2026, там же сказано «One processor version deployed for a year costs $438»). Обработка страницы у своего экстрактора — 3 цента, у готового Invoice parser от Google — 10 центов, но у готовых процессоров хостинга нет вовсе: плата за него относится только к своим. Отсюда порог: своя версия окупается примерно от 520 страниц разбора в месяц, ниже — дешевле готовый процессор. **Но на реальном инвойсе готовый проиграл, и порог не решает.** Замер на той же странице (18.09.2026): готовый Invoice parser — 9 секунд, но 15 строк вместо 21, суммы верны 13 из 21, в количество попал вес («235,00»), наименования склеены в «Electrical control panels» на все строки; своя версия v3 — 45 секунд, 21 строка, суммы 21 из 21, цена за единицу и `hs_code` у всех 21. Инвойс нестандартный (турецкий, с колонками веса, мест и кода), а готовый процессор обучен на типовых; отдавать модели блок, которому велено верить, при 13 верных суммах из 21 опаснее, чем не отдавать ничего. Поэтому платим за свою версию, а если стандартная плата станет лишней — её можно просто снять с развёртывания: помощник переживёт это молча. Поэтому **держи развёрнутой одну версию**, а старые снимай (undeploy обратим за минуту и ничего не удаляет), и проверяй это после каждой новой версии. Отказ разбора система переживает: `docaiRead` ловит любую ошибку, страница возвращается с расшифровкой и пометкой о несверенных числах, просто без блока полей, и плата за несостоявшийся разбор не начисляется — это проверено тестом на ответе «ProcessorVersion is not deployed».

**Какие документы приносит кыргызский импортёр, и почему схема — их объединение (18.09.2026).** Владелец предложил оттолкнуться от того, какие инвойсы бывают, и два настоящих пакета оказались устроены по-разному. **Пакет 1** (Турция → Ноокат): CMR турецко-немецко-английской формы, коммерческий инвойс на 21 строку латиницей (артикул, наименование, количество, цена, сумма) и **отдельный packing list** теми же 22 строками, где живут код ТН ВЭД (853710980019), места и веса нетто/брутто, а внизу «GOODS ARE OF GERMANY ORIGIN». Деньги — в инвойсе, веса и код — в упаковочном листе, и это разные страницы одного пакета. **Пакет 2** (Турция → Бишкек): CMR другой формы (нумерация полей не совпадает, номер инвойса стоит в поле «приложенные документы») и **одна страница «COMMERCIAL INVOICE & PACKING LIST» по-русски**: Наименование | Код | Места | Количество (шт) | Вес брутто | Вес нетто | Всего в $, с итоговой строкой и «CIP Бишкек» — **цены за единицу в ней нет вообще**. Отсюда правило: схема Document AI должна быть объединением (`code` и `hs_code`, `places`, `quantity`, `unit`, `unit_price`, `total_price`, `net_weight`, `gross_weight`, `country_of_origin`), и ни одно поле нельзя считать обязательным. Замеры на русской странице: Document AI — 18 секунд, все 5 строк с кодом, местами, количеством, обоими весами и суммой, плюс валюта, итог 24 600 и страна; полный путь чтения — **3,6 секунды и 0,11 цента**, и Document AI не понадобился вовсе, потому что три чтения сошлись. То есть на простой странице дорогой разбор не включается сам, как и задумано.

**Четыре чужих образца из сети (18.09.2026), чтобы не мерить на двух своих.** Взяты публичные образцы: китайский коммерческий инвойс, китайская экспортная декларация, сертификат происхождения СТ-1 и экран 1С с УПД. **Китайский инвойс** разобран целиком — артикул, `hs_code`, места, количество, единица, цена за единицу, сумма, страна, валюта USD и итог 27 272,32 (20 с). **Экспортная декларация** дала Document AI почти ничего — она не инвойс, схема не про неё, — но расшифровка модели собрала форму таблицей с ярлыками полей: 成交方式 FOB, 运费/率 0, 运抵国 俄罗斯联邦, 包装种类 纸箱; нечитаемые из-за низкого разрешения ячейки помечены «[неразборчиво]», а не выдуманы. **СТ-1** дал строки с местами и обоими весами, номер и дату контракта, отправителя и получателя. **Экран 1С** прочитан как экранная форма, с номером и датой. Выводы два: путь чтения не привязан к виду документа и держится на всех четырёх, а **Document AI осмыслен только на инвойсах и накладных** — на прочих документах он молчит, и это правильно, потому что зовётся он лишь при расхождении чисел. Мелочь на будущее: у СТ-1 колонка «критерий происхождения» (П/Д) попадает в `country_of_origin` — если этот документ станет важен, поле надо будет развести.

**Условие поставки — дыра, которую открыл этот разбор.** `calc_payments` принимал стоимость и молча считал её таможенной. В обоих пакетах поставка включена (DAP Kant, CIP Бишкек), поэтому ошибка не проявлялась, но на типичном китайском инвойсе FOB или EXW перевозка до границы в цену не входит, и платежи вышли бы заниженными без единого признака. Теперь инструмент принимает `incoterm` и `transport`: перевозка прибавляется к стоимости и печатается в расчёте отдельным слагаемым, а при EXW, FCA, FAS и FOB без `transport` ответ начинается с «⚠ расчёт занижен» и требования спросить фрахт. Условие поставки инвойсы пишут прямо в таблице, и модель обязана его передавать — это в промте.

**Инвойс на несколько строк считается одним вызовом, потому что сбор — один на декларацию (18.09.2026).** `calc_payments` считал по одному коду и в каждый ответ вписывал таможенный сбор; на живом прогоне настоящего инвойса на пять строк модель честно вызвала расчёт пять раз и сложила сборы — **8 755,28 сом вместо 8 605,08**, потому что в мелкой строке срабатывал минимум в 500 сом. На инвойсе из 21 строки так набежало бы 10 500 сом минимумов вместо одного сбора. Поэтому у инструмента появился `items`: весь инвойс уходит одним вызовом, `calcBatch` считает пошлину и НДС по каждой позиции, а сбор — один раз от общей таможенной стоимости (п.38 Инструкции к ПКМ КР № 79 привязывает его к помещению товаров под процедуру, то есть к декларации, и вилку 500–250 000 сом применяет там же). После правки тот же вопрос дал сбор 8 605,08 и один вызов вместо пяти. Ревью того же дня закрыло, что осталось: **фрахт на весь инвойс (`transport` верхнего уровня) распределяется по позициям пропорционально стоимости**, как режим «по стоимости» в `computeBatch`, — первая версия его молча теряла; из позиции берутся только `code, value, quantity, country, transport` (валюта, дата и условие поставки общие); непосчитанные позиции названы отдельным блоком и в сбор не входят; предупреждения и сноски печатаются один раз на код; расчёт одной позиции — `calcOne`, а `calcPayments(input)` лишь выбирает путь, чтобы внутренний флаг не был доступен из входа модели, и `runUses` приводит результат любого инструмента к строке. **Это тот же урок, что и везде здесь: правило «не складывай сборы» в промте модель соблюдала бы через раз, а один вызов с `items` не оставляет ей выбора.**

**Качество меряется контрольным набором, а не на глаз.** `node server/tests/assistant-eval.js [фильтр]` — 13 вопросов на настоящем API (платно, ~100 тыс. токенов, запускать на сервере, где есть ключ): нужный код, нужный инструмент, отсутствие воды. Ответ модели недетерминирован: один и тот же код за три прогона даёт 11–12 из 13 с разными провалами, поэтому сравнивай варианты промта не по одному прогону и **читай сами ответы** — галочки не ловят фактических ошибок (НДС «20%», «СТ-1» для ЕАЭС прошли все проверки). Сноски ЕЭК к ставкам («63С)») и к наименованиям («12)») — `private/ett-footnotes.json` из `tools/build-ett-footnotes.js`; помощнику идут только действующие для КР на дату. **Пометка в тексте PDF склеена со ставкой** («шт 563С)» = 5 и 63С) и делится по ставке из `ETT_DB`; число, которое так не делится, — повод проверить саму ставку (так найдена 2826 30 000 0: 5,5, а не 5), и с 82-й сноски буква латинская «C». Помощник принимает фото инвойсов: DeepSeek-flash читает изображения сам (проверено), страницы — по одной через `/api/assistant/read`, лимит тела 15 МБ только для него и `/api/assistant`. **Стоимость вопроса считается по каждому раунду в момент вызова** (`roundCost`, миграция `0009`): у DeepSeek вход из кэша (`cache_read_input_tokens`, в `input_tokens` не входит) в 50 раз дешевле, а часы пик вдвое дороже, поэтому по суммам токенов стоимость задним числом не восстановить; цены — `AI_PRICES` в `.env`, отчёт для счёта — `/api/admin/assistant/billing?month=`. Прогоны контрольного набора в журнал не пишутся — сумма журнала меньше счёта DeepSeek. **Тарифы по числу вопросов** — `users.ai_plan`, лимит в день и в месяц по Бишкеку (base 3/100, pro 20/300, max 60/1000, `PLANS` в `routes/assistant.js`); при исчерпанном месяце отказ говорит про месяц, а не «завтра»; вопросы с ошибкой не списываются, но их расход пишется в журнал (`err.usage` из `ask`), админы без лимита. **Один вопрос в работе на пользователя** (`inFlight` в `routes/assistant.js`, отказ `429 busy`): журнал пополняется только после ответа модели, то есть через десятки секунд, и без этого параллельные запросы проходили лимит все разом — на заглушках 10 из 10 при лимите 3 в день. Прежняя оценка «параллельные запросы у границы пройдут на один-два сверх» была неверна: окно — всё время ответа, а не миллисекунды. `has` и `add` стоят до первого `await`, иначе два запроса проскочат между ними. **`/api/auth/me` не отдаёт `id`** — не привязывай к нему клиентские ключи и держи заглушки `/me` в тестах такими же, иначе тест пройдёт, а сайт нет. **Новая колонка, которую читает `middleware/auth.js`, выкладывается миграцией до перезапуска** — иначе падает каждый запрос. Промт сокращён с 40 до 14 КБ без потери правил: при равном счёте короче — дешевле каждый раунд. Pro-модель на двух вопросах была короче, но ошиблась в коде (8517 14 вместо 8517 13) — flash оставлена. Примечания пересобираются `node tools/build-tnved-notes.js <папка>` из PDF групп со страницы ЕЭК (текст извлекается pypdf заранее; сборщик проверяет, что групп ровно 96). Проверки: `node server/tests/assistant.test.js` и `assistant-browser.test.js` (с `PLAYWRIGHT_MODULE`, модель и БД подменены).

## Mobile wrapper (`mobile/`)

A thin Capacitor shell (`kg.tnved.checker`) for Android and iOS. It ships no copy of the app: `capacitor.config.json` sets `server.url` to the production origin, so the WebView simply loads the deployed site and every `/api/*` call is same-origin. Two consequences worth remembering:

- Tightening anything origin-related on the backend is safe for the app, because the WebView's `Origin` is exactly one of the origins in `APP_ORIGIN`. That is what made the CSRF check in `server/src/index.js` safe to make fail-closed. Since the move to a real domain that setting holds a list, and the app's pinned origin must stay in it.
- Changing `server.url` means rebuilding and re-releasing the app, so the production origin is effectively pinned by the store listings. It was moved to `https://customsassist.trade` on 11.09.2026 (versions bumped to 2 / 1.1 for Android and iOS), **but the change only reaches a phone through a store release.** The urgency this used to carry was based on an assumption that no one had checked: there is no public release in either store (verified 12.09.2026, see «Addresses» above), so no installed copy is stranded. Releasing 1.1 is ordinary work, not a rescue — and if nothing was ever uploaded to Play Console, the lost 1.0 upload key costs nothing either, because Play App Signing enrols whatever key signs the **first** upload. **Establish which case you are in before planning around a key reset**: the reset is only needed when an upload key is already registered, i.e. when something was uploaded to any track at some point.
- **The app's name on the phone is not in `capacitor.config.json`, and `npx cap sync` will not change it.** Capacitor fills `android/app/src/main/res/values/strings.xml` (`app_name`, `title_activity_main`) and `ios/App/App/Info.plist` (`CFBundleDisplayName`) once, when the platform project is created; after that they are yours to edit by hand. The rename on 13.09.2026 from «Проверка ТН ВЭД» to «Customs Assist» touched eleven places across the repo, and `appName` in the config was the *least* load-bearing of them. The string is compiled into the package, so renaming needs a rebuild and a new `versionCode` — and the result must be checked against the built artifact (`aapt2 dump badging app-release.apk | grep application-label`), never against the source.
- **Keep the native label and the manifest's `short_name` identical.** Both can end up on the same phone — the APK and a copy installed from the site — and two different captions under two identical icons read as a bug. They are «Customs Assist» in both places; the page `<title>` and the manifest `name` carry the fuller «Customs Assist KG — проверка ТН ВЭД».
- **The origin change logs every updating user out once.** Session cookies belong to an origin, so a WebView that starts loading a different one arrives with no cookie. This is expected and needs no fix, but it is worth knowing before the release notes are written.
- Native projects keep their own generated copy of `capacitor.config.json` (`android/app/src/main/assets/`, `ios/App/App/`). Both are gitignored and rebuilt by `npx cap sync`, which the iOS workflow runs; after editing the root config run `npx cap sync` locally too, or a local Android build silently keeps the old origin.

**The phone is a first-class width, not a fallback — and it is measured, not eyeballed.** The wrapper is a WebView over this same site, so a CSS change reaches every installed copy at the next deploy, with no store release; only `server.url` needs one. That makes the narrow layout worth the same care as the wide one. The audit on 12.09.2026 measured an iPhone 14 (390×844) and found the header occupying 153 px, the hero banner 136 px and the search field starting at y=345 — **46 % of the first screen spent before the thing the app is opened for.** The header was three right-aligned rows (theme switch, user bar, access status) stacked by desktop rules, which on a phone reads as a ragged left edge. It is now one wrapping flex row inside `header`, ordered by `order:` so the theme pill and the email share the top line and the access chip takes the second; the theme labels moved into `<span class="ts-txt">` so the words can be dropped and the emoji kept, exactly as `.auth-theme .at-txt` already does on the login screen. Search now starts at y=188.

Five rules from that pass generalise:

- **`viewport-fit=cover` or `env(safe-area-inset-*)` is always zero.** Without it the notch and the gesture bar cut into the page in a WebView, and nothing in a desktop browser ever shows you this.
- **Never put a text input below 16 px on iOS.** Safari zooms the page in when such a field takes focus and does not zoom back out. `.si` is 17 px on phones for that reason alone.
- **An absolutely positioned overlay must be measured against the element it overlays, not its wrapper.** `.sico` is `position:absolute` inside `.sw`, and `.sw` also held the field's `<label>` — so the button was offset by the label's height and hung over the input's top edge, at *every* width. The fix is structural: the label moved out of `.sw`, which now contains only the input and the button.
- **A right padding smaller than the overlay it clears is text running under a button.** The mobile rule had `padding-right:48px` under a 46 px button offset 8 px from the edge.
- **Check the tap targets with a script, not by eye.** Buttons measured 29 px; `.btn` is now 38 px on phones with 44 px for the standalone ones (Apple HIG and Material both ask 44–48, and 38 is a deliberate compromise for a reference app this dense — say so rather than pretending it meets the guideline).

The horizontally scrolling badge strip keeps a `mask-image` fade on its right edge: it was scrollable all along with nothing to say so.

**The site installs to a home screen without either store, and that is the cheap path.** Publishing costs money the owner had not counted on — Google Play is a **one-time US$25** registration fee and the Apple Developer Program is **US$99 per membership year** (both read off the official pages on 12.09.2026, not from memory). So on that day the site became installable on its own: `manifest.webmanifest` at the root, icons under `icons/`, and the `<link rel="manifest">` plus Apple meta tags in the page `<head>`. A phone gets an icon, its own window with no browser chrome, and the same live site — with no review, no fee and no release cycle.

Four things about it are deliberate:

- **No service worker.** Chrome no longer requires one for installability (the current criteria are a manifest with 192 and 512 px icons, `start_url`, `display` and HTTPS), and with a 12 MB application script behind the page any caching layer risks serving yesterday's file — the exact failure this project has already lived through. Skipping it keeps "deploy = everyone sees it" true.
- **Nginx does not know `.webmanifest`** and served it as `application/octet-stream`, which Chrome ignores silently — no manifest, no install prompt, no error. Fixed with `location = /manifest.webmanifest { default_type application/manifest+json; }` in the site config rather than by editing `/etc/nginx/mime.types`, which a package upgrade would overwrite.
- **The icon is the emblem cropped out of `logo_mark.png`, not the whole lockup.** The lockup carries the wordmark under the emblem, and at 48–72 px the lettering turns to mush; the crop keeps only the emblem (sun, mountains, document), which reads at any size. Everything is generated from the two source files by one script — icons, the `<head>` favicon, the login-screen plate and `email-logo.jpg` — so re-cutting them is a re-run, not five hand edits. The maskable variant sits at 62 % on **white**, not on the navy the previous icon used: this mark's mountains are navy and would disappear into it, and Android crops maskable icons to a circle or squircle while guaranteeing only the central 80 %.
- **`apple-mobile-web-app-status-bar-style` is `black`, not `black-translucent`.** The translucent setting puts page content under the clock, which would need checking on a real iPhone that nobody here has.

`privacy.html` at the repo root is the only text of the privacy policy. It exists as a standalone, publicly reachable URL because app-store review requires one that works without logging in, and since 17.09.2026 the app's «Политика конфиденциальности» link opens a modal that leads to it — until then that modal was a «документ в разработке» stub, although the policy was in force (the other two footer documents, the terms of use and the consent to cross-border transfer, are still stubs: they do not exist yet, and writing them is the owner's call). **Its «Сторонние сервисы» section must name every outside party that receives user data**: Resend (address and letter), Cloudflare Turnstile (IP and browser signals on the login page and in server-side verification), DeepSeek (assistant questions). Until 17.09.2026 the policy said data went to no third party «за единственным исключением» of DeepSeek, which was false for the first two.

Builds run in Codemagic (`mobile/codemagic.yaml`); `mobile/android/local.properties` and both `node_modules` are gitignored.

## Architecture

### One file, one pattern, repeated ~37 times

Nearly the entire script is variations on: **one `SCREAMING_SNAKE_CASE` const holding a legal database, one `findX(query)` function that looks a code up in it, one block in the central `render()` that turns a hit into a result card.** Examples: `BAN_DB`/`findBan`, `VET_DB`/`findVET`, `PHYTO_DB`/`findPHYTO`, `TR_EAEU_DB`/`findTREAEU`, `ETT_DB`/`findETT`, `SPECIES_DB`/`findSpecies`, `NTM_DB`/`findEEC30`, `SAN_SECTIONS`/`SAN_REG_DB`/`SAN_SUB_DB`/`SAN_SECTION3`/`findSAN`, etc. When adding a new legal source, follow this same triplet rather than inventing a new shape.

**Before adding an act's section to one database, check whether another already covers it.** The file has ~40 `findX` functions, so "the base doesn't have this" is only meaningful after checking all of them. Section 1.2 of Решение №30 was added to `NTM_DB` in this session and turned out to be already served by `EEC_WASTE`/`findEECWaste`, so code 4013 10 000 0 showed two cards for the same ban until the duplicate was removed.

`render(q)` (search for `function render(q)`) is the dispatcher for the default "search by code" mode: it calls essentially every `findX(qt)` in one shot, and if every result is empty shows a "not found" card; otherwise it concatenates one `<div class="card c-...">` block per non-empty result type, in a fixed order. If nothing matches by code, `render()` itself falls back to a name-based match (`findByName`/`nameMatchesHtml`) rather than that being a separate mode. **A database whose natural query is a name, not a code, has to be wired into that fallback explicitly.** `TROIS_DB` is the case: a user looking for a trademark types «VENTANA», not a ТН ВЭД code, so `findTROISByName()` runs in the same branch and its card is emitted *before* `nameMatchesHtml()` — the brand query is about the register, and any ЕТТ name hits are incidental. Adding such a database with the usual `findX(code)` triplet alone leaves it unreachable by the only query people actually bring to it. The same applies to preferences: `findPrefByCountry`/`prefCountryHtml` were added on 11.09.2026 because the question people bring is «what can I bring from Bangladesh», and the 79 ЕСТП countries sat as plain text inside a card that only a ТН ВЭД code could summon. It answers for both regimes at once — ЕСТП and the five countries with their own agreement — because Iran and Mongolia are in both and an agreement does not displace ЕСТП.

**Match a country by word start, not by fuzzy prefix.** The act names countries formally («Гвинейская Республика», «Федеративные Штаты Микронезии») while people type «Гвинея», «Микронезия». A shared-prefix rule fixes those two and immediately breaks something else: at the threshold that catches Гвинея/Гвинейская it also ties «камера» to «Камерун» (five characters of six). Use word-start matching plus a whole-name `indexOf` for queries of five characters or more, and give the four adjective/genitive names (Гвинея, Сирия, Иордания, Микронезия) an explicit alias. Prove the result both ways: every one of the 79 countries must be findable by its own distinctive word, and a list of ordinary product queries («камера», «ткань», «сахар», «лампа»…) must return nothing. Note that several queries legitimately return more than one country — «Конго» is two states in *different* ЕСТП lists (75% and 0%), and «Нигер», «Судан», «Гвинея» likewise; that is the right answer, not noise. The two other search modes still wired up by `setSearchMode()` and dispatched from the single debounced `#inp` input listener are `renderSpecies` and `renderCalcSearch`; a former VIN-lookup mode (`renderVIN`/`findVIN`) and a manual "Авто" text-search mode (`renderAuto`/`findAuto`) were both removed as dead code (see session.md, 28.08.2026 and 30.08.2026 entries) — don't resurrect those names expecting them to still exist.

### «Справка по товару»: direction and country are a filter, not a caption

**Since 18.09.2026 the справка is not a page but a row under the search field** (`#srchCond`: направление · страна · дата, the fields keep their ids `lookupDir`/`lookupCty`/`lookupDate`), because the owner saw two entries that were «по сути одно и то же». `render()` calls `applySearchConditions()` after the post-processing passes: import without a country changes nothing; otherwise `lkFilter(dir,cty,box)` hides cards into `<details class="lk-hidden">`, sections and the verdict are rebuilt without them, `lkHeadHtml` banners go on top and `lkApplyRates` rewrites the rates. Changing a condition re-runs the current query, and `#result[data-rq]` («query|dir|country|date») is set last — wait for it, not for cards, since the old cards stay visible while the new answer is loading. Everything below about how the filter decides still holds; only «page» now means the search page.

`renderLookupForm`/`submitLookup` ask in the order a customs decision is actually made — direction (ввоз / вывоз / транзит), country, and only then the goods — because the first two answers decide which of `render()`'s ~40 cards apply at all. The filter re-queries nothing: it reads three attributes that `render()` now writes onto the card itself.

- `data-dir="im"` — a measure that exists only on import: ЕТТ and every preferential rate, excise, УСИР, the ГНС VAT-base risk list, antidumping, tariff quotas, the trigger measure, обязательная сертификация, ТР ЕАЭС and all fifteen VAT-exemption cards. 30 cards carry it.
- `data-kind="tariff"` — the subset that an EAEU origin removes: in взаимная торговля there is no ЕТТ, no preference and no protective measure.
- `data-cty` — the origin the measure is tied to, spelled as the act spells it (`оаэ эмираты`, `кнр украина`, `estp` for the ЕСТП card).

**The default is "show".** A card without these attributes appears under every direction, which is why every ban, licensing rule and control card is always visible: hiding a restriction is a more expensive mistake than showing an irrelevant rate. Nothing is deleted either — filtered cards move into a collapsed `<details class="lk-hidden">` with the reason printed above each one.

**Transit is not "import without duties".** Under п.1 ст.142 ТК ЕАЭС goods are carried without payment of duties, taxes and special/antidumping/countervailing duties, but ст.143 п.1 makes both обеспечение of those payments (подп.1, 2) and соблюдение запретов и ограничений (подп.5, through ст.7) conditions of the procedure. So the transit view hides the fiscal cards and keeps every prohibition and control card. The official text is `eec.eaeunion.org/upload/iblock/93c/TK-EAES.pdf` (`DOC_SOURCES.tkEaes`); articles 7, 142 and 143 were read there on 16.09.2026, not from a summary of them.

**The country field reuses the ЕСТП matcher.** `lkCountry()` resolves what was typed through `prefCountryHit`/`PREF_C_ALIAS`/`findPrefByCountry`, so every trap already solved there stays solved («Гвинея» finds Гвинейская Республика, «камера» does not find Камерун). Only EAEU member states and China needed lists of their own — neither is in ЕСТП or in `PREF_FTA`. A country the base knows nothing about is an answer too: the preference cards are hidden and the banner says the ordinary ЕТТ rate applies.

**A new card in `render()` gets the filter for free, but only the default one.** A measure that exists solely on import needs its `data-dir="im"` in the same commit, or it will also be shown for export; the reverse omission is harmless. The check is `node server/tests/lookup-filter.test.js` — without a browser it resolves countries and counts the marked cards, and with `PLAYWRIGHT_MODULE` it drives the whole path through login to the filtered result.

**One field, and the page keeps the user.** The goods are one input, `#lookupQuery`: `render()` already tries the code first and falls back to the name, so two fields only made people guess which to fill. Navigation by code goes through `goToCode()`, which checks `currentPage`: from the lookup page it fills `#lookupQuery` and re-runs the справка with the chosen direction and country; from anywhere else it opens the ТН ВЭД search as before. The name-match list, the ЕТТ list rows and the «Быстрый поиск» chips in the right column all call it — the chips used to call `setSearchMode('code')` directly, which silently threw the user out of the справка and lost both answers. `renderLookupForm()` builds the form once (a return from пояснения or the классификатор no longer wipes the result), so `resetAppView()` now clears `#pageLookup` too.

**With a country chosen, the ЕТТ card shows the rate that applies to that origin.** `lkApplyRates()` runs after the filter and asks `lkPrefRates(code, ettRate, cty, date)`, which returns every applicable basis rather than one answer — Iran and Mongolia have both an agreement and ЕСТП, and which one is used depends on the certificate the importer holds. The rule for each country is transcribed from п.2 of its own decision, read on docs.eaeunion.org on 16.09.2026: UAE №113, Vietnam №36, Iran №1 and Serbia №122 set **0% for every code outside the list**, while Mongolia №74 gives a preference only to listed codes; UAE, Iran and Mongolia add «if the duty at the ЕТТ rate is lower, the ЕТТ rate applies». Vietnam's decision has no such clause, so where its list rate is above today's ЕТТ (3304 30 000 0: 11,3% against 6,5%) the card says that without claiming the preference the goods clear at ЕТТ. **The date field now matters.** The UAE schedule is in force from 06.10.2026 and runs by calendar year («на 2026 год» … «на 2033 год и последующие»), Mongolia from 22.07.2026; before those dates the card keeps the ЕТТ rate and says from when the preferential one applies — 0201 10 000 1 from the UAE is 15% on 16.09.2026 and 13,1% from 06.10.2026. A rate expressed as a share of ЕТТ (ЕСТП 75%, Mongolia's «скидка 50%») is computed by `lkScaleRate`, which scales the leading figure and the amounts before «евро»/«долл» and leaves «за 1 кг» and «100% спирта» alone; that is exact for combined rates because max(k·a, k·s) = k·max(a, s). **This needed the full Vietnam and Iran lists.** Until 16.09.2026 `ETT_VN_DB` and `ETT_IRAN_DB` held only the rows with a reduced rate (134 of 604 and 59 of 1736), following a note in `docs/legal-sources.md` that has since been corrected: with the «ставка ЕТТ» rows gone, a listed code was indistinguishable from an unlisted one at 0%. Both now carry the whole consolidated ЕЭК list as `[code, name, rate, из, code footnote, rate footnote]`; the first three fields kept their meaning, and all old rows were confirmed verbatim in the new data.

Along the way `enhanceResultCards()` stopped refusing to work outside `#result`: the «правовое основание» plaques and the raising of ban cards are just as useful on the lookup page. The summary is still built only for `#result`, because it writes into `#resultSummary`, which that page does not have.

### One window, two people: a view must be cleared on the way out, not just hidden

`#appWrap` and `#authScreen` are two divs of one page, and logging out only ever set `display:none` on the first. Everything the previous user had on screen — the admin table of all accounts, their search results, their own address in the user bar — stayed in the DOM, so a person who registered in the same window right afterwards saw it. Reported on 12.09.2026 by exactly that route: the owner logged out of the admin account, registered as an ordinary user and got the full user list.

**The data was never re-served.** `routes/admin.js` mounts `router.use(requireAdmin)` and a live probe with the new user's own session returned `403 {"error":"forbidden"}` for `GET` and `POST /api/admin/users`. That is what makes this a client-side leak rather than an authorisation hole — and it is also why it is easy to miss: every server-side check passes.

Two fixes, and the split between them is the point. `resetAppView()` empties the elements one user fills and the next must not inherit (`result`, `resultSummary`, `adminResult`, `userBar`, `accountPanel`, `calcPrintArea`, `pageLookup`, `speciesResult`, `#inp`, the verify bar) and resets `searchMode`/`currentPage`; it is called both from `doLogout()` **and** at the top of `showApp()`, because a session can also end without anyone pressing «Выйти». And `setSearchMode()` now refuses `'admin'` for a non-admin, falling back to `'code'` — the server would answer 403 anyway, but the mode renders its markup before the answer arrives. **Add a new element that holds per-user content and add it to `resetAppView()` in the same edit**; nothing else in the file will notice that you didn't.

### The login screen is the one dark surface, and its ids are load-bearing

`#authScreen` is a full-screen overlay holding four views — `authViewLogin`, `authViewForgot`, `authViewReset`, `authViewRegister` — that `showAuthView()` toggles. ### Two themes, switchable, and the theme lives in the tokens

On 11.09.2026 the interior was repainted to match the login screen: graphite canvas, glass panels, the same accent gradient. The first attempt used a saturated navy (`--bg:#0A0F20`) with near-white text (`#E9EDF8`) and the owner reported it as physically tiring — «болят глаза». **That was a contrast-too-high problem, not a contrast-too-low one**: 16.3:1 on a background with visible blue saturation makes small text halate. The shipped palette is the softened one — `--bg:#171A21`, `--text:#D7DBE3`, 12.5:1, background saturation down from 22 to 10. Aim for roughly 7-12:1 here; WCAG's 4.5:1 is a floor, not a target, and the audit below only catches the floor. **The whole theme is `:root` tokens** — `--bg`, `--surface`, `--text`, `--muted`, `--glass*`, `--shadow*` and the nine semantic hues — so a future re-theme is a token edit, not a sweep. Three things make that true, and breaking any of them re-opens work that is already done:

- **The semantic hues were raised in lightness, not renamed.** «Запрет — красный, разрешено — зелёный, ставка — розовый» still holds; the original values (`--red:#E0342B`, `--teal:#0E8A96` …) were picked for white and read as mud on dark, so they became `#FF7A72`, `#3FC7D4` and so on. The low-alpha rgba tints behind chips and icons were **left alone on purpose** — the same hue at 8-30 % over a dark ground gives the right muted wash, and repainting them would have been a hundred pointless edits.
- **One token could not serve both roles.** `--indigo` is a text colour in eleven places and a button background in three; lightening it for text dropped white-on-indigo buttons to 3.5:1. It was split: `--indigo` (light, for text) and `--indigo-surface` (deep, for the active nav item and the search button).
- **`@media print` now re-declares the light palette.** The print block used to inherit a light theme by default; with dark tokens a printout would be near-white text on white paper. It overrides `:root` back to light values inside the print media block only, plus `body`/`.card`/`.side-panel`/`.modal` backgrounds. Verified by emulating print media and reading computed styles: body goes `rgb(255,255,255)` / `rgb(17,17,17)`. Keep that block in sync when adding a token.

**Every colour that depends on the theme must be a token.** The first dark pass left a handful of values hard-coded in rules (`#7FD6EE` for cyan text, `#9AA8C6` for hints, the placeholder grey …). They looked fine, and then the first attempt at a light palette came back with 21 contrast failures — because those values stayed dark while everything around them turned light. They are now `--ink-cyan`, `--ink-blue`, `--ink-link`, `--hint`, `--placeholder` in `:root`, so a palette swap really is one block. If you add a colour that has to change with the theme, add a token; do not write the value into the rule.

**The old light theme was worse than either dark one.** Running the same audit against the pre-11.09 version reports **398** contrast failures on a single results page — small tinted chips on a light ground. So «просто вернуть светлую» is not a way out; a light palette for this app needs its chip colours redone first (about 13 of them).

**There are two themes and a switch.** Graphite dark is the default; light is grey (`--bg:#E8EBF1`), not white, because at this user's sensitivity a white ground is the same glare mistake in the other direction — 14.4:1 against 12.0:1. The light theme is `:root[data-theme="light"]` plus about twenty `[data-theme="light"] .selector` rules for the places where a translucent *white* glass fill is baked into the rule and cannot be expressed as a token. The choice lives in `localStorage` under `ca-theme`. The control sits **in the header, top right** — it was first put in the left nav list and the owner reported not finding it: among eight section buttons it reads as a ninth section rather than a setting. On the login screen the same control is a labelled pill in the top-right corner; the label matters, because a bare icon there was missed too.

**The switch is applied by a boot script in `<head>`, and that tag is deliberately `<script data-boot>`, not `<script>`.** The theme has to be on `<html>` before first paint or a light-theme user sees a dark frame flash on every load. `checker-access.test.js` and the server-side deploy check compile the page's first *bare* `<script>`, so writing the boot tag with an attribute keeps that check pointed at the auth script. If you ever add another script tag, keep that property or update both.

**A palette swap re-runs the audit in both themes.** The light theme was born with 147 contrast failures that the dark one never had, all from colours written as values rather than tokens — three quick-search chip colours set through `style.cssText` in JS. They are `var(--cyan)`, `var(--orange)`, `var(--pink)` now. Both themes report zero across ten scenarios.

**The audit has one blind spot worth knowing: gradients.** `getComputedStyle().backgroundColor` is transparent for an element painted with `linear-gradient`, so the checker walked up to the parent and reported white-on-indigo buttons as 1.05:1 — a false alarm that would have sent you chasing a non-existent defect. It now skips any element whose nearest painted background is a gradient. Prefer a solid `background-color` under text you want audited.

**Check contrast mechanically, not by eye.** The harness that made this safe opens the file over `file://`, injects a fake `currentUser` and calls `showApp()`+`initApp()` — that renders the whole interior without a backend — then walks every element with direct text, composites the effective background through transparent ancestors, and reports anything under the WCAG threshold (4.5:1, or 3:1 for large/bold). It found exactly five real defects across the search results and one more across the other seven pages, all of which would have been easy to miss by eye: a `#3b5070` hint colour at 2.07:1, white-on-indigo buttons at 3.5:1 and a primary button at 2.64:1. All eight pages now report zero. Re-run it after any palette change.

### A time-limited measure needs a machine date, or it stays red after it ends

Until 17.09.2026 no card knew dates. The ban card showed «⛔ Запрет вывоза» for livestock (ПКМ № 160, по 10.09.2026), fertilizers (№ 115, по 15.09), saplings (№ 103, по 01.09) and used catalysts (№ 116, по 05.09) after all four had lapsed, and the unilateral-measures card showed the same bans as «действующие» because the ЕЭК register snapshot (`UNIMEAS_ASOF` 24.08.2026) still flagged them so. The date was right there in the text; nothing read it.

- **`BAN_DB`**: a dated ban carries `exFrom`/`exUntil`/`imFrom`/`imUntil` (ISO, both days inclusive), and **`banOn(e, side, today)`** decides whether it is in force — for the card, `calcWarnings` and the batch summary alike. Out of term the card replaces the red tag with «⏳ Срок запрета … истёк — продление в базе не найдено» or «⏸ Запрет … действует с …», keeping the act text. A suspension is a start date: the oil-products import ban suspended by ПКМ № 484 through 01.04.2027 has `imFrom:'2027-04-02'`.
- **`UNIMEAS_DB`**: `findUniMeasure` clears the register's «действует» flag when every «до/по ДД.ММ.ГГГГ» in the term has passed (**`umTermEnded`**).
- **Tariff benefits and antidumping measures use the same idea.** A `BAN_DB` benefit carries `льгUntil` (`banOn(e,'льг')` — «⏳ Срок льготы истёк» after it); an `ANTIDUMP_DB` row carries its end date as the seventh element, taken from «до/по ДД.ММ.ГГГГ» or «вступила в силу …, действует N лет», and **`adActive(rec)`** gates the calculator warning «на этот код действуют …» and the batch line, while the card marks lapsed rows. The nearest ends when this went in were tyres 13.11.2026, pipes 21.12.2026 and the benefits 31.12.2026 — nothing had lapsed yet, which is exactly when to add the date.
- **Do not give a date where a perpetual act continues the ban**: 7204 has ПКМ № 564 (по 03.03.2027) *and* the бессрочный Указ УП № 375, so it has no `exUntil`. `lookup-filter.test.js` requires a machine date on every ban whose text starts «Запрет на … до/по ДД.ММ.ГГГГ», except when the text names a бессрочный act.
- **An expired term is a question for the registry, not a conclusion.** Extensions arrive as new resolutions or amendments: read the document card (`GetDocument` → `editions`, `documentReferences`) of the act, and remember the registry lags signing by one to two weeks — which is why the card says «продление в базе не найдено», not «запрет отменён». On 17.09.2026 that check found the 7204 extension (ПКМ № 564, реестр 7-58055) and no extension for the other four.

### The result list is styled by post-processing, not by the card templates

Three passes run over the finished markup of `#result` after `render()` writes it, in this order: `compactifyCards()` (collapse everything after `.tags` behind a click on the header), then `enhanceResultCards()`, which calls `buildResultSummary()` last. Doing this on the DOM rather than in the ~40 card templates is deliberate — a layout change would otherwise have to be repeated in every template — and it means **a new card template gets all of it for free, as long as it follows the existing shape** (`.rh > .ico + .rc`, then `.rn`, then `.tags`, then the details).

What each pass keys on, so a new template does not silently opt out:

- **The summary banner reads the cards' own `.tag` elements** — their text becomes the chip's bold label and their class its colour (`SUM_TAG_COLOR`), while the card's `.rn` becomes the rest of the line and `SUM_FLAG_ORDER` its position. There is deliberately no "card type → risk" table to keep in sync; give a new card a tag with an existing `t-` class and it shows up correctly. The banner is skipped when there is only one card. **It is one row per card, not two.** Until 10.09.2026 it drew risk chips from the tags and jump buttons from the `.rn` texts in two separate rows, which said the same thing twice — «🛡️ Товарный знак в ТРОИС» above «🛡️ По этому коду … есть действующие товарные знаки». They are merged into one clickable line per card (`.sum-items`/`.sum-item`); a card with no tag still gets a line, or it would be unreachable. The tell that two such rows should be merged is that their elements correspond one-to-one to the cards.
- **A card is "alerting" (raised to the top of the list, red frame) if it carries a ban tag** — `t-ex`, `t-im`, `t-eec-ex`, `t-eec-im` — not if it carries class `c-ex`, which list cards use too. Already-raised cards are marked `data-ord`, so the classification-precedents card that arrives asynchronously does not re-trigger the entry animation of everything else.
- **Anything the user must see while the card is collapsed has to be moved out of `.card-more` explicitly.** `.ett-rate` sits after `.tags` in the template, so collapsing hid the duty rate — the very number that card exists for; `enhanceResultCards()` moves it back. The same applies to any new "headline" element placed after the tags.
- **`auditNote()` renders a `<details>`,** not a paragraph: only the status line and the date stay visible on the card. Its text runs to 2-3 kB, which is why `.card.open .card-more` allows 9000px.
- Links found anywhere in a card are collected into a `.legal-basis` plaque above the collapsed part (deduplicated by URL, first four shown). That is one more reason to route a verified citation through `docLink()`: an `<a>` reaches the plaque, plain text does not. **A link that belongs to one row of a list, not to the card, must carry class `lb-skip`** — the collector takes `a[href]:not(.lb-skip)`. The ТРОИС card is why: every row links to its own page of the register (`#page=63`, `#page=270`, …), and without the opt-out a card with a dozen rows filled its plaque with page links while the acts fell into "+ ещё N".

**A skewed results grid is never about the grid — it is one unbreakable token.** `#result` becomes a two-column grid while a search is active, and on 11.09.2026 its columns came out 332 px and 1296 px with the page scrolling horizontally to 2007 px at a 1280 px viewport. `1fr` means `minmax(auto, 1fr)`, and a track's automatic minimum is the min-content width of the widest item in it — so one item can widen a whole column. Find it by measuring, not by eye: set `width:min-content` on each card in turn and rank them. Eleven cards measured 150-333 px; the Mongolia preference card measured 1296 px because its `.det` carried a **percent-encoded URL 205 characters long** pasted in as plain text. A sweep over 380 codes confirmed it was the only one — every other long token is at most 82 characters (chemical names, ordinary links). Two structural fixes went in alongside routing that URL through `docLink()`: `repeat(2,minmax(0,1fr))` on the grid, so no item can ever widen a track again, and `overflow-wrap:anywhere` on `.card`, so a long token wraps instead of stretching the card. This is the limit of the "paste a verified URL as plain text" convention documented above: it is safe until the URL is percent-encoded, and Cyrillic in a filename turns the link into a two-hundred-character word.

### The calculator: one item form, one batch, and one fee per declaration

`renderCalcSearch` → `selectCalcCode` renders the form for a single code; `readCalcForm()` turns that form into an item object, and **`itemDuty(item, customsValueSom)` is the only place a duty is computed.** It takes the customs value as an argument precisely because the same item is costed twice: alone (`runCalc`) from its declared value, and inside a batch from its value *plus* its share of the shipment's transport costs. Add a new rate shape to `parseRateInfo` and it works in both paths at once; compute a duty anywhere else and the batch will silently disagree with the single-item card.

- **Value is converted to сом at the moment the item is read**, not stored in the invoice currency — a batch can mix USD, EUR, CNY, RUB and KZT items, and postponing the conversion makes every later sum wrong in a way that is hard to see. Rates come from `/api/nbkr-rates` (`nbkrRateFor`), which since 09.09.2026 returns all five currencies of НБКР's `daily.xml` in `rates` (the older `usd`/`eur` fields are kept because the auto calculator uses them). The parser divides by `<Nominal>`: it is 1 for all five today, but НБКР has historically published rates per 10 and per 100 units.
- **The customs fee is charged once for the whole batch, never per row.** П.38 of the Instruction to ПКМ КР № 79 от 13.02.2020 (ред. № 444 от 29.06.2026) ties it to the act of placing goods under a customs procedure — a declaration — and the 5–2500 РП floor/ceiling applies there too. Charging it per row would multiply the 500 сом minimum by the number of items.
- Transport costs belong to the customs value, so distributing them raises both duty and VAT. When distribution "by weight" is asked for but no item carries a weight, `computeBatch()` falls back to distribution by value and *says so* on the card rather than dividing equally in silence.
- **The VAT-exemption lists moved to ПКМ КР № 596 от 02.09.2026 on 16.09.2026**, three days before it took effect. Its own п.3 repeals ПКМ № 539 от 29.08.2025 and п.5 of № 811 от 18.12.2025; п.4 gives fifteen days from official publication, and «Эркин-Тоо» printed it on 04.09.2026 — so **19.09.2026**, read off the act rather than off the registry's status label (which still said «Не вступил в силу»). The three annexes are separate registry documents: `43-194` лекарственные средства, `43-195` медицинские изделия, `43-196` исходные материалы. `LS_CODES`/`MED_CODES`/`MAT_CODES` now hold 33 / 65 / 316 keys.

  Four things from that transcription are worth keeping:

  - **Annex 1 is not a rectangular table.** The «№» and «коды» cells are merged vertically wherever one number covers several МНН, so rows come in three shapes — 5 cells (new number, new codes), 4 cells (number inherited), 3 cells (both inherited). 602 data rows under 549 numbers. Parse it as a rectangle and you silently drop the continuations, which is exactly how 27 МНН went missing from the old `LS_CODES` — Галоперидола деканоат and Трастузумаб are 3-cell rows.
  - **The act contradicts its own typography and the length histogram catches it.** Code «3006 60 000 1» is printed that way in two rows and as «3006 60 0001» five rows later. A segmenter built only for 4/4+2/4+2+3/4+2+3+1 emits a phantom `0001` plus a stump `300660`; it needs a branch that accepts a 4-digit group after 4+2 as a merged «3+1». The first regex attempt had a worse bug of its own — it ate the last digit and produced 9-digit codes — and the histogram is what exposed both.
  - **№ 596 has no «Из NNNN» rows at all**, in any of the three annexes (checked against the raw markup, zero matches in the number and code columns). `VATFREE_PARTIAL` is therefore empty, kept rather than deleted so a future redaction can refill it. Annex 3 stays conditional — not by how a code is written but by the perechen's own title, which exempts imports only for use in producing medicines and medical devices.
  - **Fourteen codes of annex 3 are absent from the current ЕТТ** (2914 21 000 0 камфора, 2930 90 990 0 ихтиол and others). They are reduced to the longest live ЕТТ prefix — the same keys the old file already carried — and the act's own spelling now goes into the row's name, so the question does not reopen. Completeness is proved by the act's own numbering: 1..549, 1..31, 1..313 with no gaps and no repeats.
- **A hit in a benefit list is not the same as the benefit applying.** `itemVatFree()` zeroed VAT whenever `findLS`/`findMed`/`findMat` returned anything, and two whole classes of row in the ПКМ КР № 539 annexes do not carry that meaning. Rows the act writes as **«Из NNNN»** name a product *inside* a heading and give no subheading at all; such a row is stored under a bare 4-6-digit key, and two-way prefix matching then lifts it onto every code of the heading — «Из 3926» made all plastic articles VAT-free, «Из 9018» all medical instruments, «Из 3004» all dosed medicaments. And the whole of annex 3 (raw materials) exempts only imports *for use in producing* medicines and medical devices, a purpose no code can confirm — the search card said so while the calculator contradicted it. `vatFreeHits()` now splits hits into unconditional (the act names the code) and conditional (an «Из NNNN» row or annex 3); only the first zeroes the rate, the second charges the tax and says on what condition it comes off. Draw the line where the act does: a short key that is merely the longest live ЕТТ prefix of a code the act *did* name (`30044` for тиопентал натрия, `293391` for мидазолам) stays unconditional.

- **Personal shipments are a different act, and the rate table alone is not enough to read it.** The "📦 Личные отправления" panel implements annex 1 (duty-free norms) and table 1 of annex 2 (единые ставки) of Решение Совета ЕЭК № 107, which the car code had left untouched. Three things generalise. **A norm can be per-member-state and time-phased**: item 2 gives one figure for Armenia and another for everyone else, and the "everyone else" figure changed on 01.04.2024 — take the Kyrgyz, current-dated branch and say in the constant which branch it is. **A missing rate can mean "forbidden", not "free"**: table 1 has no rate for alcohol above 5 л or tobacco above the norm because annex 6 takes such goods out of the personal-use category entirely, so the calculator must say "нельзя", not quote a bigger number — you only learn this by opening annex 6. **A rate in one annex can be unreadable until you find the norm it hangs on**: table 1's item 9 quotes a 5 000 € threshold but never says where it comes from — it is set by п.4 of annex 3, which also confines the whole regime to accompanied/unaccompanied baggage, and until that annex was opened the item read as an uncheckable sentence. Annex 3 carries its own redaction chain, different from annexes 1 and 2. Note too that **a wording difference between neighbouring items of one table is worth confirming with a second PDF extraction**: items 1-4 say «процентов от стоимости в части превышения стоимостной нормы» while item 9 says only «процентов от стоимости», and that difference decides whether the percentage runs on the excess or on the whole value — layout and flat extraction agreed, so it is the act's, not the parser's. And when a general norm and a special exemption both fit, they are two bases rather than a choice: compute both and apply the smaller, saying which one won. And **the fee for a personal shipment is settled by the law, not by the Instruction**: п.38 of the Инструкция to ПКМ КР № 79 speaks of placement under a customs procedure, which a personal shipment never gets, but п.1 ч.1 ст.41 Закона КР № 52 ties the fee to the *release* of goods; ч.3 п.7 of that article waives it for an oral declaration, and п.38²/38³ of the Instruction give the fixed 6 сом/кг for e-commerce goods and 22 РП for a car.

- **The PDF estimate is browser print, not a JS-generated PDF.** Cyrillic in jsPDF/pdfmake needs an embedded font (hundreds of KB of base64) for one button; `printCalcEstimate()` instead fills `#calcPrintArea` and adds `printing-estimate` to `<body>`, which hides the app in the print stylesheet. The class is removed on `afterprint` **and** on a timer — Safari and old Edge do not always fire the event, and without the fallback the page stays with an invisible UI. The estimate table is sized for A4 portrait (fixed column widths, the rate moved into the name cell); check it at 760px width after changing it.

**A tariff quota makes the ЕТТ rate conditional, and `QUOTA_DB` holds two different mechanisms.** The search card showed quota volumes all along while the calculator quoted the rate in silence — for `0207 14 100 1` that is 25%, applicable only to goods imported within an allocated share of the quota. `calcWarnings` now says so, and it has to say two different things, because the ЕТТ itself splits the cases: a **classic EAEU quota** (beef, pork, poultry, whey, rice) gets its own ЕТТ subheading whose name reads «в порядке, указанном в дополнительном примечании … к группе» or «в порядке тарифной квоты», whereas an **agreement quota** (Serbia, Iran, Vietnam) and the 2026 Belarus tariff relief sit on an ordinary subheading and the reduced rate comes from the agreement. The split is clean and is the ЕТТ's own marking, not an inference from the digits: across all 41 `QUOTA_DB` rows, every code of a classic row carries the phrase (6/6, 8/8, 24/24, 100/100 …) and no code of an agreement row does (0/8, 0/23, 0/14 …). One wording for both would be wrong for half of them. Add the row's own note (it carries the decision number) and the Kyrgyz volume, and when that volume is zero or unset across every matching row — Vietnamese rice, the Belarus relief — say outright that the quota cannot be used, or the generic «a reduced rate applies within the quota» misleads.

**Do not derive the out-of-quota code from the digits.** It looks obvious — same nine digits, different last one — and it does not hold: `0201 10 000` has four lines (…1 quota, …2 beef above €8000/t, …3 high-quality, …8 other), and of the 243 quota codes exactly one «other» sibling exists for 113, none for 118 and several for 12. What actually defines the mechanism is the chapter's «дополнительные примечания», so until those are read the card should say that a different subheading applies beyond the quota without naming its code.

**Two mistakes worth not repeating, both from this work.** `/проч(ее|ие|ая|ий)\b/` matches nothing: JS `\b` is defined by `\w`, which is ASCII, so **there is no word boundary between two Cyrillic letters** — the regex silently returned zero hits and the check reported a clean bill. And when replacing a block in this file, anchor **both** ends on exact strings: locating the end by scanning forward for `});` and `}` cut 43 KB out of the file in one go. `git checkout -- tnved_checker.html` restores it; then redo the edit as a single clean insertion and confirm with `git diff --stat` that the deletion count is zero.

### Reading a spec file: .xlsx is parsed in-page, with no library

`onSpecFile` → `readXlsx`/`readCsv` → `specRowsToItems` → preview modal → `specImport`. The xlsx path uses the browser's own `DecompressionStream('deflate-raw')` plus a ~60-line ZIP central-directory reader; adding SheetJS would cost about a megabyte inside a file that is deliberately self-contained. Four traps, all covered by fixtures in the 09.09.2026 session:

- **Take the local header's own filename/extra lengths**, not the central directory's, when computing where an entry's data starts — the extra field usually differs between the two, and using the wrong one lands mid-file.
- **Find the worksheet through `xl/_rels/workbook.xml.rels`**, not by assuming `xl/worksheets/sheet1.xml`: the sheet can be named anything (the test fixture uses `lист.xml`), and archive order does not follow sheet order.
- **Strings come in two shapes** — `t="inlineStr"` (what openpyxl writes) and `t="s"` indexing `sharedStrings.xml` (what Excel writes). Support both, and take the column number from the cell's `r` attribute ("B3" → 1): Excel omits empty cells entirely, so positional reading silently shifts every value.
- **CSV delimiter detection must prefer `;`** — Excel in a Russian locale writes CSV that way, and a comma in such a row is a decimal separator, not a new column.

Column headers are matched by meaning (`SPEC_COLS` regexes), not by position, and the name and rate always come from `ETT_DB` rather than from the file — a broker's spec carries trade names, and the duty has to be computed against the official description. Every row that cannot be used keeps a stated reason in the preview; when a code is absent from the ЕТТ, `specNotFoundHint()` looks it up in `TNVED_MAP` first and otherwise offers the nearest live codes by shared prefix, because "not found" is usually old nomenclature rather than a typo.

**`findX()` returns an array — test `.length`, never truthiness.** `calcWarnings()` had `if(findAntidump(code))`, so the "antidumping measures apply to this code" warning fired for *every* code in the calculator; an empty array is truthy in JS. The same mistake reappeared in the batch requirements list and was caught only because smartphones and t-shirts came back flagged. The batch summary (`BATCH_REQS`) is built from the same `findX()` functions the search cards use, so adding a database there gives a summary line for free — but each entry must state its own predicate explicitly, and distinguish an exact hit from a prefix-only one (hazardous waste matches `2710` for petrol).

### Export control (NKS): the set is a transcription of the act, at the act's own digit length

Since 05.09.2026 the НКС data is derived mechanically from the current official text of the annex to Постановление КМ КР №63 (`cbd.minjust.gov.kg/160067`, edition 38652 = редакция 08.10.2025), not hand-maintained:

- `NKS_MAP` — code → array of indices into `NKS_ITEMS`; `NKS_ITEMS` — `[listIdx, secIdx, "пункт", "наименование"]` (1,539 rows); `NKS_SECS`/`NKS_LISTS` — section and list titles. The card names the act's item number and wording, so the claim is checkable against the act.
- `NKS_UNVER` — 122 codes that were in the old hand-built set but appear in **no** edition of the act (10.02.2023 / 26.12.2024 / 08.10.2025). They are kept (dropping them would silently lose a possible warning) but rendered as a separate "не подтверждено" card. A code that is both unconfirmed *and* only reachable through the legacy fallback is not shown at all — that is two guesses stacked.
- `NKS` = keys of `NKS_MAP` ∪ `NKS_UNVER`, still the set `findNKS` iterates.
- `NKS_ITCAT`/`nksCat()` survive only as a label/icon source; they no longer drive card grouping. Do not treat `NKS_ITCAT` as something that must be kept in sync with `NKS`.

**Store codes exactly as the act writes them — 4, 6, 9 or 10 digits.** The act says «8411 11 000» (9 digits); the earlier set padded that to `8411110000`, a code that does not exist, which is why the position was unreachable. `findNKS`'s two-way prefix match handles short codes correctly; padding does not.

If the act is amended, re-derive rather than patch: fetch the current edition, parse the annex tables (see "Parsing a Word-exported HTML table" below), and regenerate the four constants. Verification that only checks whether a code's *prefix* appears somewhere in the act text is not enough — that is exactly what let 122 unfounded codes survive the 27.08.2026 check.

**Validate a code database against the ЕТТ by prefix, not by exact match — and expect padding.** Running every `TR_EAEU_DB` code against the current ЕТТ on 06.09.2026 found 477 of 7,965 that exist nowhere in it. 441 were headings or subheadings **padded with zeros to ten digits** (`7324` stored as `7324000000`), which is fatal because `findTREAEU` compares prefixes in both directions: `7324210000` does not start with `7324000000` and vice versa, so the row was unreachable by any real code and only a bare four-digit query found it. The other 19 were genuinely abolished subheadings. The two cases are told apart mechanically: strip the code back to its longest prefix that exists in the ЕТТ, and if everything stripped was zeros it was padding, otherwise the position is obsolete and needs the official chapter PDF to decide what survives. This is the same trap already documented for НКС — **store codes exactly as the act writes them, 4, 6, 9 or 10 digits.** Parsing act annexes has three traps of its own. **Word 97 annexes mix encodings inside one file** — part reads as UTF-16 and part only as 8-bit, and in each decoding the other part turns to mojibake, so take the *union* of both decodings and let the ЕТТ-prefix check throw away the noise. **A naive code regex welds adjacent short codes together** — «2520 2811 2835» becomes «252028»; segment the whole run of digit groups into shapes 4, 4+2, 4+2+3, 4+2+3+1, requiring every group to be consumed and every assembled code to be a valid ЕТТ prefix. **A table row with no name is a continuation of the row above, not a section heading** — treating it as a heading silently dropped nine codes from the first rebuild of TR 050. And expect false positives that pass the prefix check anyway: `2003`/`2006` from XML namespace URLs, `1520` from «колеи 1520 мм», `4012` and `8702` from GUIDs, `120110` from food additive E1201 — only the surrounding text tells those apart.

Every database in this file that stores ТН ВЭД codes was run through this check on 06.09.2026: 178 dead codes were found across sixteen of them (68 padded, 110 abolished) and all were fixed. `ETT_DB` itself was the reference for that sweep and so was never checked against the official text; when it finally was, 158 of its codes turned out to exist nowhere in the ЕТТ — but all 158 were already carried in `TNVED_MAP` as `typo`/`gone`, so their cards already say the code is not in the current ЕТТ. Every other database's codes are present in the ЕТТ. Re-run the check after any bulk code import. Two details that cost time: codes are stored **in both single and double quotes** in different databases, so a replacement pass keyed on `"code"` alone silently misses a third of them; and the abolished-heading marker in a chapter PDF is a bare `[8803]` / `[8107]`, which means the longest-existing-prefix rule degenerates (it yields `880`) and those codes need a real correlation instead — `TNVED_MAP` already carried the 8803 → 8807 mappings.

### Legacy nomenclature: `TNVED_MAP` resolves, it does not guess

`ETT_UAE_DB` and `ETT_RS_DB` are transcriptions of the annexes to the EAEU–UAE and EAEU–Serbia agreements, and parts of the НКС act still use codes that HS2022 or later EAEU decisions have removed (2845 90 900 0 → 2845 90 800 0; HS2022 split 8701 20 into 8701 21…8701 29; heading 8803 was abolished in favour of 8807). Because every `findX()` matches on a digit prefix, such entries are unreachable from a current code.

Runtime detection stays as it was: `legacyPrefix()` returns the deepest prefix of a 10-digit code that still exists in `ETT_DB` (8→6→4), and `legacyMapFor()` caches one such map per database, keyed by the code as that database spells it. Keep the fallback iterating the small legacy map, never the whole database — the first draft scanned all 7,917 UAE rows on every keystroke and made search five times slower.

**Since 17.09.2026 the preference lists and the tax-exemption lists resolve through `TNVED_MAP` too.** `lkListRow` (Iran, Vietnam, UAE, Mongolia) and the three tax finders `findArt297Perechen`/`findArt298`/`findArt297P20` (through `actCodeNote`) match a list row whose code is absent from the ЕТТ by that code's successors, and the tax cards append «в перечне — код X, в действующем ЕТТ — Y» to the name. Without it the EEC's consolidated Iran list, which prints two rows of the 8807 90 block under the abolished 8803, made the справка promise 0% «вне перечня» where the list says «ставка ЕТТ». When you add a successor mapping for a benefit, take only the successors the act's own context supports — 8512 90 900 9 in an annex of components for industrial assembly maps to 8512 90 900 2 alone, not to «прочие» 900 8.

What changed on 05.09.2026 is what happens after detection. `TNVED_MAP` (225 entries since 17.09.2026) maps each code that is not in the current ТН ВЭД to its current counterpart(s), and `legacyNote(code, at, tail)` renders one consistent block for every card. Each entry carries `t` (current codes), `b` (basis), `n` (explanation), `s` (source) and `d` (date checked). Bases split into two families: codes written that way by an act (`split`/`merge`/`renumber`/`hs`/`new`) and codes that only ever existed in this file's own `ETT_DB` (`typo` — the same position is in the ЕТТ under a different code; `gone` — no counterpart, nearest current subheadings listed). The second family is 158 of the 218: the ЕТТ card must not present a duty rate for a code the official ЕТТ does not contain, so it says so outright.

**Prefer answering over warning.** `findETTRS` shows the pattern: when a query matches nothing directly but `TNVED_MAP[qn]` knows the replacement, it returns the *current* rows with `rr.mappedFrom = qn` set, and the card says "запрошенный код X заменён на Y" instead of a "verify applicability" warning. Reuse that shape in any other act-transcribed database rather than falling back to the prefix warning, which should stay the last resort. **ЕЭК publishes no consolidated correlation table between ТН ВЭД editions** — verified 05.09.2026 across the ЕТТ section, the site search and docs.eaeunion.org; only commercial aggregators publish one, and those are not a primary source. So entries are derived from the official per-chapter ЕТТ publications (their publication date goes into `s`) plus, for HS-level changes, the WCO HS2017→HS2022 correlation tables. The card states the basis and still tells the user to check applicability against the position's wording.

**An FTA annex is not frozen.** The EAEU–Serbia exclusion list looked like a 2019 treaty annex stuck in old nomenclature — but Решение Коллегии ЕЭК № 81 от 23.09.2025 transposed it onto the current nomenclature, and the file's copy was one redaction behind (906 rows against 957). Before mapping such a list's codes by hand, look for the ЕЭК's own consolidated publication: for Serbia it is `eec.eaeunion.org/comission/department/catr/ttr/serbia-pref.php` → "Перечень Сербия на <дата>.pdf", whose header names every amending decision. When one exists, it *is* the correlation — and it independently confirmed the mappings derived structurally here (`8704 21 390 3 → 8704 21 380 1` and the whole 8701 20 → 8701 21…29 fan-out).

Four traps this uncovered, worth remembering:

- **A missing code in `ETT_DB` produces a false "obsolete" flag.** 47 of the 219 codes flagged by the 05.09.2026 review were perfectly current; the app just did not have them. Before believing that an act's code is obsolete, check it against the official ЕТТ chapter PDF, not against `ETT_DB`.
- **Absence from the published ЕТТ can also mean "newer".** `5804 21 900 1`/`…900 9` were introduced by Решение Коллегии ЕЭК №94 от 14.07.2026, while the ЕЭК's published chapter 58 (08.03.2026) still shows only `5804 21 900 0`. That is what basis `new` is for; flagging such a code as obsolete is a straight error.
- **Warn on the code, not on how it matched.** A card must show the obsolescence note whenever a matched code is in `TNVED_MAP`, including when the user typed that obsolete code and it matched directly. Keying the warning off the legacy-fallback flag alone silently hides it in exactly the case where the user is looking at the obsolete code.
- **Check the in-force date, not just the act.** The EAEU–UAE rate schedule (Решение Коллегии ЕЭК № 113 от 25.08.2026) is correct down to every one of 7,922 rows and eight yearly rates — and does not apply yet: the document card on docs.eaeunion.org gives "Дата вступления в силу 06.10.2026", and the act's own п.4 ties it to the Agreement's entry into force. A perfectly transcribed schedule presented as current is still a wrong answer.

Direction of risk still differs per database: over-matching is safe for export control (`NKS`) and for the Serbia exclusion list, where a miss wrongly implies "no restriction"; it is *not* safe for the UAE rate schedule, where a spurious match implies a preference the declarant may not be entitled to, so that card's wording is deliberately harsher.

### ЕСТП: the preference is a property of the origin, not of the code

`PREF_GOODS`/`PREF_DEV_C`/`PREF_LDC_C`/`findPref` implement the Union's own preference scheme (единая система тарифных преференций) — 75% of the ЕТТ rate for goods originating in a developing user country, 0% for a least developed one. It is not one of the free-trade agreements: it is unilateral, and its four acts are published as consolidated PDFs on the ЕЭК **Департамент торговой политики** page, `eec.eaeunion.org/comission/department/dotp/tariff_preferences.php`. Take them from there rather than from the legal portal. Two traps in the sources themselves:

- **The rates are in the Treaty, not in Решение КТС №130.** Пункты 1 and 4 of that decision are «утратил силу»; only п.3 survives, and it merely points at the lists. The operative rates are п.2 and п.3 ст.36 Договора о ЕАЭС. The Russian Treaty text on docs.eaeunion.org is an 88 MB / 322 MB scan and the smaller files there are the Kazakh, Armenian and English versions — the readable Russian text is ЕЭК's own `eec.eaeunion.org/upload/medialibrary/222/…/Dogovor.pdf`.
- **The site search returns a superseded redaction of the rules of origin.** `Pravila-dlya-RS-i-NRS_itog_Reshenie-33.pdf` is ред. №33 от 17.03.2022; the current one (№49 от 14.05.2024) is the file the department page links. Take the file the page links, not the file the search ranks first.

**An exclusion is asymmetric, and conflating the two directions breaks the answer.** The list is written as «02 (кроме 0203, 0207)», so a query can either lie *inside* an exclusion (0203 11 … — the preference is off) or *contain* one (a query of «07» contains eight exclusions — the preference is on for the rest of the chapter, and the card must list what is carved out and ask for a full code). `findPref` returns both sets separately (`ex` and `exPart`); collapsing them either kills a whole chapter or silently hides a real exclusion. Note too that one code routinely gets opposite answers from the two sections — the whole of chapter 02 is in the least-developed list while pork is excluded from the developing one — so the card answers per section rather than once.

**A preference scales the duty, not the base, so it belongs in one line of `itemDuty`.** 0.75 of the rate is exactly 0.75 of the duty for every rate shape the file has, including the combined ones, because max(0.75a, 0.75s) = 0.75·max(a, s). The old body moved to `itemDutyETT` and `itemDuty` wraps it; single item, batch and the VAT base all followed for free. It must *not* apply to `it.auto` — the personal-car единая ставка of Решение Совета ЕЭК №107 replaces duty and taxes and is not an ЕТТ rate at all.

### Citations: `DOC_SOURCES` + `docLink()`

`DOC_SOURCES` is a registry of verified `{key: url}` pairs to primary sources (docs.eaeunion.org for EAEU Board/Council decisions, cbd.minjust.gov.kg for Kyrgyz government acts). `docLink(label, url)` renders a real `<a>` when `url` is truthy, otherwise falls back to plain escaped text — **never invent a URL to fill this in**; if a primary source can't be confirmed, leave the citation as plain text (this convention is explicit and intentional, see `session.md`). `NPA_REGISTRY_URL` is the generic fallback link to the Kyrgyz Кабмин NPA registry, used when a specific act can't be pinned down.

Not every citation goes through `docLink()`, though — several DB entries carry their act reference inline inside a `name`/`note` field that `render()` only ever passes through `esc()` (e.g. `NTM_DB` notes, `SAN_REG_DB` exclusion names). Restructuring `render()` just to wire one more field through `docLink()` is usually not worth it. In that case, once a URL is verified, just paste it as plain readable text directly into the `name`/`note` string itself — it renders as inert but legible text, which is consistent with the project's existing precedent and cheaper than plumbing a new field through the render pipeline.

### Conflicting matches within one `findX()` — most-specific-code-wins

Several `findX()` functions match by prefix (`cn.startsWith(qn)||qn.startsWith(cn)`), which lets a query simultaneously hit both a broad, generic-level entry (e.g. a whole heading `2915`) and a narrow, more specific one nested inside it (e.g. an exclusion for exact code `2915120000`) that's meant to override it. Left unhandled, `render()` shows both cards at once with contradictory messages (e.g. "registration required" next to "registration not required" for the same code). `findSAN()` (near `SAN_REG_DB`) solves this by computing, per candidate match, the length of its longest code that is actually a prefix of the query (i.e. genuinely applicable to this specific query, not just "contains a longer code somewhere"), then keeping only the matches tied for the maximum such length — so a more specific hit suppresses a more generic one, but a bare/short query (shorter than any candidate code) isn't wrongly reduced to nothing. If you add a new DB where a specific entry is meant to carve an exception out of a broader one, replicate this pattern in that `findX()` rather than trying to patch it in `render()`.

### Editing the large data literals

Several DB constants are single lines hundreds of KB long (the whole `NKS_ITCAT` object or `NKS` array can be one line). The `Edit` tool is unreliable at that size — prior sessions insert/remove entries with a small Python/Node script that does a targeted, anchor-based string replacement on the raw file text (confirm `content.count(anchor) == 1` before replacing, to avoid silently touching the wrong occurrence), then re-run the syntax check and a runtime smoke test. Bulk table data pulled from a fetched legal text is parsed out separately (regex over the stripped-HTML text, watching for CAS-number/ISO-number/range-reference collisions eating adjacent real codes) before being spliced in the same way.

**Relabeling many existing entries in an object literal** (e.g. correcting hundreds of `NKS_ITCAT` codes that were categorized under an old/generic label and should say something more specific): don't do hundreds of scattered surgical replacements across a 12 MB file of single-line literals. Instead, just append new `"code":[...]` entries with the *same keys* to the end of the object literal, right before its closing `};` — a JS object literal lets a later duplicate key silently override an earlier one, so the new label wins at lookup time while the old entry stays physically in the file, inert. Much safer than editing hundreds of scattered locations, at the cost of some dead weight in the file.

**Parsing a Word-exported HTML table** (the `contentRu`/`contentKg` blobs from cbd.minjust.gov.kg, or any `.docx`→HTML dump): these tables routinely omit closing `</tr>`/`</td>` tags, relying on the next opening tag to implicitly close the previous one — feeding this to `html.parser.HTMLParser` naively produces empty cells, because nothing ever calls `handle_endtag`. Write the parser to close the current cell/row explicitly inside `handle_starttag` whenever a new `<td>`/`<tr>` opens (in addition to on the real end tag), not just in `handle_endtag`. Also watch for tables nested inside a note/example cell (e.g. a materials-compatibility reference table embedded in a "Примечание") — they show up as extra `<table>` elements in sequence; since they generally lack a code column, they're harmless to include in the row stream as long as downstream row-classification filters on the expected item-number pattern (e.g. `^\d+(\.\d+)+\.?$`), which such nested tables' first cells won't match.
