# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is **not** a conventional software project — it's a working folder for building and maintaining a single deliverable:

- **`tnved_checker.html`** — a self-contained, single-file web app ("Проверка ТН ВЭД — КР 2025/2026") for checking Kyrgyz Republic / EAEU customs (ТН ВЭД) codes against import/export bans, licensing, certification, veterinary/phytosanitary/sanitary control, technical regulations, export control (dual-use/NKS), duty rates, and more. No build step, no package manager, no framework — pure HTML + inline `<style>` + one inline `<script>`, ~8 MB, almost entirely legal/customs reference data hard-coded as JS constants.
- **`server/`** — a small Node/Express + PostgreSQL backend added in the "accounts/admin" phase, providing real (server-verified) login and an admin panel for creating/editing/disabling user accounts. See "Backend (`server/`)" below.
- The rest of the repo is **source material**: official legal texts (`.md` files — tax code, Единый перечень, government resolutions, etc.) that get manually parsed and encoded into the app, and **`session.md`**, a running Russian-language changelog of what was done, why, and what's still unverified. `session.md` remains the narrative record of past work — why something was done and what is still unverified — so append to it when you make a substantive change. Since the review of 05.09.2026 the repo also has **real git history** (it previously had none): commit `eade5b8` preserves the working set as it had been staged, including 15 legal source `.md` files that by then existed only in the git index and not on disk. Those files are recoverable with `git checkout eade5b8 -- <path>` if they are ever needed again. There is still no remote, so history is local-only and is a rollback path, not a backup.

**`.gitattributes` sets `* -text` and must stay that way.** `tnved_checker.html` is ~11 MB with *mixed* line endings (some large one-line data literals contain CRLF inside them), and every edit to it is an anchored exact-string replacement. Git's `core.autocrlf` would rewrite those bytes on checkout, breaking anchors and producing a whole-file phantom diff. This was caught during the review: the first attempt at committing the file silently stripped 7,466 CR bytes.

Beyond `server/`, there is no other service and no CI. "Running" `tnved_checker.html` alone by double-clicking it (`file://`) no longer works end-to-end: the file now gates its UI behind a login screen that calls `/api/auth/*`, so it needs to be served over http(s) from the same origin as the backend (Nginx serving the static file + proxying `/api/*` to `server/` in production; `server/`'s own `express.static` fallback for local dev — see below). The underlying legal-data constants are still fully embedded in the page source either way (nothing moved server-side in this phase), so the login gate controls who can *use* the tool, not who can view its bundled reference data via "view source."

## Commands

There is no build/lint/test tooling. The workflows that stand in for them, established over prior sessions:

**Syntax-check the inline script** (the file is too large for editors/tools to just "open and check"; do this after every edit):
```bash
python3 -c "
import re
content = open('tnved_checker.html', encoding='utf-8').read()
m = re.search(r'<script>(.*)</script>', content, re.S)
open('/tmp/inline_script.js', 'w', encoding='utf-8').write(m.group(1))
"
node --check /tmp/inline_script.js
```
Note: `python3` here resolves to the Windows Store alias, which does **not** see git-bash POSIX paths like `/tmp/...` — write scratch files to a Windows-style path (or the session scratchpad dir) instead, and read them back with the `Read` tool, not by printing to the bash console (the console mangles Cyrillic output; files round-trip correctly).

**Runtime smoke-test** a function or DB after editing it: extract the inline script as above, then run it inside a Node `vm` context with minimal DOM stubs (`document.getElementById`, `classList`, `innerHTML`/`value`/`textContent` getters/setters, etc. — the top-level script calls a few `render*Panel` functions immediately on load, so it throws without stubs). Expose the globals you need via `this.__x = x;` appended to the script source before `runInContext`, since top-level `const`/`let` in a vm context aren't reliably visible as properties of the sandbox object otherwise. This is how new/changed lookup functions and DB entries get verified end-to-end without a browser.

**Browser check** (for UI/rendering changes): no browser is preinstalled for automation. Prior sessions installed `playwright-core` into a temp folder and drove the system Microsoft Edge via `channel:'msedge'` (no browser download needed). Since `tnved_checker.html` now requires a backend to get past its login screen, point this at a running instance of `server/` (local or the real VPS deploy) rather than a bare `file://` path — opening the file directly still renders the login screen (confirms the UI didn't break), but every `fetch('/api/...')` call fails immediately with a CORS/network error under `file://`, so nothing past the login screen is reachable that way.

## Backend (`server/`)

A small Express + PostgreSQL app providing session-based login and an admin API (`/api/auth/*`, `/api/admin/*`) for `tnved_checker.html`. See the plan at the time it was added for the full design rationale (RLS-equivalent access model, why sessions instead of JWT, CSRF approach, etc.) — this section just covers day-to-day commands.

**Local dev:**
```bash
cd server
npm install
cp .env.example .env   # fill in DATABASE_URL (a local Postgres) and SESSION_SECRET
psql "$DATABASE_URL" -f migrations/0001_init.sql
npm run create-admin -- you@example.com "some-password"   # one-off first admin
npm run dev
```
`server/src/index.js` also serves `tnved_checker.html` itself (via `express.static`, pointed at the repo root) so `http://localhost:3000/` works standalone for local testing without Nginx in front.

**Deploy (VPS):** install Node LTS + PostgreSQL, create the DB/role and apply `migrations/0001_init.sql`, deploy `server/` and run `npm ci --omit=dev`, run `create-first-admin.js` once, run the app under a systemd unit (`ExecStart=node server/src/index.js`, `EnvironmentFile=` pointing at a production `.env`), and put Nginx in front: serve `tnved_checker.html` as static content at `/`, reverse-proxy `location /api/ { proxy_pass http://127.0.0.1:3000; }`, and terminate TLS there (Let's Encrypt via `certbot --nginx`, which needs a real domain pointed at the VPS — a bare IP can't get a cert).

**Deploying a change to `tnved_checker.html` alone** (no `server/` change): back up the current file on the VPS, `scp` the new one to `tnved_checker.html.new`, compare its md5 with the local file, run `node --check` on the extracted `<script>` **on the server** (not only locally — that is what catches a corrupted transfer), then `mv` it into place and `chown tnved:tnved`. Nginx serves this file as static content, so **no `systemctl restart tnved`** — the restart is only for `server/`. Verify by `curl`ing the site and checking that the served bytes have the same md5 and contain the new text. Editing the file without this step does not count as finished work: a fix once sat in the repo for a session while the user was looking at the old page.

**Schema/migrations:** there's no migration framework — `migrations/*.sql` files are applied by hand with `psql -f`, in order, once each. Add new migrations as new numbered files rather than editing an already-applied one.

## Mobile wrapper (`mobile/`)

A thin Capacitor shell (`kg.tnved.checker`) for Android and iOS. It ships no copy of the app: `capacitor.config.json` sets `server.url` to the production origin, so the WebView simply loads the deployed site and every `/api/*` call is same-origin. Two consequences worth remembering:

- Tightening anything origin-related on the backend is safe for the app, because the WebView's `Origin` is exactly `APP_ORIGIN`. That is what made the CSRF check in `server/src/index.js` safe to make fail-closed.
- Changing `server.url` means rebuilding and re-releasing the app, so the production origin is effectively pinned by the store listings.

`privacy.html` at the repo root is deliberately *not* linked from the app (which shows its policy in a modal). It exists as a standalone, publicly reachable URL because app-store review requires one that works without logging in.

Builds run in Codemagic (`mobile/codemagic.yaml`); `mobile/android/local.properties` and both `node_modules` are gitignored.

## Architecture

### One file, one pattern, repeated ~37 times

Nearly the entire script is variations on: **one `SCREAMING_SNAKE_CASE` const holding a legal database, one `findX(query)` function that looks a code up in it, one block in the central `render()` that turns a hit into a result card.** Examples: `BAN_DB`/`findBan`, `VET_DB`/`findVET`, `PHYTO_DB`/`findPHYTO`, `TR_EAEU_DB`/`findTREAEU`, `ETT_DB`/`findETT`, `SPECIES_DB`/`findSpecies`, `NTM_DB`/`findEEC30`, `SAN_SECTIONS`/`SAN_REG_DB`/`SAN_SUB_DB`/`SAN_SECTION3`/`findSAN`, etc. When adding a new legal source, follow this same triplet rather than inventing a new shape.

**Before adding an act's section to one database, check whether another already covers it.** The file has ~40 `findX` functions, so "the base doesn't have this" is only meaningful after checking all of them. Section 1.2 of Решение №30 was added to `NTM_DB` in this session and turned out to be already served by `EEC_WASTE`/`findEECWaste`, so code 4013 10 000 0 showed two cards for the same ban until the duplicate was removed.

`render(q)` (search for `function render(q)`) is the dispatcher for the default "search by code" mode: it calls essentially every `findX(qt)` in one shot, and if every result is empty shows a "not found" card; otherwise it concatenates one `<div class="card c-...">` block per non-empty result type, in a fixed order. If nothing matches by code, `render()` itself falls back to a name-based match (`findByName`/`nameMatchesHtml`) rather than that being a separate mode. The two other search modes still wired up by `setSearchMode()` and dispatched from the single debounced `#inp` input listener are `renderSpecies` and `renderCalcSearch`; a former VIN-lookup mode (`renderVIN`/`findVIN`) and a manual "Авто" text-search mode (`renderAuto`/`findAuto`) were both removed as dead code (see session.md, 28.08.2026 and 30.08.2026 entries) — don't resurrect those names expecting them to still exist.

### Export control (NKS): the set is a transcription of the act, at the act's own digit length

Since 05.09.2026 the НКС data is derived mechanically from the current official text of the annex to Постановление КМ КР №63 (`cbd.minjust.gov.kg/160067`, edition 38652 = редакция 08.10.2025), not hand-maintained:

- `NKS_MAP` — code → array of indices into `NKS_ITEMS`; `NKS_ITEMS` — `[listIdx, secIdx, "пункт", "наименование"]` (1,539 rows); `NKS_SECS`/`NKS_LISTS` — section and list titles. The card names the act's item number and wording, so the claim is checkable against the act.
- `NKS_UNVER` — 122 codes that were in the old hand-built set but appear in **no** edition of the act (10.02.2023 / 26.12.2024 / 08.10.2025). They are kept (dropping them would silently lose a possible warning) but rendered as a separate "не подтверждено" card. A code that is both unconfirmed *and* only reachable through the legacy fallback is not shown at all — that is two guesses stacked.
- `NKS` = keys of `NKS_MAP` ∪ `NKS_UNVER`, still the set `findNKS` iterates.
- `NKS_ITCAT`/`nksCat()` survive only as a label/icon source; they no longer drive card grouping. Do not treat `NKS_ITCAT` as something that must be kept in sync with `NKS`.

**Store codes exactly as the act writes them — 4, 6, 9 or 10 digits.** The act says «8411 11 000» (9 digits); the earlier set padded that to `8411110000`, a code that does not exist, which is why the position was unreachable. `findNKS`'s two-way prefix match handles short codes correctly; padding does not.

If the act is amended, re-derive rather than patch: fetch the current edition, parse the annex tables (see "Parsing a Word-exported HTML table" below), and regenerate the four constants. Verification that only checks whether a code's *prefix* appears somewhere in the act text is not enough — that is exactly what let 122 unfounded codes survive the 27.08.2026 check.

**Validate a code database against the ЕТТ by prefix, not by exact match — and expect padding.** Running every `TR_EAEU_DB` code against the current ЕТТ on 06.09.2026 found 477 of 7,965 that exist nowhere in it. 441 were headings or subheadings **padded with zeros to ten digits** (`7324` stored as `7324000000`), which is fatal because `findTREAEU` compares prefixes in both directions: `7324210000` does not start with `7324000000` and vice versa, so the row was unreachable by any real code and only a bare four-digit query found it. The other 19 were genuinely abolished subheadings. The two cases are told apart mechanically: strip the code back to its longest prefix that exists in the ЕТТ, and if everything stripped was zeros it was padding, otherwise the position is obsolete and needs the official chapter PDF to decide what survives. This is the same trap already documented for НКС — **store codes exactly as the act writes them, 4, 6, 9 or 10 digits.** Parsing act annexes has three traps of its own. **Word 97 annexes mix encodings inside one file** — part reads as UTF-16 and part only as 8-bit, and in each decoding the other part turns to mojibake, so take the *union* of both decodings and let the ЕТТ-prefix check throw away the noise. **A naive code regex welds adjacent short codes together** — «2520 2811 2835» becomes «252028»; segment the whole run of digit groups into shapes 4, 4+2, 4+2+3, 4+2+3+1, requiring every group to be consumed and every assembled code to be a valid ЕТТ prefix. **A table row with no name is a continuation of the row above, not a section heading** — treating it as a heading silently dropped nine codes from the first rebuild of TR 050. And expect false positives that pass the prefix check anyway: `2003`/`2006` from XML namespace URLs, `1520` from «колеи 1520 мм», `4012` and `8702` from GUIDs, `120110` from food additive E1201 — only the surrounding text tells those apart.

Every database in this file that stores ТН ВЭД codes was run through this check on 06.09.2026: 178 dead codes were found across sixteen of them (68 padded, 110 abolished) and all were fixed. `ETT_DB` itself was the reference for that sweep and so was never checked against the official text; when it finally was, 158 of its codes turned out to exist nowhere in the ЕТТ — but all 158 were already carried in `TNVED_MAP` as `typo`/`gone`, so their cards already say the code is not in the current ЕТТ. Every other database's codes are present in the ЕТТ. Re-run the check after any bulk code import. Two details that cost time: codes are stored **in both single and double quotes** in different databases, so a replacement pass keyed on `"code"` alone silently misses a third of them; and the abolished-heading marker in a chapter PDF is a bare `[8803]` / `[8107]`, which means the longest-existing-prefix rule degenerates (it yields `880`) and those codes need a real correlation instead — `TNVED_MAP` already carried the 8803 → 8807 mappings.

### Legacy nomenclature: `TNVED_MAP` resolves, it does not guess

`ETT_UAE_DB` and `ETT_RS_DB` are transcriptions of the annexes to the EAEU–UAE and EAEU–Serbia agreements, and parts of the НКС act still use codes that HS2022 or later EAEU decisions have removed (2845 90 900 0 → 2845 90 800 0; HS2022 split 8701 20 into 8701 21…8701 29; heading 8803 was abolished in favour of 8807). Because every `findX()` matches on a digit prefix, such entries are unreachable from a current code.

Runtime detection stays as it was: `legacyPrefix()` returns the deepest prefix of a 10-digit code that still exists in `ETT_DB` (8→6→4), and `legacyMapFor()` caches one such map per database, keyed by the code as that database spells it. Keep the fallback iterating the small legacy map, never the whole database — the first draft scanned all 7,917 UAE rows on every keystroke and made search five times slower.

What changed on 05.09.2026 is what happens after detection. `TNVED_MAP` (218 entries) maps each code that is not in the current ТН ВЭД to its current counterpart(s), and `legacyNote(code, at, tail)` renders one consistent block for every card. Each entry carries `t` (current codes), `b` (basis), `n` (explanation), `s` (source) and `d` (date checked). Bases split into two families: codes written that way by an act (`split`/`merge`/`renumber`/`hs`/`new`) and codes that only ever existed in this file's own `ETT_DB` (`typo` — the same position is in the ЕТТ under a different code; `gone` — no counterpart, nearest current subheadings listed). The second family is 158 of the 218: the ЕТТ card must not present a duty rate for a code the official ЕТТ does not contain, so it says so outright.

**Prefer answering over warning.** `findETTRS` shows the pattern: when a query matches nothing directly but `TNVED_MAP[qn]` knows the replacement, it returns the *current* rows with `rr.mappedFrom = qn` set, and the card says "запрошенный код X заменён на Y" instead of a "verify applicability" warning. Reuse that shape in any other act-transcribed database rather than falling back to the prefix warning, which should stay the last resort. **ЕЭК publishes no consolidated correlation table between ТН ВЭД editions** — verified 05.09.2026 across the ЕТТ section, the site search and docs.eaeunion.org; only commercial aggregators publish one, and those are not a primary source. So entries are derived from the official per-chapter ЕТТ publications (their publication date goes into `s`) plus, for HS-level changes, the WCO HS2017→HS2022 correlation tables. The card states the basis and still tells the user to check applicability against the position's wording.

**An FTA annex is not frozen.** The EAEU–Serbia exclusion list looked like a 2019 treaty annex stuck in old nomenclature — but Решение Коллегии ЕЭК № 81 от 23.09.2025 transposed it onto the current nomenclature, and the file's copy was one redaction behind (906 rows against 957). Before mapping such a list's codes by hand, look for the ЕЭК's own consolidated publication: for Serbia it is `eec.eaeunion.org/comission/department/catr/ttr/serbia-pref.php` → "Перечень Сербия на <дата>.pdf", whose header names every amending decision. When one exists, it *is* the correlation — and it independently confirmed the mappings derived structurally here (`8704 21 390 3 → 8704 21 380 1` and the whole 8701 20 → 8701 21…29 fan-out).

Four traps this uncovered, worth remembering:

- **A missing code in `ETT_DB` produces a false "obsolete" flag.** 47 of the 219 codes flagged by the 05.09.2026 review were perfectly current; the app just did not have them. Before believing that an act's code is obsolete, check it against the official ЕТТ chapter PDF, not against `ETT_DB`.
- **Absence from the published ЕТТ can also mean "newer".** `5804 21 900 1`/`…900 9` were introduced by Решение Коллегии ЕЭК №94 от 14.07.2026, while the ЕЭК's published chapter 58 (08.03.2026) still shows only `5804 21 900 0`. That is what basis `new` is for; flagging such a code as obsolete is a straight error.
- **Warn on the code, not on how it matched.** A card must show the obsolescence note whenever a matched code is in `TNVED_MAP`, including when the user typed that obsolete code and it matched directly. Keying the warning off the legacy-fallback flag alone silently hides it in exactly the case where the user is looking at the obsolete code.
- **Check the in-force date, not just the act.** The EAEU–UAE rate schedule (Решение Коллегии ЕЭК № 113 от 25.08.2026) is correct down to every one of 7,922 rows and eight yearly rates — and does not apply yet: the document card on docs.eaeunion.org gives "Дата вступления в силу 06.10.2026", and the act's own п.4 ties it to the Agreement's entry into force. A perfectly transcribed schedule presented as current is still a wrong answer.

Direction of risk still differs per database: over-matching is safe for export control (`NKS`) and for the Serbia exclusion list, where a miss wrongly implies "no restriction"; it is *not* safe for the UAE rate schedule, where a spurious match implies a preference the declarant may not be entitled to, so that card's wording is deliberately harsher.

### `SOURCE_AUDIT`: every card says when its source was last checked

`SOURCE_AUDIT` (next to `DOC_SOURCES`) holds one record per card family: name, act, url, date, status and the scope of the check. `auditNote(key)` renders the line inside a card; `renderSourceAudit()` fills the left sidebar panel `#srcAudit` (✔ checked in full / ◐ checked in part / ○ not checked in this revision). **Never write a date into a record whose check you did not actually perform.** Equally, do not write "дата не зафиксирована" without looking: the first version of this registry said that about the veterinary, phytosanitary and sanitary lists while the dates sat in comments next to those very databases — grep the file for a `//` comment containing a date and a form of «сверен/проверен» before declaring a check undated.

As of 06.09.2026 the registry has twenty-two records — sixteen ✔, five ◐ and one ○ — and the sidebar panel lists them all.

**✔ checked in full (16):** `ett`, `nks`, `uae`, `rs`, `vn`, `ir`, `mn`, `vet`, `phyto`, `san`, `sert`, `eec30`, `waste`, `quota`, `antidump`, `nalog`. Every ЕТТ code, rate and (where the act gives one) name is verified; for the 3,902 codes whose official description is just «прочие», the file's paraphrase was checked against the official *context* instead — the parent chain has to match, which is exactly where a copied neighbouring name shows up.

**◐ checked in part (5),** each saying why on its own card (`eecdec` and `trigger` are described under "No record at all" below, since they were added in this revision):
- `tr` — the composition of the set is now complete: 44 entries, and the five technical regulations still absent (012, 014, 021, 022, 049) publish no ТН ВЭД code list at all, so they cannot be searched by code. The contents were verified on 06.09.2026 too: the annexes of all 38 cited acts were downloaded from the legal portal and diffed against the file. Thirty-one matched exactly; five were wrong — 050 was rebuilt whole (26 positions to 57), 043 was missing positions 81-104 entirely (fire hoses, hydrants, fire doors, smoke dampers, ducts) despite an in-file comment claiming the 80-position list was "probably complete", 003 carried three wood codes where the act has 102, 004 lacked the whole hand-power-tool section, and 016 lacked position 15. **A citation that opens is not a citation that is right:** three entries pointed at unrelated documents (015 at a resolution about verifying declarations, 030 at a draft-decision approval, 044 at the technical regulation instead of its list), and six carried no URL at all with a comment saying the act "is not indexed on the portal" — all eight were found by paging the portal's year sections. Check the card's title, not just that the link resolves. **Do not trust the ЕЭК per-regulation page as an index of what exists:** it omits the перечень for ТР ЕАЭС 045/2017 (Решение Коллегии ЕЭК от 18.06.2019 № 101) entirely, and it dates Решение № 235 for ТР ТС 007/2011 to 2020 while the portal card says 24.12.2019. The only reliable way to establish that a перечень does *not* exist is to sweep the portal's «Коллегия ЕЭК — Решения» year sections.
- `species` — every appendix number is now verified: section 2.7 parses cleanly once you stop splitting rows on runs of 2+ spaces (layout extraction inserts those *inside* long Latin names) and instead take the appendix as **the cell that is exactly I, II or III immediately before the first cell containing Cyrillic**. Column bounds from the page header do not work either — the columns drift within a page. Two further traps: the act's own Latin names contain Cyrillic homoglyphs (`Lophophоrus`, `Geoсlemys`, `Сorallium`), so normalise them before comparing; and a species can have *two* rows in the act — Appendix I for the species "except the population of X" and Appendix II for that population — so check for a second row before "correcting" an appendix number. A third trap is structural: the CITES part of `SPECIES_DB` held **two generations of rows** — an older one whose Latin carries a bracketed synonym (`Acrocephalus (=Bebrornis) rodericanus`) and a newer one transcribed from the act — and 81 taxa had both, so the card showed the species twice. They were merged on 06.09.2026 (85 rows removed, 4,488 → 4,403), keeping the act's spelling and folding the synonym and the differing Russian name into the surviving row. **Before correcting a name, check whether a row with the correct spelling already exists** — eleven exact duplicates were created in this very session by renaming misspelled rows that already had a correct twin; the right move was to delete the misspelled one. What keeps the record at "in part" is ~180 rows the act does not carry under their own Latin name — species the file expands by name while the act lists them at order or family level (FALCONIFORMES spp., STRIGIFORMES spp., PRIMATES spp., CETACEA spp., Gruidae spp., Otididae spp.), which is not an error and is not tied row-by-row to its parent entry. The seventeen Appendix III listings withdrawn by Costa Rica, Malaysia and Honduras *are* marked: those rows carry a fifth element that `renderSpecies` prints as a warning line.
- `ban` — the twelve cited Kyrgyz acts all resolve correctly and are current, and the «льготный ввоз» rows were traced to пункт 7 of Решение КТС № 130 on 05.09.2026: nine subparagraphs currently apply to Kyrgyzstan and all nine are in the file. What keeps this record at "in part" is six rows whose basis was **not** found in any act — five fresh-fruit exemptions announced only by a Kyrgyz ministry press release, and the helium export restriction — all six carry `unver:true` and say so on their card.

**No record at all (4 databases):** `USIR_DB` (1,915 rows), `AUTO_DB` (1,798), `KEF1606_MAP` (143), `PERMIT_ORGS` (24). These are national or calculator data with no EAEU primary source to parse, so the "fetch the official PDF and diff" method does not apply to them; they need a different approach, and until then they carry no verification date. `PERMIT_ORGS` was chased on 06.09.2026 and could *not* be closed, which is itself the finding: ЕЭК publishes no register of member-state authorised bodies (the non-tariff department's «Реестры» page holds only the cryptography and radio-electronics registers), and on the Kyrgyz side the nearest act — ПКМ КР от 24.03.2016 № 142 on licensors (`7-19265`) — is marked repealed with no repealing act named, while no successor could be found in the registry. It now carries a `permit` audit record with status ○ saying exactly that. Two search traps found along the way: `GetDocuments` returns its hits in **`data`**, not `documents`, and it ranks codes and laws above government resolutions, so a query about export licensing returns the Air Code and the Tax Code while the resolution you want never appears — reaching an act through the `documentReferences` of a neighbouring document is often faster than refining the phrase.

`EEC_DECISIONS` and `TRIGGER_DB` got records on 06.09.2026 — both are verifiable after all, because every row cites a decision whose card is on docs.eaeunion.org. All citations were checked (number + adoption date), and completeness was established by sweeping the portal's year sections for titles beginning «О классификации…»: all 207 of 2013-2026 were present, and of the 21 Комиссия Таможенного союза decisions of 2010-2012 one was missing — Решение КТС № 819 от 18.10.2011 — and was added, bringing the file to 236. Note that portal sections nest: КТС has both a year section (191 = all of 2011) and per-meeting sections (192-202) whose contents repeat, so a sweep must deduplicate pages by content or the counts lie.

**Checked and known, not gaps** — each already stated on its card: приложение 11 of ПКМ №131, on which п.23 ст.297 rests, is absent from the current redaction (`unver:true`); 122 НКС codes appear in no edition of the act (their own "не подтверждено" card); the legal status of the Kyrgyz building-materials technical regulation is unconfirmed (the registry marks it repealed but names no repealing act, while ПКМ №267's перечень still cites it); the EAEU–UAE schedule is correct but only enters force 06.10.2026; the titanium-dioxide measure's suspension is known from a notification whose decision number was never found.

**Checked and deliberately not added:** the Единый перечень продукции, подлежащей обязательной оценке (подтверждению) соответствия в рамках Таможенного союза (Решение КТС от 07.04.2011 № 620, last amended in 2014). Its chapters are the product groups that the technical regulations have since taken over — chapter 1 is низковольтное оборудование, i.e. ТР ТС 004/2011, in force since 2013 — and it lists ТН ВЭД ТС codes of 2011 vintage. Its residual scope is products no TR covers, which is now essentially empty, so it is not a gap in the file. Do not re-open it without first finding an act that gives it current customs effect.

When you verify a card against its primary source, update its record in the same commit.

**Verify a name against the whole official chain, not against one line.** The `ett` audit record used to say that 3,922 codes whose own text is just «прочие» could not be checked at all — that was the hole: `2201 90 000 0` was named «Лед и снег», which is part of the *heading*, while the position's own text is «прочие». Parse each chapter into `code → товарная позиция : every intermediate subheading (including the un-coded «– –» ones) : own text`, then apply three tests: (1) the position's own text is «прочие» but the file names something specific that appears nowhere in the chain; (2) the file's name overlaps a *neighbouring* row's own text more than its own; (3) two codes of one subheading carry the same name in the file. On 06.09.2026 this found 17 names belonging to the neighbouring row (`0910 99 310 0` «тимьян дробленый или молотый» is actually тимьян ползучий недробленый; `2009 39 510 0`/`550 0` shifted inside the «более 30 / не более 30 / без сахара» triple; `2208 20 270 0`/`290 0`; `3705 00 900 0`; `3909 39 000 0`) plus 368 codes that shared a name with a sibling because the distinguishing clause had been dropped (`0404 10 340 0`, `360 0` and `380 0` all said «с жиром более 27%»). Test (3) is the cheapest and catches the most: identical names on sibling codes are always a defect. Then **run the same comparison over the Cyrillic words alone**: a Latin binomial or a list of heading numbers matches between file and act even when the Russian half was taken from the neighbour, and that overlap hides the error — `0303 34 000 0` read «Торбо (Psetta maxima)» instead of «тюрбо» and survived every other test. That pass found four more shifts and thirteen names that stop at the parent level and omit the position's own text, which is often the only thing distinguishing two codes (`8607 91 100 0` said «прочие: локомотивов» instead of «буксы и их части»; `7226 91 910 0`/`990 0` lacked «толщиной 4,75 мм или более»/«менее»). One more parse artifact to strip: a position added by a later decision is printed with a leading `+`, so «+ 8607 91 900 0» can end up inside the name.

Six traps in parsing those chapter PDFs, each of which silently truncates a name:
- **A subheading is printed in five shapes** — 4, 4+2, 4+2+2, 4+2+3 and 4+2+3+1 digit groups. A regex without 4+2+2 («0106 13 00») drops a whole level out of the chain.
- **The table's column header is reflowed into the row text** — «Ставка ввозной таможенной стоимости либо в евро, либо» glues itself onto names and ruins any word-overlap comparison.
- **A wrapped name shares its line with the wrapped rate**: «ширине более 2, но менее 3» and «0,03 евро за 1 кг» are two cells of one line, so a continuation handler that expects a single cell loses the tail.
- **A numeric continuation is not always a rate.** «27 мас.%» alone on a line finishes the name of `0404 10 360 0`; «0,4 евро за 1 кг» is a rate. Match the phrase «евро за 1 <unit>», because names do contain «стоимостью, превышающей 30 евро за 100 кг нетто-массы».
- **A line holding nothing but a code is a name continuation too** — `8524 11 005 7`'s name «для товаров субпозиции» continues on a line reading «9028 30».
- **Never filter the name cell by "starts with a digit"** — that deletes chemical names like «1,2-дихлорэтан». Filter only the columns after the name.

**The same defect shows up in codes, rates and names: a one-row shift.** `ETT_DB` had 58 rates and 609 names belonging to the *neighbouring* row (`0105 94 000 0` described as «прочие: массой не более 2000 г» instead of «куры домашние»; `2106 90 980 1…5` each carrying the next row's rate). Names cannot be compared literally — the file paraphrases, the act does not — so compare *word sets* and treat "no word in common with the official row" as the signal; that found all of them and produced no false positives worth acting on. When rebuilding a name, walk the official hierarchy («товарная позиция: подзаголовок: собственный текст») and include the un-coded dash headers («– – замороженная:»), which carry meaning the code prefixes do not.

**Completeness of a measure list can be checked through the document stream.** For antidumping there is no published registry of measures in force, but `docs.eaeunion.org/documents/?filter_departament[]=14` lists every trade-defence document (625 of them). Extracting the goods from every «О применении / О продлении действия … меры» notification gives the full set of subjects; each one is then either in the file or a measure whose notification PDF states the date it expired (four had). That turns "we cannot confirm completeness" into a checkable claim, and the same trick applies to any EEC department with its own document filter.

**To find a specific EEC decision by number, use the portal's year sections**, not search — the full, verified table of section ids is in "Finding an older decision by number" below (an earlier version of this line had several of them wrong). Each page lists «Решение Коллегии ЕЭК № NN» with its link, and the document card gives дата принятия / опубликования / вступления в силу. That located nine decisions the department's own document filter did not include. Note that the department stream lags: this file cited Решения № 62/2026 and № 50/2025 that repealed the decisions the latest notifications described, so a "newer than the notification" citation is not automatically wrong.

### Verifying a code list against a Kyrgyz act, in practice

The exemption lists (`ART297_PERECHEN_LISTS`, `ART298_LISTS`, `ART299_CODES`, `LS_CODES`, `MED_CODES`, `MAT_CODES`, …) are transcriptions of annexes to ПКМ КР, and the 05.09.2026 sweep found the same three failure modes in all of them, worth checking for first:

- **A whole annex silently rewritten.** Annex 5 of ПКМ №131 (goods for people with disabilities) was reissued by ПКМ №664 от 14.10.2025 and grew to 141 codes; the file still had 28. Always re-derive the list from the current edition rather than diffing what you remember.
- **Multi-code cells glued into one key.** A cell reading «7216, 7604» became the key `72167604`, which matches nothing. Search every code map for keys longer than 10 digits — that is the signature.
- **An annex that no longer exists.** П.23 ч.1 ст.297 in the file points at "Приложение 11" of ПКМ №131, and the current text has neither the annex nor a single reference to it. When a basis cannot be found, mark the entry (`unver:true`) and say so on the card instead of deleting it or leaving it unqualified.

Extraction tips: parse the annex tables with `wordtable.py`-style tolerant parsing, pick the code column as the first cell that is almost entirely digits, and validate every extracted code against the official ЕТТ prefix set — that alone rejects the glue artifacts. Codes in these acts are written with spaces (`8507 80 000 0`), sometimes with an odd grouping (`0105 11 1100`), and sometimes prefixed «из» for partial inclusion.

### Citations: `DOC_SOURCES` + `docLink()`

`DOC_SOURCES` is a registry of verified `{key: url}` pairs to primary sources (docs.eaeunion.org for EAEU Board/Council decisions, cbd.minjust.gov.kg for Kyrgyz government acts). `docLink(label, url)` renders a real `<a>` when `url` is truthy, otherwise falls back to plain escaped text — **never invent a URL to fill this in**; if a primary source can't be confirmed, leave the citation as plain text (this convention is explicit and intentional, see `session.md`). `NPA_REGISTRY_URL` is the generic fallback link to the Kyrgyz Кабмин NPA registry, used when a specific act can't be pinned down.

Not every citation goes through `docLink()`, though — several DB entries carry their act reference inline inside a `name`/`note` field that `render()` only ever passes through `esc()` (e.g. `NTM_DB` notes, `SAN_REG_DB` exclusion names). Restructuring `render()` just to wire one more field through `docLink()` is usually not worth it. In that case, once a URL is verified, just paste it as plain readable text directly into the `name`/`note` string itself — it renders as inert but legible text, which is consistent with the project's existing precedent and cheaper than plumbing a new field through the render pipeline.

### Verifying legal text against primary sources

`cbd.minjust.gov.kg` is a React SPA — don't try to scrape it as static HTML. It has an undocumented JSON API instead:
- `POST /api/v1/GetDocuments` with `{"number":..., "dateAdoptedFrom":..., "dateAdoptedTo":...}` to find a document's `documentCode` and current `lastEdition` id.
- `GET /api/v1/GetEdition?editionId=<id>&lang=ru` returns the full text (`contentRu`, a Word-export HTML blob) and its date (`nameRus`).
- The public document URL pattern is `https://cbd.minjust.gov.kg/<documentCode>/edition/<editionId>/ru`.
- `GET /api/v1/GetDocument?documentCode=<code>&lang=ru` (no POST, no Cyrillic body) returns the document card, including `editions` — **every** redaction with its id and date — and `documentReferences`, which names the amending acts. This is how you find out that a text has been amended: a Постановление and its Приложение are separate documents, and the annex can have three editions while the parent act still shows one. Checking only the parent act's date is how the НКС set stayed two redactions behind. `GetEdition`'s `nameRus` is the edition's date, not the document's title.
- The registry's `status` field can be stale: ПКМ КР №649 от 08.10.2025 still reads "Не вступил в силу" almost a year after its publication, although its own text says it enters into force 15 days after official publication. Read the act's closing paragraph rather than trusting the status label.
- **Annexes on docs.eaeunion.org come as a `.zip` of `.docx`**, linked from the document card as "Приложения … скачать в word". That is far better material than the PDF: the tables are real cell data. Parse them without extra libraries — a `.docx` is a zip whose `word/document.xml` yields tables by iterating `w:tbl` → `w:tr` → `w:tc` and concatenating `w:t` text (`scratchpad/docx.py` in the 05.09.2026 session did exactly this for the 7,922-row EAEU–UAE schedule). Use it whenever a перечень is attached to an EEC decision.
- **Parse those chapter PDFs with `page.extract_text(extraction_mode="layout")`.** The default flat extraction merges the four columns (код / наименование / доп. ед. изм. / ставка) into one stream, which forces a pile of heuristics — the footnote glued to the rate (`1563С)` = rate 15, footnote 63), a wrapped `, но не менее 0,7 евро за 1 кг` landing outside the row, code cross-references inside names, one code appearing several times per chapter. Layout mode preserves the columns, so a row splits cleanly on runs of 2+ spaces and no heuristic is needed. It also finds what the flat text hides: switching to it took rate verification from 12,886 of 13,451 codes to all 13,292 and immediately exposed 14 more wrong rates. Do this first for any per-chapter ЕЭК PDF.
- **The authoritative current ТН ВЭД/ЕТТ text** is the per-chapter PDF set on `https://eec.eaeunion.org/comission/department/catr/ett/` (`.../ru.2022/ru.<NN>_2022_<DD.MM.YYYY>.pdf`, or `/upload/files/catr/ett/ru.<NN>_2022.pdf` for chapters never amended since 2022). The date in the filename is the publication date of that chapter — quote it as the source of any statement about what codes currently exist. Two parsing traps: rows added by later amendments are printed inline, prefixed with `+`, *inside* the previous row's text, so a line-start-anchored regex misses them (scan the whole flattened text for code patterns instead); and an abolished heading appears as a bare `[8803]` marker, which is a useful signal in its own right.
- The WAF blocks any POST body containing raw (UTF-8) Cyrillic bytes regardless of field name — encode the JSON body with `ensure_ascii=True` (`\uXXXX` escapes) to get through.
- The WAF also blocks plain `GET /api/v1/GetEdition` requests that look like a bare script (no browser-like headers) — add `User-Agent` and `Referer: https://cbd.minjust.gov.kg/<documentCode>/edition/<editionId>/ru` to get a 200 instead of 403.
- For EAEU-level acts (Решения Коллегии/Совета ЕЭК), prefer `docs.eaeunion.org` — do not guess a URL by pattern-matching a neighboring document's numbering; two similarly-numbered documents there can point to completely unrelated acts.
- For EAEU Commission department-level technical/sanitary annexes (e.g. Единые санитарные требования under Решение №299) that aren't single consolidated acts, check `eec.eaeunion.org/comission/department/<dept>/regulation/...` (e.g. `depsanmer` for sanitary measures) — these pages link directly to per-section PDFs at `eec.eaeunion.org/upload/files/<dept>/.../раздел N ЕСТ.pdf`-style URLs (URL-encode the Cyrillic filename). No special headers needed here, unlike cbd.minjust.gov.kg. Fetch with `curl`/Bash and extract text with the `pypdf` package (`PdfReader(path).pages[i].extract_text()`), which is already available in this environment — don't rely on WebFetch's summarizing model for a legal code table, since digit-level transcription errors there are invisible until they cause a wrong lookup.
- `cbd.minjust.gov.kg`'s `GetDocuments` search-by-number can silently return the wrong act: Kyrgyz act numbering is not unique across act types within the same year (a «Постановление» and a «Распоряжение» — or a presidential «Указ» — can share the same number), so a number+date match still needs its `vid`/`organ`/`nameRu` fields checked against what you're actually looking for before you trust it — don't assume a hit is correct just because the number and rough date line up.
- `GetDocuments`'s full-text search (`searchByTextRu`) appears to cap at a small batch of results (~10-17) even when the response's own `totalResultsCount` reports far more, and adding `length`/`pageSize`/`start` params doesn't change this — so don't rely on requesting "more" results; narrow the search phrase itself (longer, more distinctive substrings from the act's actual wording) until the specific act you want lands inside that small returned batch.
- A `GetDocuments` search that finds nothing for a very recently signed act (within roughly the last one to two weeks) is not proof the act doesn't exist — the registry appears to lag real-world signing by that long before indexing. Say so explicitly ("not yet indexed, unconfirmed") rather than treating an empty result as a negative finding.
- `docs.eaeunion.org`'s own search/portal poorly indexes older EAEU Council/Board decisions generally — this isn't limited to the pre-2013 acts noted above; a 2020 decision has also come up unfindable there. Treat any docs.eaeunion.org "not found" as inconclusive rather than as confirmation the act lacks a portal page, and don't burn excessive effort re-trying the same search phrasing once eec.eaeunion.org and independent cross-checked secondary sources have already been exhausted.
- **The current text of an EAEU list is often published by ЕЭК, not by the legal portal.** `docs.eaeunion.org` carries the act as signed; for a list that has been amended many times, look for a consolidated publication on `eec.eaeunion.org` first. Two that matter here: the Единый перечень of Решение №30 has one consolidated PDF *per section* linked from `https://eec.eaeunion.org/comission/department/catr/nontariff/ep.new.php` (files like `/upload/files/catr/EP.pdf/2.3_137.pdf`), and the ЕАЭС–Сербия exclusion list has a single consolidated file on the same site. **The filename does not reliably give the section number** — section 2.12 (наркотические средства) lives in `2.13_45_2026.pdf` — so take the number from the heading inside the PDF itself. Parse these with `extraction_mode="layout"` and derive the code column's left and right bounds from the table header row; without a right bound, Basel-convention codes (`А1030`, `B3040`) and years from the prose land in the code set.
- **The consolidated text of an EAEU list lives on the responsible department's page, not on the legal portal.** Beyond the Единый перечень of Решение №30 (department `catr`), the sanitary list of Решение КТС №299 is published whole as `eec.eaeunion.org/upload/files/depsanmer/Санмеры/Единый перечень.pdf`, linked from `.../depsanmer/regulation/sanitarnye-mery.php` — its header lists every amending decision, and it carries both Раздел I (numbered items with their ТН ВЭД group sets) and Раздел II (a per-group code table). A previous revision recorded that ЕЭК "does not publish" this text; it does. Before writing "no consolidated text exists", open the department's own regulation page.
- **A dispute over whether a code still exists is settled by the official per-chapter ЕТТ publication, never by comparing tariff aggregators.** `4412 32 100 0` sat unresolved for a session because kodtnved.ru and tws.by disagreed; the ЕЭК chapter 44 PDF settles it in one line (HS2022 split 4412 32 into 4412 33 and 4412 34, so the code does not exist). Check the chapter PDF first and skip the aggregators.
- **A cbd.minjust.gov.kg `documentCode` in an existing citation can be wrong even when the act name looks right.** `7-21561` was cited here as ПКМ КР №267 от 20.05.2022 about certification; it is actually ПКМ №263 of the same date about pay scales. Kyrgyz acts also split into several registry documents: ПКМ №267 is `7-21576`, its Приложение 2 (the перечень) is `43-141`, and the two procedures attached to it are `50-407` and `50-408`. Search by number and date, then read `nameRus` of every hit before trusting one — and expect the annex you want to be its own document.
- The registry's `status` can say «Утратил силу» while `terminationHeaderRu` and `terminationData` are empty, i.e. without naming the repealing act or a date. Treat that as a flag to re-check, not as proof: the ТР law on building materials is marked repealed while ПКМ №267's перечень in its 22.05.2024 redaction still refers to its annex. Keep the data and say the status is unconfirmed rather than deleting positions.
- **A decision's rates and code lists are usually in its annexes, not in the decision.** Each document page on `docs.eaeunion.org` attaches the decision in every Union language plus an `*_att.zip` of the annexes; a rate table read only from the main `.docx` will come back empty. Pick the Russian file by the letters that Russian does *not* have (`ә қ ң ө ұ ү һ і ў ғ`) plus the Armenian Unicode block, not by heading words — every translation opens with the same words. This matters beyond convenience: **the official Kyrgyz translation of Решение Коллегии ЕЭК №12 от 09.02.2021 omits code 7306 40 200 9**, which the Russian original and the Kazakh and Armenian translations all carry, so a check run against the wrong file reports a phantom discrepancy in the DB.
- **A legacy `.doc` annex still yields its numbers.** Some decisions attach their annex as Word 97 (`Прил. к реш. КЕЭК.doc` inside the `skachat-v-word.zip`), which `zipfile` cannot open and whose PDF is often a scan. Decode the whole file as UTF-16LE and keep the printable runs: codes and figures come out exactly, and vertically merged cells show up as missing values in a row — which is itself information, since the merged value belongs to the group. This is how the 2026 and 2027 tariff-quota tables were read.

  Two follow-on traps. **Filtering the decoded runs by "almost all characters are Cyrillic" silently drops rows**: in the Word 97 annex to Решение Коллегии ЕЭК от 11.01.2022 № 6 that filter threw away position 4 of the перечень (сжиженный природный газ, 2711 11 000 0), because it shared a line with binary junk. Count the positions against the numbering in the text, never against the number of surviving lines. **And the Russian original is not always where the filename suggests**: for Решение Коллегии ЕЭК от 16.04.2019 № 61 the `_doc.pdf` is a scan, the `_doc.docx` is the Armenian translation, and the Russian text is inside `_att.zip`. Beyond losing codes, translations can lose structure — the Kyrgyz version of that decision merges subparagraphs «б» and «в» and omits «г» entirely.
- **Preferential rate schedules live under `eec.eaeunion.org/comission/department/catr/ttr/Preferences/<country>/`** — one consolidated PDF per country (Vietnam, Iran, Serbia, Mongolia), reachable from `freetrade.php`. Every code covered by the agreement is listed, and most rows say «ставка ЕТТ», meaning the agreement does not change the rate; only the rows with a different rate belong in the file. Watch for rows written «из <код>»: the Vietnam list carries fourteen of them, and one (`из 9006 59 000 9`) explicitly *excludes* `9006 59 000 1`, which the file had been offering the preference for.
- **Finding an older decision by number**: the portal's year sections are not numbered consecutively by year. Коллегия ЕЭК → Решения: 2012 → 277, 2013 → 251, 2014 → 254, 2015 → 292, 2016 → 305, 2017 → 315, 2018 → 253, 2019 → 335, 2020 → 247, 2021 → 379, 2022 → 399, 2023 → 414, 2024 → 429, 2025 → 446, 2026 → 463. Совет ЕЭК → Решения: 2025 → 447, 2026 → 461. Page a section with `?PAGEN_1=<n>`. Link labels in the older sections omit the space — «Решение Коллегии ЕЭК №178», not «№ 178» — so a regex that requires one silently finds nothing.

  **Beyond the last page the pager lies.** `?PAGEN_1=<n>` with n past the real page count returns the *first* page's content rather than an empty list, so a loop that stops on "no results" never stops. A Коллегия year section holds 100 documents per page and three to four real pages; the tell is that the set of decision numbers stops growing. Sweeping all fourteen sections this way is the only reliable completeness check for "does an act of this kind exist" — it is what found the ТР ЕАЭС 045/2017 перечень and confirmed that Решение № 136 от 05.09.2023 repealed the earlier tractor list. Listing pages carry the *full* title of every document, so the sweep can be done on the listing text alone, without opening cards; search both for the regulation's designation («ТР ЕАЭС 045/2017») and for a reference to the base decision («от 13 мая 2014 г. № 70»), because an amending act's title usually contains only one of the two.
- A code extracted from an official PDF sometimes has fewer digits than the file's own DB entry (e.g. source says "8421 39 200", DB has `8421392000`; source says "8716 39 800", DB has `8716398000`) — don't assume this is a PDF-extraction artifact (a dropped trailing zero) without checking. Confirm one way or the other by (a) checking whether the shorter form recurs multiple times in continuous prose across independent documents (a real, deliberately-shortened conventional reference) vs. appearing once inside a table cell (more likely a layout-driven truncation), and (b) checking whether the longer, fully-qualified code actually exists as a real current tariff line — search this file's own `ETT_DB` first, then a tariff aggregator (alta.ru, tks.ru, kodtnved.ru, tws.by). If the long code is real and in active use, keep it; if no such code exists anywhere, truncate the DB entry to the shorter, confirmed subheading-level code instead of leaving an unreachable one in place.


### Conflicting matches within one `findX()` — most-specific-code-wins

Several `findX()` functions match by prefix (`cn.startsWith(qn)||qn.startsWith(cn)`), which lets a query simultaneously hit both a broad, generic-level entry (e.g. a whole heading `2915`) and a narrow, more specific one nested inside it (e.g. an exclusion for exact code `2915120000`) that's meant to override it. Left unhandled, `render()` shows both cards at once with contradictory messages (e.g. "registration required" next to "registration not required" for the same code). `findSAN()` (near `SAN_REG_DB`) solves this by computing, per candidate match, the length of its longest code that is actually a prefix of the query (i.e. genuinely applicable to this specific query, not just "contains a longer code somewhere"), then keeping only the matches tied for the maximum such length — so a more specific hit suppresses a more generic one, but a bare/short query (shorter than any candidate code) isn't wrongly reduced to nothing. If you add a new DB where a specific entry is meant to carve an exception out of a broader one, replicate this pattern in that `findX()` rather than trying to patch it in `render()`.

### Editing the large data literals

Several DB constants are single lines hundreds of KB long (the whole `NKS_ITCAT` object or `NKS` array can be one line). The `Edit` tool is unreliable at that size — prior sessions insert/remove entries with a small Python/Node script that does a targeted, anchor-based string replacement on the raw file text (confirm `content.count(anchor) == 1` before replacing, to avoid silently touching the wrong occurrence), then re-run the syntax check and a runtime smoke test. Bulk table data pulled from a fetched legal text is parsed out separately (regex over the stripped-HTML text, watching for CAS-number/ISO-number/range-reference collisions eating adjacent real codes) before being spliced in the same way.

**Relabeling many existing entries in an object literal** (e.g. correcting hundreds of `NKS_ITCAT` codes that were categorized under an old/generic label and should say something more specific): don't do hundreds of scattered surgical replacements across an 8 MB single-line file. Instead, just append new `"code":[...]` entries with the *same keys* to the end of the object literal, right before its closing `};` — a JS object literal lets a later duplicate key silently override an earlier one, so the new label wins at lookup time while the old entry stays physically in the file, inert. Much safer than editing hundreds of scattered locations, at the cost of some dead weight in the file.

**Parsing a Word-exported HTML table** (the `contentRu`/`contentKg` blobs from cbd.minjust.gov.kg, or any `.docx`→HTML dump): these tables routinely omit closing `</tr>`/`</td>` tags, relying on the next opening tag to implicitly close the previous one — feeding this to `html.parser.HTMLParser` naively produces empty cells, because nothing ever calls `handle_endtag`. Write the parser to close the current cell/row explicitly inside `handle_starttag` whenever a new `<td>`/`<tr>` opens (in addition to on the real end tag), not just in `handle_endtag`. Also watch for tables nested inside a note/example cell (e.g. a materials-compatibility reference table embedded in a "Примечание") — they show up as extra `<table>` elements in sequence; since they generally lack a code column, they're harmless to include in the row stream as long as downstream row-classification filters on the expected item-number pattern (e.g. `^\d+(\.\d+)+\.?$`), which such nested tables' first cells won't match.
