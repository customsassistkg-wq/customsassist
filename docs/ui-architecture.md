# UI architecture: result page, card post-processing, login screen, themes, phone width

Moved out of `CLAUDE.md` on 20.09.2026 without changing the text of the paragraphs (headings added). **Read before changing layout, cards, the verdict/summary, the login screen, colours or themes, responsive/phone rules, icons, or anything measured in a browser.** The card templates themselves live in `base.js` and are described in [base-architecture.md](base-architecture.md); everything here runs in `checker.js` and the page after `render()` writes its markup. How to open the page in a browser without the backend is in [testing.md](testing.md). Design work on this project is done under the Senior UI/UX brief the owner gave: measured, not eyeballed, and in the comfortable contrast band (the owner finds high-contrast white-on-dark physically tiring).

## The result page is a verdict and sections, built by post-processing (18.09.2026)

The UX audit of 18.09.2026 (measured on the harness of `engine-browser.test.js`, not by eye) found the result page saying everything twice — a 16-row summary of pills above 16 cards each headed by the same code in 22 px — with the search field at 43 % of the first screen behind a 133 px header and a decorative image. What replaced it lives in `checker.js` after `render()`, so the ~40 card templates in `base.js` are untouched:

- **`resSectionOf(card)` assigns every card one of six groups by the text of its tags and title** — Запреты, Разрешительные документы и лицензии, Контроль на границе, Сертификация и техрегламенты, Платежи и ставки, Справочно. It reads text, not tag classes, because the classes are semantically mixed (`t-nks` is worn by НКС, СЭН and ветконтроль alike; `t-ex` by a ban, an excise and the Red Book). A new card lands in a group by its words; if it lands wrong, extend the regexes there rather than adding a class. The «info» check runs first («не требуется», «исключено», «истёк», «ТРОИС», «УСИР»…) — and it must say «исключено», not «исключен», or the UAE card («перечень исключений») falls out of Платежи. **A tag must not contain «запрет» even in a negation**: «Прослеживаемость — учёт, не запрет» sent the traceability card to Запреты and turned the verdict of every television and fridge red (fixed 29.09.2026 — the tag is «учёт в ЭСФ 2.0»). The same day «разрешени», «маркировк», «прослеживаем» and «условия ввоза» joined the documents group, where a pyrotechnics permit, the marking card and the live-fish conditions had been sitting in the collapsed Справочно. In `lkFilter` a merged card's country sub-blocks are now filtered for an EAEU country too (before, «Россия» left Mongolia-only veterinary restrictions visible); the preference family is still hidden for the EAEU by `data-kind="tariff"`.
- **`buildResultSummary()` renders the verdict**: one row per group with a count, the first three measure labels and, for Платежи, the ЕТТ rate; «Запреты — нет» is printed even when empty, because that is the answer people come for. A row scrolls to its section (`focusResultSec`).
- **`sectionResultCards()` wraps the cards in `<section class="res-sec">`** in that order, creates each section once and only appends to it — moving an already placed card restarts its entry animation every time the asynchronous class-decisions card arrives. Sections are a two-column grid from 900 px, bans a single column. **All three passes take their cards through `resCards(container)`** (direct children and children of sections); a `:scope > .card` query written elsewhere will miss everything inside a section.
- **The card title is the measure, not the code**: `enhanceResultCards()` moves the first `.rn` into the header above the code (`rn-title`) whenever `.rc` is only digits, and prints the templates' «8517…» as «8517 · совпадение по позиции» — it read as a truncated code. Severity is a 3 px bar on the left (`data-sec`), coloured frames are gone, the ЕТТ rate is text-coloured rather than pink.
- **The legal-basis line shows one link collapsed and all of them open** (`.card:not(.open) .legal-basis a:nth-of-type(n+2)` is hidden); nothing is truncated to 64 characters any more.
- **Layout**: header is one row (brand · access chip · email · logout · theme), the hero image is gone, the search field starts at 133 px on the desktop and the quick-search examples are `#quickSearch` under the field, shown only in the empty state of code search through `body[data-page]`/`[data-mode]`, which `setPage`, `setSearchMode` **and `initApp`** set — the first run forgot `initApp` and the home page had no examples. Navigation is three groups (Поиск · Справка · AI; Калькуляторы; Справочники); at ≤ 1180 px `.sidebar-left` becomes `display:contents` and the nav is a horizontal strip above the content — give it `align-self:stretch;width:100%`, or in a column flex container with `align-items:flex-start` it takes its content width (1 647 px on a 390 px phone, found by ranking every element whose right edge exceeds `clientWidth`).
- **Flat surfaces, and colour only where it means severity (second pass, same day).** The owner's reaction to the first pass was that the glass style «не нравится», the verdict text «белый, не сочетается», and a copied verdict came out glued («Запретынетв базе…»). The flat look is done through tokens, not rules: `--glass` is a solid surface, `--glass-blur:none`, one thin shadow, radii 10/12, no `body::before` gradients, the active nav item a muted indigo fill. `.card .ico` and `.card .tag` override every `.c-*`/`.t-*` hue to neutral, and `data-sec` paints them red (danger) or amber (docs/control/cert) — so the nine semantic hues no longer compete. The verdict prints rows only for groups that exist (the title says «Запретов нет» or «⛔ Есть запрет»), a one-line meaning under each group (`RES_HINT`), abbreviations expanded once per verdict by whole-label match (`RES_GLOSS` — matching by prefix expanded «СЭН» twice and cut the second label), and spaces plus a newline inside its markup so a copy reads as lines. Keep `.wrap` at 1560 px: narrowing it to 1320 read as «совсем узко стало».
- **A full-screen illustration behind the login, with the hero column removed, was tried and rejected (18.09.2026).** What the owner accepted instead is the picture as a background under the unchanged layout (see the login section). Do not remove the hero column without asking.
- **The app background and the header logo come from the owner's pictures (since 18.09.2026).** `assets/source/logo_dark.png`/`logo_white.png` carry the brand drawn in their top-left corner; `tools/split-app-bg.py` splits each into a background with that corner patched (`assets/app-bg-*.webp`) and the logo as a transparent cut-out (`assets/app-logo-*.webp`, colour-to-alpha against the patched background, with a six-level tolerance — without it a near-zero channel makes the whole rectangle opaque). Re-run it if the pictures change, and re-measure the logo's crop in its `JOBS` table. The background is `#appWrap::before` under a `--app-scrim` veil, chosen by the `--app-bg` token so only the current theme's file is fetched; the header shows one of two `<img class="hdr-logo">` by theme, sized so the visible mark is 36 px like the vector one it replaced. The vector symbol `#caLogo` is gone: nothing uses it any more. Buttons and chips have a solid `var(--glass)` background, because translucent ones read poorly over the bright waves.
- The empty result no longer claims «товар, вероятно, не ограничен»: a non-existent code gets «такого кода нет в действующем ЕТТ — проверьте цифры или введите название».

**Second pass, same day, after a measured audit (the owner's «исправляй, что нашёл»).** All of it is post-processing in `checker.js` and CSS; `base.js` changed in two places. `mergeCardFamilies()` runs before `compactifyCards()` and folds a family — the НКС lists, the two СЭН cards, the preference cards, the VAT-exemption cards (`CARD_FAMILIES`, matched by title) — into one card whose members become `.sub` blocks that keep their markup and `data-cty`; `lkFilter` hides a sub of another country and the whole card when none is left, so the country test still sees zero `.card[data-cty]` for Germany. `buildResultSummary()` now prints the product (full name and VAT from `codeBundle`, the same server answer the calculator uses), «Рассчитать платежи» (`openCalcFor`), the ban line with its direction («⛔ Запрет вывоза — на ввоз не распространяется»), «Нужно оформить» chips that jump to their cards, a payments line and one «Справочно» line; `RES_HINT` is no longer printed. A short code puts its sub-position list card (`data-pick`) first, outside the sections, and «Справочно» is collapsed (`res-sec-collapsed`). In `base.js` a digits-only query of four or more digits never falls to the name search («9999 99 999 9» used to find silver of fineness 999), and name candidates carry full names. The search field has a loading bar, a hint for 1–3 characters, a history of six queries (`localStorage` `ca-hist`) and sub-position suggestions for 4–9 digits (`calcCodeList`) that hide once the same query's result is on screen; the examples are eight in one row with the old groups behind «Больше примеров». The header keeps only the theme switch and an account menu (`#accMenuBtn`: status, admin, logout — `checker-access.test.js` opens it before clicking «Выйти»). `fmtCode` strips spaces first: the raw query «8517 13 000 0» came out as «8517  1 3 0 00 0» in five cards. Phones (≤ 640 px) get a bottom tab bar (`#tabBar`: Поиск · AI · Расчёт · Коды · Ещё; «Ещё» opens the nav panel as a sheet through `body.nav-open`, and the horizontal strip is hidden there — written as `.side-panel.nav-panel`, because the base `.nav-panel{display:flex}` sits later in the file and wins at equal specificity; the same trap put `#toTopBtn` over the «Ещё» tab until its phone `bottom` moved into the later rule, and cut the 84 px bottom padding of `.wrap` to 32 px because a later `padding` shorthand in the same media block rewrote it, so the end of every page sat under the tab bar. A scan of every `@media` declaration against later rules with the same selector (same or wider media, or none) found both, plus print rules for the admin table that the base rules below them overrode; after the fix it reports zero — re-run it after adding rules to a media block, since nothing in a browser warns about a declaration that never applies), and a chapter in the classifier links its ЕЭК explanatory-notes PDF (`psnUrl`) and the section notes. `engine-browser.test.js` finds the calculator buttons as `#calcResult button` by their text, and `assistant-browser.test.js` opens AI through whichever button is visible (`#navAiBtn` on the desktop, `#tabBar` at 420 px) — a test that clicks a nav item hidden on phones waits 30 s and fails. All three of the items that pass left open were closed later the same day, and each is a rule now. **Classifier and notes are one page**: `#pageNotes`/`#navNotesBtn` are gone, the ЕЭК source and the ОПИ link sit in the root card of the classifier, every group cell of a section carries its «Пояснения к группе (PDF ЕЭК)» link as a sibling of the button (an `<a>` inside a `<button>` is invalid), and `renderNotesRoot`/`renderNotesSection`/`openNotesForCode` survive only as redirects into the classifier, because `base.js` rows still call `notesIconHtml`. **Icons are an SVG sprite at the top of `<body>`** (`<symbol id="i-…">`, 24×24 stroke, `currentColor`), referenced as `<svg class="ic"><use href="#i-search"/></svg>` in the nav, the tab bar and the theme switches; card icons are swapped by `iconizeCards()` in `enhanceResultCards()` through `ICON_MAP` (emoji → symbol), which keeps the original emoji in `data-em` — `lkApplyRates` finds the ЕТТ card by it — and leaves alone what the map does not know (flags, ☣️, 🐄); the same pass strips the leading emoji from card tags («🔐 Требует лицензии» → «Требует лицензии»), which `resShortLabel` was already doing for the verdict — so a tag's emoji is decoration in the template and nothing may key on it. A new card template needs no work: give it an emoji the map knows, or add one symbol and one map entry. **Sizes are tokens**: `--fs-xs…--fs-5xl` (10/11/12/13/14/15/16/18/20/22 px; 24 distinct values became ten steps, fractional sizes and 9 px folded to the nearest step, the six display sizes of the login hero and the «not found» card stay literal), `--radius-xs` (6 px) joins the radius scale, and `--ring`, `--ring-bad`, `--glow`, `--shadow-up` replace the hand-written focus rings, button glows and the tab-bar shadow. Write a new size or shadow as a token; the login card keeps its own three radii and two shadows on purpose. Note that `.si` on phones is `--fs-2xl` = 16 px, which is exactly the iOS zoom threshold — do not lower that step.

## The result list is styled by post-processing, not by the card templates

Three passes run over the finished markup of `#result` after `render()` writes it, in this order: `compactifyCards()` (collapse everything after `.tags` behind a click on the header), then `enhanceResultCards()`, which calls `buildResultSummary()` last. Doing this on the DOM rather than in the ~40 card templates is deliberate — a layout change would otherwise have to be repeated in every template — and it means **a new card template gets all of it for free, as long as it follows the existing shape** (`.rh > .ico + .rc`, then `.rn`, then `.tags`, then the details).

What each pass keys on, so a new template does not silently opt out:

- **The summary banner reads the cards' own `.tag` elements** — their text becomes the chip's bold label and their class its colour (`SUM_TAG_COLOR`), while the card's `.rn` becomes the rest of the line and `SUM_FLAG_ORDER` its position. There is deliberately no "card type → risk" table to keep in sync; give a new card a tag with an existing `t-` class and it shows up correctly. The banner is skipped when there is only one card. **It is one row per card, not two.** Until 10.09.2026 it drew risk chips from the tags and jump buttons from the `.rn` texts in two separate rows, which said the same thing twice — «🛡️ Товарный знак в ТРОИС» above «🛡️ По этому коду … есть действующие товарные знаки». They are merged into one clickable line per card (`.sum-items`/`.sum-item`); a card with no tag still gets a line, or it would be unreachable. The tell that two such rows should be merged is that their elements correspond one-to-one to the cards.
- **A card is "alerting" (raised to the top of the list, red frame) if it carries a ban tag** — `t-ex`, `t-im`, `t-eec-ex`, `t-eec-im` — not if it carries class `c-ex`, which list cards use too. Already-raised cards are marked `data-ord`, so the classification-precedents card that arrives asynchronously does not re-trigger the entry animation of everything else.
- **Anything the user must see while the card is collapsed has to be moved out of `.card-more` explicitly.** `.ett-rate` sits after `.tags` in the template, so collapsing hid the duty rate — the very number that card exists for; `enhanceResultCards()` moves it back. The same applies to any new "headline" element placed after the tags.
- **`auditNote()` renders a `<details>`,** not a paragraph: only the status line and the date stay visible on the card. Its text runs to 2-3 kB, which is why `.card.open .card-more` allows 9000px.
- Links found anywhere in a card are collected into a `.legal-basis` plaque above the collapsed part (deduplicated by URL, first four shown). That is one more reason to route a verified citation through `docLink()`: an `<a>` reaches the plaque, plain text does not. **A link that belongs to one row of a list, not to the card, must carry class `lb-skip`** — the collector takes `a[href]:not(.lb-skip)`. The ТРОИС card is why: every row links to its own page of the register (`#page=63`, `#page=270`, …), and without the opt-out a card with a dozen rows filled its plaque with page links while the acts fell into "+ ещё N".

**A skewed results grid is never about the grid — it is one unbreakable token.** `#result` becomes a two-column grid while a search is active, and on 11.09.2026 its columns came out 332 px and 1296 px with the page scrolling horizontally to 2007 px at a 1280 px viewport. `1fr` means `minmax(auto, 1fr)`, and a track's automatic minimum is the min-content width of the widest item in it — so one item can widen a whole column. Find it by measuring, not by eye: set `width:min-content` on each card in turn and rank them. Eleven cards measured 150-333 px; the Mongolia preference card measured 1296 px because its `.det` carried a **percent-encoded URL 205 characters long** pasted in as plain text. A sweep over 380 codes confirmed it was the only one — every other long token is at most 82 characters (chemical names, ordinary links). Two structural fixes went in alongside routing that URL through `docLink()`: `repeat(2,minmax(0,1fr))` on the grid, so no item can ever widen a track again, and `overflow-wrap:anywhere` on `.card`, so a long token wraps instead of stretching the card. This is the limit of the "paste a verified URL as plain text" convention documented above: it is safe until the URL is percent-encoded, and Cyrillic in a filename turns the link into a two-hundred-character word.

## The login screen is the one dark surface, and its ids are load-bearing

`#authScreen` is a full-screen overlay holding four views — `authViewLogin`, `authViewForgot`, `authViewReset`, `authViewRegister` — that `showAuthView()` toggles. It was redesigned on 11.09.2026 into a two-column CustomsAssistKG landing (presentation on the left, glass card on the right) on a deep-indigo canvas, while the app underneath stays light. **Every rule for it is namespaced under `#authScreen` or an `.auth-*` class**, and its scoped palette lives in `#authScreen{--ac-*}`; keep it that way, or a dark token leaks into the light app. The screen's own message boxes reuse the app's `.calc-warn`/`.w-red`, repainted by `#authScreen .calc-warn{…}` overrides rather than by new classes.

**The ids are the contract.** Roughly thirty of them (`authEmail`, `authSubmit`, `authRegisterWebsite`, …) are referenced from the auth JS, and `initAuth()` also depends on `authViewReset` existing, because a `?reset=<token>` link is handled before the session check. Restyle freely, rename nothing. `authRegisterWebsite` in particular is the registration honeypot — it must stay a visible-to-bots text input hidden by off-screen CSS, not `type=hidden`.

**Code that a guest can reach must not use anything from `checker.js`.** Since 14.09.2026 `server/private/checker.js` arrives only after login, so everything a visitor without a session can press — registration, resend, password recovery, the reset and verify links — may use only names declared in the page itself. `submitRegister` called `EMAIL_RE`, which is declared in `checker.js`: from 14.09 to 17.09.2026 the «Создать аккаунт» button threw `ReferenceError: EMAIL_RE is not defined` for every new visitor before any request left the browser, so the server journal had nothing to show. It worked in exactly one situation — a window where someone had already logged in and out, because a loaded script stays loaded — which is the very way a developer re-checks a registration form. The page's own `AUTH_EMAIL_RE` is used now. `checker-access.test.js` walks the guest path in a fresh page (register, resend, forgot) and requires zero page errors with `typeof findETT === 'undefined'`; a sweep of every top-level name of `checker.js` referenced from the page's inline scripts found this one hit and nothing else (the rest were strings, comments, `typeof` guards and post-login code in `showApp`). **Check a guest flow in a fresh browser context, never after logging out.**

**The login logo and backdrop come from the owner's pictures (since 18.09.2026).** `assets/source/logo_dark1.png`/`logo_white1.png` are split by `tools/split-app-bg.py` into `assets/login-bg-*.webp` (the `.auth-screen` background, chosen by `--login-bg` under a `--login-scrim` veil) and `assets/login-logo-*.webp` (two `<img class="auth-logo-img">` by theme, in the hero column and in the card on phones). Their widths (322/307 px) were set by measuring the previous mark in a browser, so the visible logo stays 300 px wide; re-measure if the pictures change. The layout of the screen — hero column with slogan and three features, card on the right — is unchanged. The dark picture has a bright arc right by the magnifier, which a rectangular patch smears or blackens, so that job uses `inpaint` (OpenCV Telea over a mask of the logo's own pixels); keep `opencv-python-headless` in mind when re-running. The block under the registration button («Customs Assist KG», «Таможенные данные • ТН ВЭД • Кыргызстан», «© 2026») was removed at the owner's request.

**Button labels live in `<span class="ab-label">`, and state is a class.** The handlers used to do `btn.textContent='Вход...'` and then restore `'Войти'`, which hard-coded the label in three places; the moment the markup called the button anything else, the first click silently renamed it. `authBtnBusy()`/`authBtnOk()`/`authBtnReset()` now toggle `.is-busy` (CSS spinner) and `.is-ok` instead, leaving the text alone. If you add another auth action, use those helpers rather than touching `textContent`.

**Field validation is local and mirrors the server.** `authCheckEmail`/`authCheckPassword` mark `.auth-field.is-bad` and write into its `.auth-fe`, so the message sits under the field rather than in the banner at the top; `AUTH_EMAIL_RE` is deliberately the same pattern as `EMAIL_RE` in `server/src/routes/auth.js`, so the form neither rejects what the backend accepts nor forwards what it will refuse. The highlight clears on the next keystroke through one delegated `input` listener.

## Two themes, switchable, and the theme lives in the tokens

**Light is the default since 24.09.2026 (owner: «по умолчанию давай светлую тему будем ставить»).** The boot script at the top of the page (and of `server/dash/index.html`) sets `data-theme="light"` unless `localStorage["ca-theme"]` is `"dark"` — so everyone who never touched the switch, and every browser where storage is blocked, gets light; whoever chose dark keeps it. The script is wrapped in a function so its variable never becomes a global. `manifest.webmanifest` uses the light `#E8EBF1` for the installed app's splash and bar. The dark palette stays in `:root`, light in `:root[data-theme="light"]`: only the default changed, not the tokens.

**The switch is one control everywhere (22.09.2026, owner's request «одной кнопкой… красиво оформи»).** `.theme-toggle` is a `role="switch"` button with a sliding knob: the knob carries the icon of the current theme and sits on its side of the track (moon left, sun right), the other icon shows faintly on the free side to say where a tap leads, and a label next to it names the current theme («Тёмная»/«Светлая»; hidden on phones by `.hdr-tools .tt-txt`/`.auth-theme .tt-txt`). `aria-checked="true"` means light; `syncThemeButtons()` updates every `.theme-toggle` on the page (state, label, `aria-label`/`title`) and one click handler toggles. The same markup sits in four places — the login screen (`#authThemeBtn`, with class `auth-theme` for the corner position and the `--ac-*` palette), the app header (`#themeToggle`), and both spots of the dashboard page — so a restyle is one CSS block copied twice. The previous two-button group (`.theme-sw`, `#themeDarkBtn`/`#themeLightBtn`, `aria-pressed`) is gone; tests click `#themeToggle`.

On 11.09.2026 the interior was repainted to match the login screen: graphite canvas, glass panels, the same accent gradient. The first attempt used a saturated navy (`--bg:#0A0F20`) with near-white text (`#E9EDF8`) and the owner reported it as physically tiring — «болят глаза». **That was a contrast-too-high problem, not a contrast-too-low one**: 16.3:1 on a background with visible blue saturation makes small text halate. The shipped palette is the softened one — `--bg:#171A21`, `--text:#D7DBE3`, 12.5:1, background saturation down from 22 to 10. Aim for roughly 7-12:1 here; WCAG's 4.5:1 is a floor, not a target, and the audit below only catches the floor. **The whole theme is `:root` tokens** — `--bg`, `--surface`, `--text`, `--muted`, `--glass*`, `--shadow*` and the nine semantic hues — so a future re-theme is a token edit, not a sweep. Three things make that true, and breaking any of them re-opens work that is already done:

- **The semantic hues were raised in lightness, not renamed.** «Запрет — красный, разрешено — зелёный, ставка — розовый» still holds; the original values (`--red:#E0342B`, `--teal:#0E8A96` …) were picked for white and read as mud on dark, so they became `#FF7A72`, `#3FC7D4` and so on. The low-alpha rgba tints behind chips and icons were **left alone on purpose** — the same hue at 8-30 % over a dark ground gives the right muted wash, and repainting them would have been a hundred pointless edits.
- **One token could not serve both roles.** `--indigo` is a text colour in eleven places and a button background in three; lightening it for text dropped white-on-indigo buttons to 3.5:1. It was split: `--indigo` (light, for text) and `--indigo-surface` (deep, for the active nav item and the search button).
- **`@media print` now re-declares the light palette.** The print block used to inherit a light theme by default; with dark tokens a printout would be near-white text on white paper. It overrides `:root` back to light values inside the print media block only, plus `body`/`.card`/`.side-panel`/`.modal` backgrounds. Verified by emulating print media and reading computed styles: body goes `rgb(255,255,255)` / `rgb(17,17,17)`. Keep that block in sync when adding a token.

**Every colour that depends on the theme must be a token.** The first dark pass left a handful of values hard-coded in rules (`#7FD6EE` for cyan text, `#9AA8C6` for hints, the placeholder grey …). They looked fine, and then the first attempt at a light palette came back with 21 contrast failures — because those values stayed dark while everything around them turned light. They are now `--ink-cyan`, `--ink-blue`, `--ink-link`, `--hint`, `--placeholder` in `:root`, so a palette swap really is one block. If you add a colour that has to change with the theme, add a token; do not write the value into the rule.

**The old light theme was worse than either dark one.** Running the same audit against the pre-11.09 version reports **398** contrast failures on a single results page — small tinted chips on a light ground. So «просто вернуть светлую» is not a way out; a light palette for this app needs its chip colours redone first (about 13 of them).

**There are two themes and a switch.** Graphite dark is the default; light is grey (`--bg:#E8EBF1`), not white, because at this user's sensitivity a white ground is the same glare mistake in the other direction — 14.4:1 against 12.0:1. The light theme is `:root[data-theme="light"]` plus about twenty `[data-theme="light"] .selector` rules for the places where a translucent *white* glass fill is baked into the rule and cannot be expressed as a token. The choice lives in `localStorage` under `ca-theme`. The control sits **in the header, top right** — it was first put in the left nav list and the owner reported not finding it: among eight section buttons it reads as a ninth section rather than a setting. On the login screen the same control is a labelled pill in the top-right corner; the label matters, because a bare icon there was missed too.

**The switch is applied by a boot script in `<head>`, and that tag is deliberately `<script data-boot>`, not `<script>`.** The theme has to be on `<html>` before first paint or a light-theme user sees a dark frame flash on every load. `checker-access.test.js` and the server-side deploy check compile the page's first *bare* `<script>`, so writing the boot tag with an attribute keeps that check pointed at the auth script. If you ever add another script tag, keep that property or update both.

**The first script of the page reports browser errors, and it too carries an attribute: `<script data-errors>` (01.10.2026)**, just before `data-boot`. It listens for `error` and `unhandledrejection` on `window` from the very first line, so it covers the login screen (guest code) and `checker.js` (a `blob:` script in the same window), and posts at most five cleaned reports per load to `/api/client-error` (what is cut and why — [backend-ops.md](backend-ops.md), «Монитор доступности…»). It uses only standard APIs, as any guest-reachable code must. The section it reports is `auth` while `#authScreen` is displayed (`getComputedStyle`, not `offsetParent`: the screen is `position:fixed`, and `offsetParent` of a fixed element is always `null`) and the id of the active `.nav-item` otherwise. Its syntax is checked only by the browser tests (`client-error.test.js` loads the page and expects no page error but its own).

**Images are files under `/assets/`, never base64 in the page (01.10.2026).** The footer logo — the pre-18.09.2026 emblem with the flag, shown at 40×40 — sat in the page as a 420×420 PNG: 207 KB of 481 KB, downloaded again with every new page version. Since 01.10.2026 the footer shows **the current mark — the magnifier with the sun and the box from `logo_wide.png`, the same as in the header and on the login screen** — on a white square, `assets/footer-logo.webp` (120×120 for 3× screens, 4.4 KB, made by `tools/build-logo.py` like the icons: the lens is cut from `WIDE_BOX`, and the edge of the first letter, which the lens handle reaches under, is whitened first), `loading="lazy"` like the other logos; the page went from 481 KB (275 KB gzip, as Nginx sends it) to 208 KB (66 KB gzip). `static-assets.test.js` fails when base64 images in the page exceed 32 KB in total (the favicon from `tools/build-logo.py`, ~21 KB, is the only one left) or the page reaches 300 KB. The white square keeps the mark readable on the dark footer too (checked in both themes at 1280 and 390 px).

**Search snippet and link preview (01.10.2026).** After `<title>` the page carries `<meta name="description">` (the manifest's `description`, word for word), `<link rel="canonical">` and Open Graph tags (`og:title`, `og:description`, `og:url`, `og:image` = `https://customsassist.trade/assets/icons/icon-512.png`, 512×512; `twitter:card` = `summary`), so a link pasted into Telegram or WhatsApp, or a search result, shows the name, a line of text and the icon instead of a bare address. Only the login screen is public, so the tags describe the service, never a user. `og:image` has to be an absolute URL; `static-assets.test.js` resolves absolute links to the site's own files as well, so renaming the icon fails the test instead of silently breaking previews. A dedicated preview picture (1200×630 for a large card) would go to `assets/` like any other image. There is no `robots.txt`: `/robots.txt` falls through to the page, which crawlers read as «no rules».

**Accessibility is measured, not assumed (01.10.2026).** axe-core 4.13 (WCAG 2.0/2.1 A and AA plus best-practice rules) was run on the live site — login, register, forgot, search (empty and with a result), calculator, classifier, assistant and the administrators' panel, at 1280 and 390 px, light and dark. Result: **no serious or critical violation anywhere, contrast included, in both themes** (the palette audit of 24.09 holds), and also none against WCAG 2.2 AA at 390 px (target size). Three moderate findings, all structural, all fixed in markup without any visual change: no `main` landmark (`role="main"` on `.main-col` and on `#authScreen`), the sidebar is not announced as navigation (`role="navigation" aria-label="Основное меню"`; `<header>`, `<footer>`, `#tabBar` were already landmarks), and no level-one heading (a visually hidden `<h1 class="sr-only">` in the header, which the global `h1` rule cannot show because `.sr-only` clips it). The h1 made existing `<h3>` titles skip a level, so the seven `<h3>` in `checker.js` (assistant greeting, admin sections, modal titles) carry `aria-level="2"` — **not** `<h2>`: `.modal h2` and the UA default would change their look. `a11y.test.js` holds all this (32 view × width × theme combinations; mutation-checked by hand: removing `role="main"` fails it with `landmark-one-main` and `region`). It does not replace a pass with a real screen reader, keyboard-only use, 200 % zoom and reduced motion — none of which has been done.

**Keyboard use (04.10.2026).** Everything that opens on a click now opens from the keyboard. Before, the rows of the name-search list (`.usir-row`), the ETT rows (`.ett-row`, also in the classifier), the breadcrumb spans of the tree, the calculator's code picks, the headers of the collapsible cards (`.rh`) and the header of the folded «справочно» section were `div`/`span`/`h2` with a mouse handler: Tab skipped them, Enter did nothing, a screen reader did not announce them as controls — and axe-core does not see this (it knows nothing about handlers), so the accessibility test stayed green. Now these elements carry `role="button" tabindex="0"` (the markup is in the `base.js` templates and in `checker.js`); the **card header is a button with `aria-expanded`**, kept in step with the `open` class by `setCardOpen()` (also used by «развернуть все» and by the verdict chips, `focusResultCard`); the section header is a **real `<button class="res-sec-btn">` inside the `h2`** (the heading stays a heading) with `aria-expanded`, switched by `toggleResSec()` and `focusResultSec()`; **one `keydown` handler in `initApp`** presses any `[role=button][tabindex]` that is not a button, link or field on Enter and Space (Space is `preventDefault`ed so the page does not scroll); the 📖 notes icon inside a row is mouse-only (`aria-hidden`), so that no button sits inside another one (axe `nested-interactive`); the chevron is `aria-hidden`. **A new clickable `div`/`span` must get the same two attributes in the same edit**: `tests/keyboard.test.js` walks the real page (Tab from the search field reaches a list row, Enter and Space open the code and Space does not scroll, cards and the section report `aria-expanded`, the tree and the calculator picks work) and audits every `[onclick]` that is not a button, link or field on six views; nineteen mutations of it (keyboard, motion and reflow) are caught. Found on the way and fixed: **Enter in the calculator and species modes only cancelled the pending 250 ms search** (a pasted code followed quickly by Enter showed nothing — now Enter runs the search at once in every mode); and **the highlighted row of the classifier in the dark theme had contrast 3.2 and 3.5** (its code and rate on the olive highlight; `a11y.test.js` now also scans the name list, a position with its rows, and a classifier group) — `.notes-hl .ec,.notes-hl .er{color:var(--text)}`. **Reduced motion (04.10.2026).** Before, only the assistant's greeting, the theme switch and the login screen honoured `prefers-reduced-motion`; the folding of cards, the suggestion list, the loading indicators and the dialogs always moved. Now one rule in the page (`*,*::before,*::after` → `animation-duration:.01ms`, `transition-duration:.01ms`, one iteration, `scroll-behavior:auto`, all `!important`; not zero, so `animationend` and `transitionend` still fire) and `smoothOrAuto()` in `checker.js` for the eight smooth scrolls (`scrollIntoView`, `scrollTo` — the CSS rule does not reach an explicit `behavior:'smooth'`). **Reflow (WCAG 1.4.10):** measured at 320 CSS px on ten views in both themes — no horizontal scroll anywhere; `a11y.test.js` now runs a 320 px pass and fails on any overflow. Still not done: the 📖 icon in a row for the keyboard (the notes are one step away on the code card), the administrators' mail rows (`tr.onclick`), and a pass with a real screen reader.

**What opening the app costs, and what must not be asked for at start (01.10.2026).** Traced on the live site with a one-off session (Playwright, cache off, CDP `Network.emulateNetworkConditions` for «slow 4G» — 1.6 Mbit/s, 150 ms RTT; phone width 390 px): the page (66 KB gzip), `/api/auth/me` and `/api/auth/config` in parallel, then `/api/checker.js` (≈95 KB gzip, only after `me` — it needs the session), then the first `/api/engine` calls. On a fast line the app is visible after ~0.95 s and the first code search is drawn after ~1.5 s; on slow 4G after 2.2 s and 3.1 s. The trace found two things that nobody had asked for yet, both removed: the **Cloudflare captcha script** (85 KB, behind a 302) fetched on every page open although a logged-in user sees no captcha (now started by `showAuthView` for the login/register/forgot views — `docs/security-auth.md`, «Captcha»), and the **«Актуальность баз» table** (`sourceAuditHtml`, 249 KB of HTML, ≈40 KB gzip) requested at start although the sidebar panel is collapsed (now `sourceAuditSum` — a few bytes for the summary line — at start, and the table on the first opening of the `<details>`). The rule: **at start request only what the first screen shows**; a collapsed panel, a hidden mode or a modal loads on first use. Still loaded at start and cheap: `autoBrands` (car calculator), `/api/nbkr-rates`. Known and left: the login screen's background and logo (≈80 KB, light theme) load while the session is being checked, because `#authScreen` is the visible default; hiding them for a returning user needs a «had a session» hint in storage, which would be one more key to name in the policy. `engine-browser.test.js` holds the audit table's laziness, `turnstile-lazy.test.js` the captcha's.

**A palette swap re-runs the audit in both themes.** The light theme was born with 147 contrast failures that the dark one never had, all from colours written as values rather than tokens — three quick-search chip colours set through `style.cssText` in JS. They are `var(--cyan)`, `var(--orange)`, `var(--pink)` now. Both themes report zero across ten scenarios.

**The audit has one blind spot worth knowing: gradients.** `getComputedStyle().backgroundColor` is transparent for an element painted with `linear-gradient`, so the checker walked up to the parent and reported white-on-indigo buttons as 1.05:1 — a false alarm that would have sent you chasing a non-existent defect. It now skips any element whose nearest painted background is a gradient. Prefer a solid `background-color` under text you want audited.

**Check contrast mechanically, not by eye.** The harness that made this safe opens the file over `file://`, injects a fake `currentUser` and calls `showApp()`+`initApp()` — that renders the whole interior without a backend — then walks every element with direct text, composites the effective background through transparent ancestors, and reports anything under the WCAG threshold (4.5:1, or 3:1 for large/bold). It found exactly five real defects across the search results and one more across the other seven pages, all of which would have been easy to miss by eye: a `#3b5070` hint colour at 2.07:1, white-on-indigo buttons at 3.5:1 and a primary button at 2.64:1. All eight pages now report zero. Re-run it after any palette change.

## The phone is a first-class width, measured, not eyeballed

**The phone is a first-class width, not a fallback — and it is measured, not eyeballed.** The wrapper is a WebView over this same site, so a CSS change reaches every installed copy at the next deploy, with no store release; only `server.url` needs one. That makes the narrow layout worth the same care as the wide one. The audit on 12.09.2026 measured an iPhone 14 (390×844) and found the header occupying 153 px, the hero banner 136 px and the search field starting at y=345 — **46 % of the first screen spent before the thing the app is opened for.** The header was three right-aligned rows (theme switch, user bar, access status) stacked by desktop rules, which on a phone reads as a ragged left edge. It is now one wrapping flex row inside `header`, ordered by `order:` so the theme pill and the email share the top line and the access chip takes the second; the theme labels moved into `<span class="ts-txt">` so the words can be dropped and the emoji kept, exactly as `.auth-theme .at-txt` already does on the login screen. Search now starts at y=188.

Five rules from that pass generalise:

- **`viewport-fit=cover` or `env(safe-area-inset-*)` is always zero.** Without it the notch and the gesture bar cut into the page in a WebView, and nothing in a desktop browser ever shows you this.
- **Never put a text input below 16 px on iOS.** Safari zooms the page in when such a field takes focus and does not zoom back out. `.si` is 17 px on phones for that reason alone.
- **An absolutely positioned overlay must be measured against the element it overlays, not its wrapper.** `.sico` is `position:absolute` inside `.sw`, and `.sw` also held the field's `<label>` — so the button was offset by the label's height and hung over the input's top edge, at *every* width. The fix is structural: the label moved out of `.sw`, which now contains only the input and the button.
- **A right padding smaller than the overlay it clears is text running under a button.** The mobile rule had `padding-right:48px` under a 46 px button offset 8 px from the edge.
- **Check the tap targets with a script, not by eye.** Buttons measured 29 px; `.btn` is now 38 px on phones with 44 px for the standalone ones (Apple HIG and Material both ask 44–48, and 38 is a deliberate compromise for a reference app this dense — say so rather than pretending it meets the guideline). Links and chips get at least 32 px on phones from one `@media (max-width:640px)` block that sits **last** in the stylesheet, so no later rule can undo it (18.09.2026: «Забыли пароль?» and the breadcrumb were 16 px, the footer links 20, the verdict chips 24). Group a measurement per element, not per tag: grouping every classless `<a>` under one key hid the footer links behind the login link. Two things under 32 px are deliberate — the fields of the conditions row, whose 32 px pill is the target, and a link inside a line of text, which WCAG 2.5.8 exempts.

The horizontally scrolling badge strip keeps a `mask-image` fade on its right edge: it was scrollable all along with nothing to say so.

**`#appWrap` is its own stacking context, so an overlay for things inside it must live inside it (22.09.2026).** `.wrap{position:relative;z-index:1}` exists for the fixed background `#appWrap::before` (`z-index:-1`), and it means every `z-index` inside `#appWrap` — the «Ещё» menu (`.nav-panel`, 59), the tab bar (60), the terms window (`#termsGate`, 100) — counts only inside that layer, which sits at 1 in the page. The dimming layer of the «Ещё» menu was `body.nav-open::after` with `z-index:58` at the root, so it lay **above** the menu and the tab bar: after a tap on «Ещё» every tap on a phone landed on the dimming layer, nothing answered, and there was no way out but reloading the page (reported by the owner from an iPhone). It is now `body.nav-open #appWrap::after` — under the menu and the tab bar, over the content — and a tap on it closes the menu, as do «Ещё» again and Escape. The closing handler sits on `#appWrap`, not on `document`: iOS does not send `click` for a tap on an element without a handler on it or an ancestor below `body`. The same rule caught `#toTopBtn` (root, `z-index:50`) floating over the dimmed terms window; it is hidden while the window is shown. Elements meant to cover the whole app go to the root on purpose — `#authScreen` (50) and the modal (`.modal-backdrop` appended to `body`, 100). **Check a new overlay by hit-testing, not by eye**: `document.elementFromPoint` at the centre of each control that should be reachable must return that control; `checker-access.test.js` does this for the menu at 420 px, and a Playwright `click()` without `force` fails the same way («… intercepts pointer events»). The dashboard page (`server/dash/index.html`) copies this shell and carries the same fix.

## The back button: history entries without the URL (01.10.2026)

**A section, a mode and a code opened from a list are entries in the tab's history**, so the browser's Back and Forward — and the Back button of the Android wrapper, which used to leave the app on the first press — return to the previous section and the previous query. The module sits right after `updateNavActive()` in `checker.js`: `navPush()` at the end of `setPage` and `setSearchMode` (a nav button calls both — the push waits for a microtask, so one action is one entry), `navReplace()` after the debounced `render` of the search field (typing updates the current entry instead of adding one per letter, so Back from a code opened in a list returns to that list), and a `popstate` handler that closes the open menus and restores section, mode and query. **The URL never changes** (`pushState` without a URL): an address like `#q=8517…` would put the user's searches into the address bar and the browser's own history, which outlives logout on a shared computer — the same reason `ca-hist` is owner-tagged and removed in `doLogout()`. So there are no shareable links to a result; that was weighed and left out. **Entries carry the login's token** (`navToken`): `resetAppView()` calls `navReset()`, `showApp()` calls `navStart()` after `initApp()` — both through `typeof … === 'function'`, because they run in the page before `checker.js` exists — so after logout and another login in the same tab Back does not reopen the previous person's query (the entry is skipped silently). A repeat login in the same tab also returns the view to the code search: `initApp()` used to return early and leave the previous person's section on screen. Modals are not history entries: Back with a window open changes the page under it. `lookup-filter.test.js` (browser part) walks it: search → calculator → Back → the query → Forward; a word → a code from its list → Back → the list again; one nav click — one entry; the address stays `/`; logout and login — Back stays in the same document and opens nothing.
