The deployment order for the application files (six files together) is in [server/CHECKER.md](../server/CHECKER.md); the mobile wrapper is in [mobile.md](mobile.md); authentication, captcha and privacy are in [security-auth.md](security-auth.md).

## Backend (`server/`)

A small Express + PostgreSQL app providing session-based login and an admin API (`/api/auth/*`, `/api/admin/*`) for `tnved_checker.html`. See the plan at the time it was added for the full design rationale (RLS-equivalent access model, why sessions instead of JWT, CSRF approach, etc.) — this section just covers day-to-day commands.

**Local dev:**
```bash
cd server
npm install
cp .env.example .env   # fill in DATABASE_URL (a local Postgres) and SESSION_SECRET
psql "$DATABASE_URL" -f migrations/0001_init.sql
npm run create-admin -- you@example.com "some-password"   # one-off first admin
npm run dev
```
`server/src/index.js` exports `app` and only listens (and starts the class-decisions and НБКР background loads) under `require.main === module`, so `tests/api-boundary.test.js` drives the real middleware order — Origin check, session, the 15 MB `/api/assistant` body parsed only for a signed-in user, 400/413 instead of 500 for bad bodies — with the database and session store stubbed. It also serves the page itself so `http://localhost:3000/` works standalone for local testing without Nginx in front — but **only from an explicit list of public files plus the icons.** Pointing `express.static` at the repo root, as it did until 14.09.2026, would serve `server/private/checker.js` and every backup HTML next to it, which is exactly what the split was for.

**Exchange rates (`services/nbkrRates.js`, last-good copy on disk since 02.10.2026).** The daily rates come from `https://www.nbkr.kg/XML/daily.xml` (USD, EUR, CNY, RUB, KZT; refreshed hourly in memory; the calculator, the assistant and the dashboard read them). Every successful answer is also written to `server/var/nbkr-rates.json` (the state folder of the engine counters and the watcher's report; public data, no personal data). The file is read and written only by the service started through `init()` (as with the engine counters), never by tests or scripts that merely require the module — otherwise every test run with a real `getRates()` left `server/var/nbkr-rates.json` in the working tree (`server/var/` is in `.gitignore` now as well). It is only a fallback: a request is always made first, and the disk copy is taken when it fails (the site does not answer, HTTP 500, no USD/EUR in the file) **and memory is empty** — which is exactly the situation after a restart, i.e. after every deploy and every OS update. Before this, a restart during an nbkr.kg outage left the calculator and the assistant without rates until the site came back. The copy keeps the date of the NBKR rate («курс НБКР на 01.10.2026» in the calculation text), the dashboard tile says «из файла на диске: nbkr.kg не ответил» and shows the error, and the next successful hourly refresh replaces it. A damaged, foreign-version or incomplete file is ignored (no rates, as before). **Which day's rate is served (02.10.2026).** NBKR publishes tomorrow's rate in the evening — at 17:40 Bishkek time on 02.10.2026 `daily.xml` already said `Date="03.10.2026"`, and the `?date=` parameter is ignored — while customs takes the rate in force on the day the declaration is registered. So the service keeps the last ten rates it received (also in the file on disk, version 2 with `history`; a version-1 file is still read) and `getRates(forIso)` returns the one with the greatest date **not later than the wanted day** (default: today in Bishkek, decided at request time, so midnight needs no refresh). From the evening until midnight the calculators and the assistant therefore use today's rate, not tomorrow's; a first start in the evening, when yesterday's rate is not yet known, serves what exists (tomorrow's) rather than refusing. The dashboard tile shows the latest received date (`status().date`); the one in use is `status().effectiveDate`. `tests/nbkr-rates.test.js` covers both parts with the network and the clock replaced (mutations: selection off, history not filled).

**Silent failures are reported, not only drawn on the dashboard (`services/health.js`, 02.10.2026).** Every hour (the first pass two minutes after start) the API process checks what the dashboard already shows and the owner rarely opens: **disk** (less than 12 % free on `/`; on 02.10.2026 16 % was used), **the nightly database copy** (`tnved-db-backup.service` ended with anything but `success`, or the last exit is older than 36 hours, or the timer is not `active`), **the TLS certificates** of the site and the dashboard (fewer than 14 days left — Let's Encrypt renews at 30, so this means «renewal is not happening»), **the NBKR rate** (requests failing for more than 24 hours in a row — `nbkrRates.status().failingSince`; the copy on disk keeps the calculator working meanwhile, see above). One Telegram message per trouble per 24 hours while it lasts, then one «✅ Снова в порядке»; the messages carry machine and service state only, never user data. It reuses the dashboard collectors (`systemSection`, `systemdSection`, `certsSection`, exported from `routes/dash.js`), so a check cannot disagree with the tile. Not covered on purpose: the copy-pull to the owner's machine (it depends on that machine being on), the uptime of the site from outside (`.github/workflows/uptime.yml`), the provider balance of the assistant (its own alert in `routes/assistant.js`). `tests/health.test.js` has every threshold, the daily throttle, the recovery message and «one failing check does not silence the others», checked by mutation.

**Deploy (VPS):** install Node LTS + PostgreSQL, create the DB/role and apply `migrations/0001_init.sql`, deploy `server/` and run `npm ci --omit=dev`, run `create-first-admin.js` once, run the app under a systemd unit (`ExecStart=node server/src/index.js`, `EnvironmentFile=` pointing at a production `.env`), and put Nginx in front: serve `tnved_checker.html` as static content at `/`, reverse-proxy `location /api/ { proxy_pass http://127.0.0.1:3000; }`, and terminate TLS there (Let's Encrypt via `certbot --nginx`, which needs a real domain pointed at the VPS — a bare IP can't get a cert).

## Addresses, origins and the neighbouring project

**Addresses (since 11.09.2026).** The only address is **`https://customsassist.trade`**; `www` 301-redirects to it, and both names are covered by one Let's Encrypt certificate. The temporary `65-109-170-170.sslip.io` was switched off the same day at the owner's explicit request, in the belief that the consequence was severe — that the app version in the stores pointed at that origin and could not load until its user installed 1.1. **On 12.09.2026 that belief was checked and did not hold:** `kg.tnved.checker` returns 404 from the Google Play listing endpoint and 0 results from the iTunes lookup API, while a control request for `com.whatsapp` returns 200 — so there is no public production release in either store, and switching the origin off stranded nobody. What this does *not* rule out is a Play Console draft, a closed/internal test track or a TestFlight build, none of which appear in those public endpoints; only the consoles themselves settle that. Its Nginx block and certificate are gone; what remains is a default server that answers HTTP with a 301 to the canonical address and rejects the TLS handshake on HTTPS, so a stale bookmark still lands somewhere sensible and nobody is served a certificate for the wrong name.

`APP_ORIGIN` therefore holds a single value again, but `server/src/index.js` still **parses it as a comma-separated list** — keep that, it is what makes the next origin move survivable. Note the matching trap it created once: `routes/auth.js` builds the password-reset link, and a list cannot be pasted into a URL, so the canonical address for links comes from `publicOrigin()` (explicit `PUBLIC_ORIGIN`, else the first entry). The CSRF check stays fail-closed: no `Origin` header and an unlisted one both get 403 — including `https://www.customsassist.trade`, which is fine precisely because www never serves the page, it redirects first.

The same domain also fronts a **different project on a different server**: `ts.customsassist.trade` → 167.233.142.113 is «Учёт транспортных средств», an Nginx + Gunicorn/Django app in its own repo, reached over SSH with the `id_ed25519_checkts` key. Two things about it are worth knowing before touching that host: Django answers **400 DisallowedHost** for any hostname missing from `ALLOWED_HOSTS`, so a new name needs `ALLOWED_HOSTS` *and* `CSRF_TRUSTED_ORIGINS` in `/opt/checkts/.env` plus `systemctl restart checkts`; and its catch-all `:80` block redirects everything to the old sslip.io name, so a new domain needs its own `:80` block or it loses its hostname on the first request. The zone file and the whole move are documented in [dns/](../dns/).

## The administrators' dashboard: `dash.customsassist.trade` (22.09.2026)

The monitoring dashboard is the same Node process and the same PostgreSQL behind a second Nginx `server` block (`server/nginx.conf`, «dash.customsassist.trade»): `root /opt/tnved/server/dash`, `location = /` serves `index.html`, `/assets/` is an `alias` to the site's images, `/api/` is proxied as on the main host, everything else is 404. The main host never serves that directory because `/server/` is blocked there. What lives where:

- `server/dash/index.html` — the login screen and the shell, in the site's own look (the tokens, auth screen, header, left menu, cards and tab bar were copied from the page's `<style>` on 22.09.2026 — a restyle of the site is repeated here by hand). It holds no data and no dashboard code.
- `server/private/dash.js` — the dashboard interface, served only through `GET /api/dash.js` (`requireAdmin`) and executed as a blob, like `checker.js`.
- `server/src/routes/dash.js` — `GET /api/dash/data` (`requireAdmin`): one JSON with every section, each collected separately and failing separately (`{error}` in the section, never a 500 for the whole page). It reads the tables (`users`, `session`, `assistant_log`, `admin_audit_log`, the token tables), the in-memory counters of `/api/engine` (`routes/engine.js`, `usage`), `services/metrics.js` (request counters per route and status, the last 60 minutes, event-loop delay, the last 50 `console.error`/`console.warn` lines — all in process memory, reset by a restart; the contents of searches are never recorded, `privacy.html` promises that), `systemctl show` for `tnved.service`, `tnved-db-backup.service` and its timer (the backup directory is `postgres` 700 and the API cannot read it; the unit's `Result` and timestamps are enough), the site's own TLS certificate read by a TLS connection to its own name (the Let's Encrypt files are not readable by `tnved`; cached for an hour), `nbkrRates.status()`, `classDecisions.status()`, and the base through `services/base.js` (dated bans, antidumping, agreements in force, `SOURCE_AUDIT` — computed once per process, the base changes only by a deploy).
- `.env`: `DASH_ORIGIN=https://dash.customsassist.trade`. `index.js` adds it to the allowed origins, `services/turnstile.js` to the allowed hostnames, and `routes/auth.js` refuses a non-admin login on that host (`403 admin_only`, after the password, no session). The session cookie is host-only, so the dashboard has its own login; the session carries `dash:true` and `endUserSessions(…, 'replaced', …, {dash})` replaces sessions only within its own circle — logging into the dashboard does not log the administrator out of the site, and vice versa; disabling, deleting, an expired subscription and a password reset still end both.

**Publishing it took three things outside the repo, all done on 22.09.2026**: an `A` record `dash` → `65.109.170.170` in Cloudflare (DNS only, grey cloud — also in the zone file in `dns/`; only the owner's account can add it), `DASH_ORIGIN` in `/opt/tnved/server/.env` before the restart, and the certificate expanded to the new name. The certificate was expanded with **`certbot certonly --nginx --cert-name customsassist.trade -d customsassist.trade -d www.customsassist.trade -d dash.customsassist.trade --expand`** — `certonly`, so the nginx plugin only answers the HTTP-01 challenge and does not rewrite `sites-available/customsassist` (its hash was the same before and after; plain `certbot --nginx` would have edited the server blocks and made the installed config differ from the repo). The lineage keeps its name, so the `dash.*` block needed no change; `nginx -t && systemctl reload nginx` afterwards, and `certbot renew --cert-name customsassist.trade --dry-run` confirmed that auto-renewal covers the three names. Let's Encrypt answered «Service busy; retry later» to the first attempts; a retry after half a minute went through — run a `--dry-run` first either way. Before the record existed the block was reachable only from the server itself (`curl --resolve dash.customsassist.trade:443:127.0.0.1 -k https://dash.customsassist.trade/`). Deploy order: `nginx -t` and reload first, then `server/src/*`, `private/dash.js` and `dash/index.html` together with a restart (`services/base.js` changed: it exposes the base names the dashboard reads). Check from outside: `/api/dash.js` and `/api/dash/data` answer 401/403 without a session, a non-admin login on the dashboard host answers `403 admin_only`, and in a browser the seven sections render under the owner's account.

## Обращения: входящая почта через Cloudflare Email Worker (23.09.2026)

Письмо на адрес домена идёт так: Cloudflare Email Routing → Email Worker в аккаунте владельца → две вещи сразу, копия на почту владельца (`message.forward`) и сырое письмо потоком на `POST /api/mail/inbound`. Исходник Worker лежит в репозитории (`server/cloudflare/inbound-email.js`), но публикуется вручную в панели Cloudflare: Workers and Pages → Create → вставить код → Deploy, затем Email Routing → правило адреса → Send to a Worker. Переменные Worker: `FALLBACK_TO` (подтверждённый адрес назначения), `INBOUND_URL`, `INBOUND_SECRET`; без секрета шаг с передачей на сервер пропускается, и Worker работает как обычная пересылка — поэтому его можно опубликовать до готовности серверной части, ничего не сломав.

**Письмо не разбирается в Worker намеренно**: на бесплатном тарифе у Worker 10 мс процессорного времени на вызов при письме до 25 МиБ, и документация Cloudflare прямо предупреждает, что сложный обработчик не справится. Потоковая передача — ввод-вывод, а не вычисления. Порядок «сначала пересылка, потом передача сервису» выбран так, чтобы письмо не пропало при недоступном сервере; если не вышло ни то, ни другое, Worker возвращает временный отказ, и почтовый сервер отправителя повторит доставку.

На стороне сервиса: `routes/mail.js` — единственный маршрут, принимающий данные без входа, поэтому он исключён из проверки Origin (`index.js`, `MAIL_INBOUND_PATH`), сверяет `MAIL_INBOUND_SECRET` сравнением постоянного времени, держит свой предел в сто писем в час и не трогает сессию; Nginx даёт этому пути `client_max_body_size 26m` вместо общего `1m`. Разбор — `services/mailparse.js`, свой, без зависимостей: кодированные слова RFC 2047, base64 и quoted-printable, charset через `TextDecoder` (windows-1251 в том числе), multipart любой вложенности, RFC 2231 в именах файлов. **Не сохраняются**: сырое письмо, HTML-часть (превращается в текст при разборе, поэтому чужая разметка не попадает в админку) и содержимое вложений (остаются имя, тип и размер; сам файл — в копии, которую Worker переслал владельцу). Таблица `inbox` (миграция `0015`) хранит и входящие, и исходящие ответы одной лентой по `thread_key`; срок хранения — год, чистит `services/retention.js`. Ответ из админки уходит через Resend с адреса `MAIL_SUPPORT_FROM` (по умолчанию `info@`) с заголовками `In-Reply-To` и `References`, поэтому попадает в ту же переписку у получателя. Раздел «Обращения» есть и в админ-панели сайта, и на дашборде. Проверено живьём 23.09.2026: письмо с вложением прошло через Nginx в базу, ответ из админки дошёл до Gmail владельца. Тест — `tests/mail.test.js`.

**Сообщения с сайта (02.10.2026).** Кнопка «Сообщить о неточности» в результате поиска (`routes/feedback.js`, `POST /api/feedback`, вошедшему с подтверждённым адресом) кладёт сообщение в ту же таблицу `inbox` входящей строкой с `auth_results = 'site-form'` (поле для настоящих писем хранит результат SPF/DKIM и в админке не показывается — здесь оно служит пометкой, миграции не понадобилось): `from_email` — адрес учётной записи, `user_id` — она же, `message_id` — `<report-…@customsassist.trade>` (он же `thread_key`), `to_email` — адрес поддержки, тема «Неточность в базе: 8517 13 000 0 — <карточка>», в теле текст пользователя и под чертой код, карточка и условия поиска. Администраторы читают его в «Обращениях», как почту, и отвечают оттуда: `routes/admin.js` для таких строк пишет в письме «Это ответ на ваше сообщение о неточности, отправленное из сервиса» вместо «ваше письмо на адрес…». В Telegram приходит обычное «📬 Новое обращение» — кто и тема, без текста. Заслон по таблице, поэтому он переживает перезапуск: 3 сообщения в час и 10 в сутки на пользователя; то же сообщение за сутки второй раз не пишется. Срок хранения — год (`purge_after`), как у писем; назван в `privacy.html` («Письма в службу поддержки»).

**IPv6 на VPS прописан, но не работает, и это ломало исходящие вызовы (23.09.2026).** `ip -6 route show default` даёт `default via fe80::1 dev eth0`, а `curl -6 https://api.resend.com/` не проходит. Node с версии 18 соединяется в том порядке, в каком отвечает DNS, и для имён за Cloudflare первым приходит AAAA: запрос висит до таймаута и падает с `UND_ERR_CONNECT_TIMEOUT`. Из-за этого через раз не уходили письма Resend (подтверждение адреса, сброс пароля, письма администраторам, ответы на обращения) и срывались вызовы модели, Vision, Document AI, НБКР и справочника классрешений. **`curl` эту причину маскирует**: он сам откатывается на IPv4, поэтому проверка curl'ом показывает 200, пока Node падает — диагностировать надо `node -e "fetch(...)"`, а не curl. Лечится строкой `require('node:dns').setDefaultResultOrder('ipv4first')`: она стоит в `src/index.js` (покрывает всю службу) и в `scripts/alert-admins.js` и `scripts/refresh-class-decisions.js` — эти два запускаются отдельным процессом и `index.js` не читают. **Сам IPv6 на машине исправен, сломан только маршрут до Resend (проверено 23.09.2026).** Глобальный адрес есть, `ping6` до `2606:4700:4700::1111` отвечает за 2 мс, `google.com` и `one.one.one.one` по IPv6 дают 200 за десятки миллисекунд, а TCP до `api.resend.com` по IPv6 не устанавливается вовсе; по IPv4 тот же адрес отвечает за 0,03 с. Значит дело на стороне Resend или Hetzner, а не в настройке машины. **Выключать IPv6 на сервере нельзя**: Nginx слушает на нём (пять строк `listen [::]` в конфигурации, четыре открытых сокета), и после `sysctl` он не запустится, пока конфигурацию не поправить.

Системная подстраховка сделана в `/etc/gai.conf` (файл вне репозитория, как `sshd_config.d` и автоперезагрузка; резервная копия — `/root/deploy_backups/*_gai/`): строка `precedence ::ffff:0:0/96 100` делает IPv4 предпочтительным для `getaddrinfo`, то есть для всех программ. Проверено: `getent ahosts` отдаёт IPv4 первыми, и Node с настройкой по умолчанию (`verbatim`) после этого доходит до Resend. **`curl` на этой машине собран с AsynchDNS (c-ares) и `gai.conf` игнорирует**: он по-прежнему первым пробует IPv6 и висит, поэтому для проверок с сервера нужен `curl -4`. Это и есть источник путаницы: `curl` без флага показывает одно, Node — другое. Правило: диагностировать исходящие вызовы `node -e "fetch(...)"`, а не curl. Обход в коде оставлен и после `gai.conf`: он переживёт переезд на другую машину. **Новый сетевой скрипт получает эту же строку.**

## Оплата подписки по QR: xPay (24.09.2026, в тестовой среде)

Платёжная организация xPay (xpay.kg, лицензии НБКР № 2037251023 и № 3039251023 от 25.10.2023) выставляет динамический QR по ELQR, который оплачивается из приложения любого банка КР. Условия владельцу (переписка 24.09.2026): подключение и абонентская плата — 0, комиссия 1% с проведённого платежа; деньги копятся на кошельке xPay и выводятся из личного кабинета lk.xpay.kg (на счёт в Айыл Банке — без комиссии за 1–2 минуты, на другой банк — межбанковским переводом, клиринг 25–70 сом); **возврата по QR протокол ELQR не знает** — только переводом на реквизиты клиента или наличными, вручную. Документация — developer.xpay.kg (закрыта паролем от xPay, версия 1.7 от 14.09.26).

API: вход `POST /api/v1/developer/login` (`client_id`/`client_secret` → Bearer-токен на 30 минут и список услуг с `uuid`), QR `POST /api/v1/developer/qr/get`, статус `GET /api/v1/developer/qr/dynamic/status/{qr_transaction_id}`; тест `https://devapi.xpay.kg` с общим тестовым аккаунтом из документации, оплата тестовых QR — на sandbox.xpay.kg; бой `https://api.xpay.kg`. **Проверено в тестовой среде 24.09.2026**: суммы — в тыйынах целым числом и при создании, и в статусе (пример `"240.00000000"` в документации устарел); `service_name` и `comments` длиннее 32 знаков дают 409 (в документации не сказано); `payable` — сумма за вычетом 1%; статус оплаченного QR — `COMPLETED`, в нём же поля `webhook_start/execute/status`. **Ответ xPay 24.09.2026:** webhook приходит с одного их IP, без подписи, ждёт **201** и при другом ответе повторяет 24 часа с растущим интервалом; в теле — `qr_transaction_id`, `service_id`, суммы, `pay_status` и в `comments` имя и ИНН плательщика («Sender:…») — поэтому тело не читается и не хранится. **QR бессрочен и принудительно не отменяется** — оплату блокирует только `check_url`. Возвратов ELQR не знает: только прямым переводом клиенту.

Устройство (`routes/pay.js`, `services/xpay.js`, миграция `0016_pay_orders.sql`): `POST /api/pay/create` считает сумму по `PLANS` из `routes/assistant.js` (сумма из браузера не читается), создаёт заказ и QR, тот же тариф и срок в течение получаса отдают тот же QR, не больше шести заказов в час. `GET /api/pay/plans` отдаёт тариф, цену **и лимиты** (`day`, `month`, `pages`): окно оплаты показывает их до оплаты, как обещает п. 4.1 правил. Оплату засчитывает только `settle()`: сама спрашивает статус у xPay и засчитывает `COMPLETED` с суммой ровно как в заказе, переводя заказ из `waiting` один раз (`update … where status = 'waiting' returning`), затем пишет строку в `payments` (`method` «xPay QR», в `note` номер операции и зачисленная сумма) и продлевает подписку той же `extendedUntil()`, что и ручная запись. Другая сумма — `mismatch` и строка в журнале, `ERROR`/`CANCELED` — `failed`. `settle()` будят три пути: webhook `POST /api/pay/callback?o=<заказ>` (без входа, исключён из проверки Origin как `/api/mail/inbound`, не чаще раза в 2 с на заказ; отвечает 201, а если xPay не ответил на запрос статуса — 502, чтобы xPay повторил), опрос окна оплаты раз в 3 с (`GET /api/pay/status/:id`) и фоновая сверка незакрытых заказов двух последних суток раз в 5 минут. `check_url` (`/api/pay/check?o=<заказ>`, тоже без входа и Origin, любой метод) отвечает 201 только для последнего заказа пользователя, ждущего оплаты и созданного не больше часа назад, иначе 409: брошенный QR не оплатить через месяц по старой цене или после удаления заказа, два QR одного человека подряд — тоже. Webhook и `check_url` передаются xPay, только когда `publicOrigin()` — https: до локального стенда xPay не достучится, а неотвеченный `check_url` запретил бы оплату. Картинка QR отдаётся через `GET /api/pay/qr/:id` только владельцу заказа: CSP пускает картинки лишь со своего origin, а имя картинок xPay в бою заранее не известно.

Истёкшая подписка: вход с верным паролем по-прежнему отвечает 403 `subscription_expired`, но при включённой оплате пересоздаёт сессию с `payUserId` на час и `canPay:true` — `userId` в ней нет, поэтому остальной сайт видит гостя; с ней открыты только маршруты `/api/pay/*`. Окно оплаты — в самой странице (`openPay`, `#payGate`), потому что `checker.js` в этот момент не загружен; после оплаты человек нажимает «Войти» ещё раз (пароль остался в поле). Вошедшему — «Продлить подписку» в меню аккаунта, если `payEnabled` в ответе на вход и `/api/auth/me`. Без `XPAY_CLIENT_ID` всё выключено и вход с истёкшей подпиской — как раньше. Заказы удаляются через 90 дней (`services/retention.js`); xPay названа в `privacy.html`. Тест — `tests/pay.test.js` (с `PLAYWRIGHT_MODULE` — и браузер: экран входа, меню, 390 px).

## Deploying a change to the page alone

**Deploying a change to `tnved_checker.html` alone** (no `server/` change): back up the current file on the VPS, `scp` the new one to `tnved_checker.html.new`, compare its md5 with the local file, check the syntax of the page's first bare `<script>` **on the server** with `new vm.Script(...)`, exactly as `checker-access.test.js` does (not only locally — that is what catches a corrupted transfer; the application code itself is `server/private/checker.js` and is deployed by the order in `server/CHECKER.md`), then `mv` it into place and `chown tnved:tnved`. Nginx serves this file as static content, so **no `systemctl restart tnved`** — the restart is only for `server/`. Verify by `curl`ing the site and checking that the served bytes have the same md5 and contain the new text. Editing the file without this step does not count as finished work: a fix once sat in the repo for a session while the user was looking at the old page.

**Images are deployed as the folder `assets/`** into `/opt/tnved/assets/` (owner `tnved`, files 644), never as loose files at the root. `assets/source/` is not deployed at all: those are the owner's full-size originals, the input of `tools/build-logo.py` and `tools/split-app-bg.py`, and Nginx answers 404 for that path in case it ever lands there. Two old addresses stay alive by `alias` and must not be removed: `/icons/*` (installed copies of the site and iOS keep it in their manifest and `apple-touch-icon`) and `/email-logo.jpg` (letters already delivered). A new image is uploaded **before** the page that references it.

Deploying `server/private/*.js` or anything under `server/src/` follows the order in [server/CHECKER.md](../server/CHECKER.md): backup outside the web root, `nginx -t`, the six files together, `systemctl restart tnved`, the page last; SHA256 and syntax checked **on the server** before and after; then 401 without a session on `/api/checker.js` and `/api/engine`, 404 on `/server/private/base.js`, and a search by code in a browser. Every deploy in `session.md` records the backup directory (`/root/deploy_backups/<timestamp>/`) and the hashes — keep doing that.

**`bash tools/deploy.sh <commit> <label> <file>…` (02.10.2026)** does the mechanical part of the above for files of one commit: archive from git → stage on the server → SHA256 and syntax **on the server** → the live files must equal the base (the commit's parent, or `DEPLOY_BASE=<commit>` when several commits are going out together or commits between deploys did not touch these files; otherwise it stops — something undeployed is on the server) → copy of the old files to `/root/deploy_backups/<time>_<label>/` → `*.new` + `mv` (owner `tnved`) → `systemctl restart tnved` when anything under `server/` changed, with the journal and `/api/health` → the public pages last → SHA256 from outside. `DEPLOY_DRY=1` runs only the checks and changes nothing. Key and address: `DEPLOY_KEY`, `DEPLOY_HOST`, `DEPLOY_SITE` (defaults: the production ones, key `~/.ssh/id_ed25519_claude_vps`). It was a scratch file in `/tmp` through six deploys on 02.10.2026 and was moved here so that the scheduled night deploys do not depend on a temporary folder.

## Network exposure, backups and alerts

**Network exposure and backups (17.09.2026).** Node listens on `127.0.0.1` only: the port used to be bound on all interfaces with only UFW in front, and with `trust proxy` a direct request could forge `X-Forwarded-For` and walk past every per-IP limit. Nginx sends `Strict-Transport-Security: max-age=31536000` without `includeSubDomains` (`ts.customsassist.trade` is another server and another project). **`add_header` is not inherited by a `location` that has its own `add_header`**, so the header is repeated in `location = /` and `location = /tnved_checker.html`; check it on `/`, the page, the manifest and an `/api/` route after any config change. The database is dumped daily by `tnved-db-backup.timer` (`pg_dump -Fc`, 14 days, `/var/backups/tnved-db/`); the script's source is `server/tnved-db-backup.sh`, installed as `/usr/local/bin/tnved-db-backup.sh` — edit the repo copy and install it, not the other way round. **Every run restores its own dump** into a throwaway `tnved_restore_check` and compares the row counts of `users`, `admin_audit_log` and `assistant_log` with the live database (zero users or more than a hundred rows missing fails; more rows in the copy than live does not — deleting a user cascades to their `assistant_log`, and until 21.09.2026 that was a false alarm waiting for the first deletion at backup time), then drops it; the journal line reads `restore check ok: users=13/13 …`, and any failure fails the unit. **A failed unit mails the site's active admins**: `tnved-db-backup.service` and `tnved.service` carry a drop-in `alert.conf` with `OnFailure=tnved-alert@%n.service`, and the template `server/tnved-alert@.service` (installed in `/etc/systemd/system/`) runs `scripts/alert-admins.js <unit>` as `tnved` with `SupplementaryGroups=systemd-journal` — without that group `journalctl` shows `tnved` nothing of other units. The letter goes through the same Resend key and `renderEmail` template as the site's mail and carries the last 25 journal lines. For the API this fires only when `Restart=on-failure` gives up, not on every crash. `--dry-run` prints the recipient count without sending; the whole chain was proven on 17.09.2026 by a throwaway unit running `/bin/false` (deleted afterwards). Recipients come from the database, so with PostgreSQL down there is no letter — but then the site is down too. That the check can fail was proven, not assumed: a dump truncated to 6 KB is rejected by `pg_restore --exit-on-error`. **Off the server**, the Windows scheduled task `tnved-db-backup-pull` on the owner's machine copies every dump to `%USERPROFILE%\tnved-db-backups` at 12:00 (Bishkek time, after the 03:30 UTC dump) with `StartWhenAvailable`, so a day the machine was off is caught up at next boot. **The pull can fail silently, and did (23.09.2026): the task's `ExecutionTimeLimit` was `PT10M`, the 22.09 run was killed (`LastTaskResult` 267014, «terminated»), and that day's dump never left the server — nothing anywhere said so, and it surfaced only because the newest local copy looked a day old.** Three things make it visible now: the limit is `PT1H` (the copy itself takes about 25 s, so a generous limit only survives a machine that slept mid-run), the script appends a line to `%USERPROFILE%\tnved-db-backups\pull.log` (`<time> exit=<code> dumps=<n> newest=<file>` — **in Latin letters, because Windows PowerShell 5.1 reads a BOM-less `.ps1` as ANSI and mangles Cyrillic string literals**), and after a successful copy it writes the time into **`/var/lib/tnved/last-pull`** on the server, which the dashboard shows as the tile «Вывоз копий» (green under 30 h, amber under 72, red beyond). The marker lives in `/var/lib/tnved`, not next to the dumps: `/var/backups/tnved-db` is `700 postgres` and the API runs as `tnved`, so the first version got `EACCES` there. The task runs `server/pull-db-backups.ps1` from the repo, which keeps local copies **30 days** — the period `privacy.html` promises, together with 14 days on the server — and deletes old ones only when a copy younger than two days exists, so an unreachable server or a stopped dump timer never ages out the last copies there are. **A backup is storage of user data too:** the first version kept local copies forever, which contradicted the policy's right to deletion; a new copy location, retention period or recipient goes into `privacy.html` in the same commit. It uses the same root key the machine already holds for deploys, so it adds no new trust relationship.

**`location /` serves any file under `/opt/tnved`, so the config also denies by pattern (21.09.2026):** hidden files and directories (`/\.` except `/.well-known/`) and the extensions a stray file would have — `md sql sh ps1 env log bak old orig new dump gz tgz zip tar 7z` (`*.new` is the copy that sits next to its target during a deploy). The prefix blocks (`/server/`, `/backups/`, `/assets/source/`) stay. `tests/static-assets.test.js` compiles both expressions out of `nginx.conf` and checks that they close the samples and close **no real address of the site** — a lost backslash in `/\.` would match every path and take the site down, and that is exactly what happened to the first draft of this rule in a patch script.

## Монитор доступности, ошибки в браузере, вход администратора (01.10.2026)

**Why.** Every alert came from the server itself: with the VPS, Nginx or the API down nobody would know until a user said so; an error in a user's browser was seen only by that user (the registration button was broken 14–17.09.2026 and surfaced by word of mouth); an administrator logs in with a password alone.

**`GET /api/health`** (`src/index.js`, before the session middleware): 200 `{"ok":true}` when the base is parsed and PostgreSQL answers `select 1` within 3 s, otherwise 503 `{"ok":false}`; `Cache-Control: no-store`, no session, no versions or reasons. **The external monitor is a GitHub Actions workflow in this repository (01.10.2026), `.github/workflows/uptime.yml`** — chosen because it needs no new account and no copy of a secret: every 30 minutes (`7,37 * * * *`, GitHub may start it a few minutes late) a GitHub machine checks `/api/health` (200 and `"ok":true`), `/` (200 and the site's `<title>`) and the certificate (at least 14 days left), each up to three times 20 s apart. A failure opens an issue «🔴 customsassist.trade: …» — the repository owner gets the notification — and fails the run, so GitHub also mails whoever last changed the schedule in that file (the push came from the owner's account `customsassistkg-wq`); while that issue is open the runs stay green and add the state to it every six hours, so an outage gives one alert, not one every half hour; recovery comments and closes the issue. ## Schema and migrations

**Schema/migrations:** there's no migration framework — `migrations/*.sql` files are applied by hand with `psql -f`, in order, once each. Add new migrations as new numbered files rather than editing an already-applied one.

Migrations applied in production as of 01.10.2026: `0001`–`0019` (`0019_totp.sql` applied 01.10.2026 08:10 UTC as `tnved_app` before the restart — `middleware/auth.js` reads `totp_enabled_at`; the statements were piped to `sudo -u postgres psql -d tnved -v ON_ERROR_STOP=1 -1` after `set role tnved_app;`; `0017_subscription_reminders.sql` and `0018_watched_codes.sql` applied 24.09.2026 17:50 UTC as `tnved_app` before the restart; `0016_pay_orders.sql` applied 24.09.2026 as `tnved_app` — `set role tnved_app;` before the file, so the table belongs to the app role like the others; `0012_terms_acceptance.sql` applied 18.09.2026, `0013_payments.sql` and `0014_retention.sql` applied 22.09.2026, all before the API restart — `0014` adds `admin_audit_log.purge_after`, which the delete route writes and `services/retention.js` reads at start; it was first run on a copy restored from the nightly dump). A new column read by `middleware/auth.js` is deployed by migration **before** the restart, or every request fails.

**Rebuilding the schema from the repository — rehearsed (02.10.2026): `tools/db-rehearsal.mjs` + `tools/schema-probe.sql`.** The script starts a throw-away PostgreSQL 18 (the `embedded-postgres` package downloads its own binaries into a temp folder; nothing is installed, no user data can be there), applies `migrations/0001`–`0019` in order, takes the structure with the same catalog query that is run on the production database (columns, constraints, indexes, extensions, triggers — structure only) and runs `server/tests/reset-password.test.js` against that database. Result on 02.10.2026: all 19 migrations apply from scratch without errors; the structure equals production line for line (123 columns, 117 constraints, 30 indexes, 2 extensions, no triggers) **except the table `session`**, which the server creates itself at start (`connect-pg-simple`, `createTableIfMissing`, `index.js`) and which therefore is in no migration — a database restored from `pg_dump` has it, a database rebuilt from migrations gets it at the first start. So there is no hand-made change on the server that the migrations do not explain; repeat the comparison before a big migration or after any manual work in `psql` (commands are in the header of `tools/db-rehearsal.mjs`; the live structure is read over ssh with `tools/schema-probe.sql`). This covers the schema only: a full machine rebuild (OS, Nginx, Node, systemd units, `.env`, certificates) was not rehearsed — it needs a second host.

**Money (migration `0013`, 22.09.2026).** `payments` — one row per payment recorded by an administrator (`POST /api/admin/payments`: user, amount, currency `KGS`, plan, months, `paid_until`, method, note; the email is snapshotted and `user_id` goes NULL on account deletion, so the ledger survives like the audit log); recording a payment sets `users.subscription_expires_at` to the end of `paid_until` (extended from the current expiry when it is still in the future, from today otherwise; month-end dates stay on the last day — `extendedUntil()`) and `ai_plan` to the paid plan; deleting a payment row does not touch the subscription. `expenses` — recurring costs (name, amount, currency, `month`/`year`/`once`, from/to dates), seeded with the server (≈ $10/month) and the domain (≈ $6/year) from the owner's words; edited in the admin panel («Оплаты и расходы»). The dashboard's «Экономика» section (`routes/dash.js`, `economySection`) puts them together per Bishkek month: payments, expected monthly revenue from the plans of the active paid subscriptions, API spend from `assistant_log` (model + Document AI at 3 cents per disputed page; Vision estimated as pages beyond the free 1 000 per month at $1.5 per 1 000 — it is not in the log), fixed costs converted at the НБКР rate, the margin, and a per-user «paid / cost» table. Two remotes, two purposes: push to both (`git push origin main && git push vps main`) — GitHub is the collaboration and CI remote, the VPS mirror is the backup that survives a GitHub outage or a lost account.

**SSH to GitHub uses its own key, deliberately.** For the owner's account it is `~/.ssh/id_ed25519_github_ca` (`SHA256:PSb/Hp/g…`), reached through the host alias `github-customsassist` in `~/.ssh/config`, so the working machine's other projects keep `github.com` with their own key; before 26.09.2026 it was `~/.ssh/id_ed25519_github` (`SHA256:c3YED5BB…`, account tshalabaev). Either is separate from `id_ed25519` (root on the Hetzner VPS) and `id_ed25519_checkts` (root on 167.233.142.113), and `~/.ssh/config` pins github.com to it with `IdentitiesOnly yes`. Reusing a server deploy key for the account would make one stolen file both a root shell and a GitHub login. Note what the two credentials can and cannot do: the SSH key reaches repositories that already exist but cannot create one — `git push` to a missing repo answers `Repository not found`, GitHub has no push-to-create. Creating a repository needs the `gh` API token, which is a separate login (`gh auth login --web` prints a one-time code for https://github.com/login/device; the code expires in about 15 minutes, so restart the flow rather than re-offering a stale one).

Commit only when the owner asks; push to both remotes (`git push origin main && git push vps main`). Before committing in a working tree that another session may also be editing, compare `git diff --numstat` with what you actually changed (see «Two processes in one working tree» in `CLAUDE.md`).
