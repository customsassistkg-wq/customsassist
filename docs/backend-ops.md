# Backend operations: server, deploy, Nginx, VPS, database, mail, git remotes

Moved out of `CLAUDE.md` on 20.09.2026 without changing the text of the paragraphs (headings added). **Read before deployment, server configuration, Nginx, DB operations, migrations, mail, DNS or any production change**, and before touching the git remotes or SSH keys. The deployment order for the application files (six files together) is in [server/CHECKER.md](../server/CHECKER.md); the mobile wrapper is in [mobile.md](mobile.md); authentication, captcha and privacy are in [security-auth.md](security-auth.md).

## Backend (`server/`)

A small Express + PostgreSQL app providing session-based login and an admin API (`/api/auth/*`, `/api/admin/*`) for `tnved_checker.html`. See the plan at the time it was added for the full design rationale (RLS-equivalent access model, why sessions instead of JWT, CSRF approach, etc.) — this section just covers day-to-day commands.

**Local dev:**
```bash
cd server
npm install
cp .env.example .env   # fill in DATABASE_URL (a local Postgres) and SESSION_SECRET
psql "$DATABASE_URL" -f migrations/0001_init.sql
npm run create-admin -- you@example.com "some-password"   # one-off first admin
npm run dev
```
`server/src/index.js` exports `app` and only listens (and starts the class-decisions and НБКР background loads) under `require.main === module`, so `tests/api-boundary.test.js` drives the real middleware order — Origin check, session, the 15 MB `/api/assistant` body parsed only for a signed-in user, 400/413 instead of 500 for bad bodies — with the database and session store stubbed. It also serves the page itself so `http://localhost:3000/` works standalone for local testing without Nginx in front — but **only from an explicit list of public files plus the icons.** Pointing `express.static` at the repo root, as it did until 14.09.2026, would serve `server/private/checker.js` and every backup HTML next to it, which is exactly what the split was for.

**Deploy (VPS):** install Node LTS + PostgreSQL, create the DB/role and apply `migrations/0001_init.sql`, deploy `server/` and run `npm ci --omit=dev`, run `create-first-admin.js` once, run the app under a systemd unit (`ExecStart=node server/src/index.js`, `EnvironmentFile=` pointing at a production `.env`), and put Nginx in front: serve `tnved_checker.html` as static content at `/`, reverse-proxy `location /api/ { proxy_pass http://127.0.0.1:3000; }`, and terminate TLS there (Let's Encrypt via `certbot --nginx`, which needs a real domain pointed at the VPS — a bare IP can't get a cert).

## Addresses, origins and the neighbouring project

**Addresses (since 11.09.2026).** The only address is **`https://customsassist.trade`**; `www` 301-redirects to it, and both names are covered by one Let's Encrypt certificate. The temporary `65-109-170-170.sslip.io` was switched off the same day at the owner's explicit request, in the belief that the consequence was severe — that the app version in the stores pointed at that origin and could not load until its user installed 1.1. **On 12.09.2026 that belief was checked and did not hold:** `kg.tnved.checker` returns 404 from the Google Play listing endpoint and 0 results from the iTunes lookup API, while a control request for `com.whatsapp` returns 200 — so there is no public production release in either store, and switching the origin off stranded nobody. What this does *not* rule out is a Play Console draft, a closed/internal test track or a TestFlight build, none of which appear in those public endpoints; only the consoles themselves settle that. Its Nginx block and certificate are gone; what remains is a default server that answers HTTP with a 301 to the canonical address and rejects the TLS handshake on HTTPS, so a stale bookmark still lands somewhere sensible and nobody is served a certificate for the wrong name.

`APP_ORIGIN` therefore holds a single value again, but `server/src/index.js` still **parses it as a comma-separated list** — keep that, it is what makes the next origin move survivable. Note the matching trap it created once: `routes/auth.js` builds the password-reset link, and a list cannot be pasted into a URL, so the canonical address for links comes from `publicOrigin()` (explicit `PUBLIC_ORIGIN`, else the first entry). The CSRF check stays fail-closed: no `Origin` header and an unlisted one both get 403 — including `https://www.customsassist.trade`, which is fine precisely because www never serves the page, it redirects first.

The same domain also fronts a **different project on a different server**: `ts.customsassist.trade` → 167.233.142.113 is «Учёт транспортных средств», an Nginx + Gunicorn/Django app in its own repo, reached over SSH with the `id_ed25519_checkts` key. Two things about it are worth knowing before touching that host: Django answers **400 DisallowedHost** for any hostname missing from `ALLOWED_HOSTS`, so a new name needs `ALLOWED_HOSTS` *and* `CSRF_TRUSTED_ORIGINS` in `/opt/checkts/.env` plus `systemctl restart checkts`; and its catch-all `:80` block redirects everything to the old sslip.io name, so a new domain needs its own `:80` block or it loses its hostname on the first request. The zone file and the whole move are documented in [dns/](../dns/).

## Deploying a change to the page alone

**Deploying a change to `tnved_checker.html` alone** (no `server/` change): back up the current file on the VPS, `scp` the new one to `tnved_checker.html.new`, compare its md5 with the local file, check the syntax of the page's first bare `<script>` **on the server** with `new vm.Script(...)`, exactly as `checker-access.test.js` does (not only locally — that is what catches a corrupted transfer; the application code itself is `server/private/checker.js` and is deployed by the order in `server/CHECKER.md`), then `mv` it into place and `chown tnved:tnved`. Nginx serves this file as static content, so **no `systemctl restart tnved`** — the restart is only for `server/`. Verify by `curl`ing the site and checking that the served bytes have the same md5 and contain the new text. Editing the file without this step does not count as finished work: a fix once sat in the repo for a session while the user was looking at the old page.

**Images are deployed as the folder `assets/`** into `/opt/tnved/assets/` (owner `tnved`, files 644), never as loose files at the root. `assets/source/` is not deployed at all: those are the owner's full-size originals, the input of `tools/build-logo.py` and `tools/split-app-bg.py`, and Nginx answers 404 for that path in case it ever lands there. Two old addresses stay alive by `alias` and must not be removed: `/icons/*` (installed copies of the site and iOS keep it in their manifest and `apple-touch-icon`) and `/email-logo.jpg` (letters already delivered). A new image is uploaded **before** the page that references it.

Deploying `server/private/*.js` or anything under `server/src/` follows the order in [server/CHECKER.md](../server/CHECKER.md): backup outside the web root, `nginx -t`, the six files together, `systemctl restart tnved`, the page last; SHA256 and syntax checked **on the server** before and after; then 401 without a session on `/api/checker.js` and `/api/engine`, 404 on `/server/private/base.js`, and a search by code in a browser. Every deploy in `session.md` records the backup directory (`/root/deploy_backups/<timestamp>/`) and the hashes — keep doing that.

## Mail

**Mail: one branded template, and the brand is «Customs Assist KG».** `services/email.js` exports `renderEmail({title, intro, actionUrl, actionText, outro, footNote})` — a table-and-inline-styles layout, because mail clients strip `<style>` and do not do flex or grid. Both letters (verify address, reset password) go through it, so a change lands in one place. Three rules baked into it: the logo is linked from `https://customsassist.trade/assets/email-logo.jpg` (moved there on 20.09.2026; the old `/email-logo.jpg` stays served by an Nginx `alias`, because letters already in inboxes point at it) (Nginx serves any file in `/opt/tnved`, and it is a **JPEG** — WebP is still not safe in mail), the brand name is printed as text under the logo because Gmail and Outlook block remote images by default, and the action URL is repeated as selectable plain text under the button in case a client mangles the link.

## Contact address

**The contact address is `info@customsassist.trade` (since 18.09.2026, evening).** It is routed by Cloudflare Email Routing in the owner's account (MX `route1–3.mx.cloudflare.net`, root SPF `include:_spf.mx.cloudflare.net` — no clash with Resend, which sends through the `send.` subdomain and DKIM) to the owner's mailbox, and it appears in the footer, `terms.html`, `privacy.html` and the `contact` field of `ai-risk.json`; the policy names Email Routing as the receiver of those letters — a new mail path is a new recipient. The way there is the lesson. The footer first showed `info@customsassist.org`, a domain that does not exist (NXDOMAIN), so every complaint and data request bounced. Then the site was switched to `info@customsassist.trade` as soon as its MX records appeared — and all three MX answered `RCPT TO` with `550 5.1.1 Address does not exist`, the same as for a random address, because the rule was not active yet (an unconfirmed destination, the usual cause); the site went back to `tshalabaev@gmail.com` within the hour and a Resend test letter bounced. After the owner fixed the rule in Cloudflare, all three MX answered `250 2.1.0 Ok` for `info@` while a random address still got 550 — that pair is the proof. **MX records prove only that routing is on for the zone, not that an address is routed.** Before publishing or changing a mail address, run `node tools/smtp-probe.js route1.mx.cloudflare.net <address>` (and a random address for contrast) from the working machine — Hetzner blocks outbound port 25, the VPS cannot reach any MX; the probe stops before DATA, so no letter is sent. Cloudflare confirms with `250 2.1.0`, not `250 2.1.5`. **The server's Resend key can only send** (`restricted_api_key` on `GET /emails/<id>`), so the API never shows a bounce. Loading `.env` with `set -a; . ./.env` breaks on `RESEND_FROM_EMAIL=Name <addr>` and silently falls back to `onboarding@resend.dev`; run such scripts with `require('dotenv')` from inside `/opt/tnved/server`.

## Network exposure, backups and alerts

**Network exposure and backups (17.09.2026).** Node listens on `127.0.0.1` only: the port used to be bound on all interfaces with only UFW in front, and with `trust proxy` a direct request could forge `X-Forwarded-For` and walk past every per-IP limit. Nginx sends `Strict-Transport-Security: max-age=31536000` without `includeSubDomains` (`ts.customsassist.trade` is another server and another project). **`add_header` is not inherited by a `location` that has its own `add_header`**, so the header is repeated in `location = /` and `location = /tnved_checker.html`; check it on `/`, the page, the manifest and an `/api/` route after any config change. The database is dumped daily by `tnved-db-backup.timer` (`pg_dump -Fc`, 14 days, `/var/backups/tnved-db/`); the script's source is `server/tnved-db-backup.sh`, installed as `/usr/local/bin/tnved-db-backup.sh` — edit the repo copy and install it, not the other way round. **Every run restores its own dump** into a throwaway `tnved_restore_check` and compares the row counts of `users`, `admin_audit_log` and `assistant_log` with the live database (zero users or more than a hundred rows missing fails; more rows in the copy than live does not — deleting a user cascades to their `assistant_log`, and until 21.09.2026 that was a false alarm waiting for the first deletion at backup time), then drops it; the journal line reads `restore check ok: users=13/13 …`, and any failure fails the unit. **A failed unit mails the site's active admins**: `tnved-db-backup.service` and `tnved.service` carry a drop-in `alert.conf` with `OnFailure=tnved-alert@%n.service`, and the template `server/tnved-alert@.service` (installed in `/etc/systemd/system/`) runs `scripts/alert-admins.js <unit>` as `tnved` with `SupplementaryGroups=systemd-journal` — without that group `journalctl` shows `tnved` nothing of other units. The letter goes through the same Resend key and `renderEmail` template as the site's mail and carries the last 25 journal lines. For the API this fires only when `Restart=on-failure` gives up, not on every crash. `--dry-run` prints the recipient count without sending; the whole chain was proven on 17.09.2026 by a throwaway unit running `/bin/false` (deleted afterwards). Recipients come from the database, so with PostgreSQL down there is no letter — but then the site is down too. That the check can fail was proven, not assumed: a dump truncated to 6 KB is rejected by `pg_restore --exit-on-error`. **Off the server**, the Windows scheduled task `tnved-db-backup-pull` on the owner's machine copies every dump to `%USERPROFILE%\tnved-db-backups` at 12:00 (Bishkek time, after the 03:30 UTC dump) with `StartWhenAvailable`, so a day the machine was off is caught up at next boot. The task runs `server/pull-db-backups.ps1` from the repo, which keeps local copies **30 days** — the period `privacy.html` promises, together with 14 days on the server — and deletes old ones only when a copy younger than two days exists, so an unreachable server or a stopped dump timer never ages out the last copies there are. **A backup is storage of user data too:** the first version kept local copies forever, which contradicted the policy's right to deletion; a new copy location, retention period or recipient goes into `privacy.html` in the same commit. It uses the same root key the machine already holds for deploys, so it adds no new trust relationship.

**`location /` serves any file under `/opt/tnved`, so the config also denies by pattern (21.09.2026):** hidden files and directories (`/\.` except `/.well-known/`) and the extensions a stray file would have — `md sql sh ps1 env log bak old orig new dump gz tgz zip tar 7z` (`*.new` is the copy that sits next to its target during a deploy). The prefix blocks (`/server/`, `/backups/`, `/assets/source/`) stay. `tests/static-assets.test.js` compiles both expressions out of `nginx.conf` and checks that they close the samples and close **no real address of the site** — a lost backslash in `/\.` would match every path and take the site down, and that is exactly what happened to the first draft of this rule in a patch script.

## The VPS itself

**The VPS itself (17.09.2026).** SSH takes keys only — `/etc/ssh/sshd_config.d/10-hardening.conf` sets `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `X11Forwarding no`, `MaxAuthTries 3`. No account had a password, so nothing could log in that way, but the port was accepting the attempts; check `sshd -T` after any OpenSSH upgrade, because a drop-in file named later than `10-` or a cloud-init file could win. Security updates now reboot the machine themselves when a kernel or libc needs it, at 22:00 UTC = 04:00 in Bishkek (`/etc/apt/apt.conf.d/52-tnved-auto-reboot`, `Automatic-Reboot "true"`): before that the 7.0.0-31 kernel had been installed and waiting for 19 days. The first reboot was done by hand the same day at the owner's word («можешь перезагружать сколько хочешь»): every unit is enabled and the API was listening again 30 seconds after the command, so a nightly reboot costs about half a minute. Neither file lives in the repo — they are system configuration; recreate them from this paragraph on a new server.

## Schema and migrations

**Schema/migrations:** there's no migration framework — `migrations/*.sql` files are applied by hand with `psql -f`, in order, once each. Add new migrations as new numbered files rather than editing an already-applied one.

Migrations applied in production as of 19.09.2026: `0001`–`0012` (`0012_terms_acceptance.sql` applied 18.09.2026 before the API restart). A new column read by `middleware/auth.js` is deployed by migration **before** the restart, or every request fails.

## Git history, remotes and keys

- The rest of the repo is **source material**: official legal texts (`.md` files — tax code, Единый перечень, government resolutions, etc.) that get manually parsed and encoded into the app, and **`session.md`**, a running Russian-language changelog of what was done, why, and what's still unverified. `session.md` remains the narrative record of past work — why something was done and what is still unverified — so append to it when you make a substantive change. Since the review of 05.09.2026 the repo also has **real git history** (it previously had none): commit `eade5b8` preserves the working set as it had been staged, including 15 legal source `.md` files that by then existed only in the git index and not on disk. Those files are recoverable with `git checkout eade5b8 -- <path>` if they are ever needed again. Since 12.09.2026 there **is** a remote, and it is not GitHub: `vps` = `ssh://root@65.109.170.170/srv/git/tnved.git`, a bare repository on the same VPS that serves the site, mode 700 and outside Nginx's root (`/opt/tnved`), so it is unreachable from the web. `git push vps main` after a commit — 103 commits and 19.6 MiB at the time it was created. It exists because the history had no copy anywhere off the working machine; it is a backup and a rollback path, **not** a collaboration remote and not something Codemagic builds from. There is also `origin` = `git@github.com:tshalabaev/customsassist.git`, **private**, created the same day once the owner completed the device-code login; it carries the same history and is the remote Codemagic builds from. Two remotes, two purposes: push to both (`git push origin main && git push vps main`) — GitHub is the collaboration and CI remote, the VPS mirror is the backup that survives a GitHub outage or a lost account.

**SSH to GitHub uses its own key, deliberately.** `~/.ssh/id_ed25519_github` (`SHA256:c3YED5BB…`) is separate from `id_ed25519` (root on the Hetzner VPS) and `id_ed25519_checkts` (root on 167.233.142.113), and `~/.ssh/config` pins github.com to it with `IdentitiesOnly yes`. Reusing a server deploy key for the account would make one stolen file both a root shell and a GitHub login. Note what the two credentials can and cannot do: the SSH key reaches repositories that already exist but cannot create one — `git push` to a missing repo answers `Repository not found`, GitHub has no push-to-create. Creating a repository needs the `gh` API token, which is a separate login (`gh auth login --web` prints a one-time code for https://github.com/login/device; the code expires in about 15 minutes, so restart the flow rather than re-offering a stale one).

Commit only when the owner asks; push to both remotes (`git push origin main && git push vps main`). Before committing in a working tree that another session may also be editing, compare `git diff --numstat` with what you actually changed (see «Two processes in one working tree» in `CLAUDE.md`).
