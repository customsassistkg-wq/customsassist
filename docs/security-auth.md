## The login gate and the base on the server

**Since 14.09.2026 the login gate controls who can read the reference data, not only who can use the tool.** That is the opposite of what held before: while the databases sat inline in the page, "view source" handed them to anyone who opened the address. They now live in `server/private/checker.js`, which Nginx does not serve and the local Express serves only from an explicit public-file list — serving the whole repo root is no longer allowed. What the gate still cannot do is take data back: whatever a signed-in user has already received is in their browser, and a copy they saved stays theirs.

**Since 17.09.2026 a signed-in user no longer receives the base either.** Until then `/api/checker.js` carried every database, so any account — including a three-day trial registered with a real mailbox — could save the whole base in one request. The owner asked for exactly that to stop («чтобы никто не смог скачать мою базу»). The base now lives in `server/private/base.js`, which only the server executes (`server/src/services/base.js` runs it in one vm context with `checker.js`), and the browser asks for one answer at a time through `engine(fn, ...args)` → `POST /api/engine`. What this buys is honest to state: data shown to a user can always be copied by a user, so the goal is that copying the base means a long, visible enumeration tied to one account — `routes/engine.js` counts distinct heading positions, tree groups and name queries per account per Bishkek day, mails the active admins at 300 and refuses at 800 (`ENGINE_LIMITS`). **A new database follows the same split:** constant, `findX()` and card in `base.js`; anything the interface needs outside the cards goes through a new `ENGINE_API` entry that validates its own arguments, never through a direct reference from `checker.js`, which throws `ReferenceError` in the browser and only there. The split itself was mechanical (acorn over the syntax tree, 34 interface functions rewritten to `engine()`) and verified against the previous file: 2 079 `render` queries and 7 160 other answers identical byte for byte. Details, the reasoning behind the limits and the deployment order that must ship the six files together are in [server/CHECKER.md](../server/CHECKER.md).

**The limiter's key must be derived the way the base reads the query (21.09.2026).** `keysOf` counted a heading only for an all-digit query and keyed everything else by the first 60 characters of text, while every `findX()` and `calcCodeList` strip non-digits on their own: sixty dots in front of a code gave one key for all 1,228 headings of the ЕТТ (measured on the real `account()`: 0 refusals, 1 key, no alert mail — the tariff and preference cards came back, the ban and licence cards did not), and `calcCodeList('85.17')` returned the heading's code list with no key at all. The heading key is now the first four digits of the query's digits wherever they stand, next to the text key; typing a word that contains numbers is still one text position (`tests/engine.test.js`). **When a new `ENGINE_API` function takes a query, give it a `keysOf` case in the same commit and probe it with padded, dotted and mixed input** — a function missing from the `switch` is unmetered. Known and left as is: `treeChapter` opens a whole chapter per key (97 keys for the public ЕТТ tree), and one- to three-digit queries carry no key.

**The day's count survives a restart (01.10.2026).** The counters lived only in memory, so every restart of the API began the day again — and a restart is every deploy (twenty on 30.09.2026, 38 restarts in the two days before the fix): an account could open up to 800 headings between two deploys, the alert mail reset with it. `routes/engine.js` now writes them every five seconds and on SIGTERM to `server/var/engine-usage.json` and reads them at start (`init()` from `index.js`; tests and other `require`s never touch the file). What is written is the minimum the limit needs and nothing a search reveals: per account the call count, the alerts already sent and **HMAC tags of the keys** (key from `SESSION_SECRET`, 96 bits each) — no codes, no phrases; the raw text of the last query stays in memory only, for the «typing continues the word» rule. Mode 600, written through rename, yesterday's Bishkek day removed in the first seconds of the new one. Described in `privacy.html` («Чего мы не собираем»). Also fixed on the way: two rows of one heading in one request (`codeBundle` with 8517 13 and 8517 12) counted twice against the limit.

## The API boundary

`server/src/index.js` exports `app` and only listens (and starts the class-decisions and НБКР background loads) under `require.main === module`, so `tests/api-boundary.test.js` drives the real middleware order — Origin check, session, the 15 MB `/api/assistant` body parsed only for a signed-in user, 400/413 instead of 500 for bad bodies — with the database and session store stubbed. It also serves the page itself so `http://localhost:3000/` works standalone for local testing without Nginx in front — but **only from an explicit list of public files plus the icons.** Pointing `express.static` at the repo root, as it did until 14.09.2026, would serve `server/private/checker.js` and every backup HTML next to it, which is exactly what the split was for.

**The administrators' dashboard is a second host on the same API (22.09.2026).** `dash.customsassist.trade` serves `server/dash/index.html` (login and shell only) and proxies `/api/`; the dashboard code (`GET /api/dash.js`) and its data (`GET /api/dash/data`) sit behind `requireAdmin`, so a non-admin session gets 403 on both. Three things keep it admin-only and separate: `routes/auth.js` refuses a non-admin login when `req.hostname` is the host of `DASH_ORIGIN` (`403 admin_only`, checked after the password like the other refusals, no session created); the session cookie is host-only, so the dashboard has its own session, marked `dash:true`, and the «one account, one session» replacement on login works within its own circle (`endUserSessions(…, {dash})`) while disabling, deleting, subscription expiry and password reset still end every session; and `DASH_ORIGIN` is added to the CSRF origin list and to Turnstile's allowed hostnames, so the dashboard login gets the same captcha-on-demand as the site. The page uses only its own names before login (`AUTH_EMAIL_RE`), and on logout it empties the dashboard container and stops the refresh timer. Nothing new is stored: the dashboard reads existing tables and in-memory counters; the request metrics in `services/metrics.js` count routes and statuses, never the content of a request (`privacy.html`: search contents are not logged). `tests/dash.test.js` covers all of it.

**Два открытых маршрута без входа (01.10.2026)** — оба описаны в [backend-ops.md](backend-ops.md), «Монитор доступности…». `GET /api/health` — только да/нет (база разобрана, PostgreSQL отвечает), без сессии, версий и чисел. `POST /api/client-error` — отчёт об ошибке программы в браузере; без входа, потому что ломаться может и экран входа, но под общей проверкой Origin; принимает только строковые поля, вырезает из текста числа от четырёх цифр, почту и параметры адресов (повторно — после браузера), пишет одну строку в журнал, ответ всегда 204; лимит 20 в час с адреса и 300 в час всего, в Telegram — одно сообщение на ошибку в сутки и не больше десяти. **Вход администратора сообщается в Telegram** (адрес, сайт или дашборд, IP, браузер): второго фактора нет, и вход по чужому паролю иначе никто бы не заметил; двухфакторный вход для администраторов остаётся следующим шагом.

**Приём входящей почты — единственный вход без сессии (23.09.2026).** `POST /api/mail/inbound` зовёт Cloudflare Email Worker, у которого нет ни cookie, ни заголовка `Origin`, поэтому путь исключён из проверки Origin в `index.js`. Вместо входа — `MAIL_INBOUND_SECRET` в заголовке `x-ca-secret`, сравниваемый по хешам постоянного времени; без секрета в `.env` маршрут отвечает 503, с неверным — 403, и по ответу нельзя отличить одно от другого содержимого. Маршрут не читает и не создаёт сессию, ограничивает себя сотней писем в час, а Nginx даёт ему отдельный `client_max_body_size 26m` (общий лимит сайта — 1m). Что из письма попадает в базу, решено в пользу минимума: сырое письмо не хранится, HTML превращается в текст при разборе (`services/mailparse.js`), содержимое вложений не сохраняется вовсе — в админ-панель не может попасть чужая разметка, скрипт или картинка-маячок. Разбор свой, без зависимостей, и проверяется образцами писем в `tests/mail.test.js`. Ответы администратора уходят через Resend с адреса поддержки; переписка — персональные данные, названа в `privacy.html` и удаляется через год (`services/retention.js`).

## Email verification

**Email verification exists since 12.09.2026** (migration `0006`). Registration was sending nothing at all before that, which is how `esenbek@exampl.com` — a typo'd domain — got into the users table. The policy started **soft** — account created, logged in and usable immediately, with an amber bar offering a resend — and was **made hard on the same day** (migration `0007`), because the owner pointed out the obvious hole: a soft gate means registering with a made-up address gives full access, which is exactly how `esenbek@exampl.com` came to be using the service. Now `/register` **does not create a session** at all (it returns `{email, needsVerification:true}`) and `/login` answers `403 email_not_verified` until the address is confirmed.

Four consequences of that switch, each of which had to be handled rather than discovered later:

- **Existing accounts were grandfathered, deliberately.** Ten of fifteen users were unverified and eight of them had registered on 03.09.2026, before verification existed — they had never been sent a letter. Locking them out for failing a requirement that did not exist would have been unfair and would have produced a wave of support requests, so migration `0007` marks every pre-existing account verified. The timestamp it writes is `now()`, not `created_at`: it records the date of the decision to grandfather, not a confirmation that never happened — do not write a fact into data that did not occur.
- **Resend needs an unauthenticated route.** With no session until confirmation, the in-app `#verifyBar` resend is unreachable for the people who need it. `POST /resend-verification-public` takes `{email}`, answers `{ok:true}` identically every time (same anti-enumeration reasoning as `/forgot-password`), and is protected by an IP rate limit plus the two-minute per-user cooldown already inside `issueVerification` — no captcha there on purpose, since a third widget for a button that only mails an address already in the database buys nothing.
- **The refusal is checked after the password**, next to the subscription check and for the same reason: checking it earlier would let a login probe reveal which addresses are registered but unconfirmed.
- **The trial still counts from registration**, by the owner's choice, so a slow letter eats into the three days. If that ever becomes a complaint, the fix is to set `subscription_expires_at` at confirmation instead.

The UI gained a fifth auth view, `authViewVerify`, reached both from a successful registration and from a `403 email_not_verified` login. The in-app amber bar is kept even though no unverified session can now exist — an admin-created account could still be unverified, and a dead branch that costs nothing is better than one whose absence is discovered by a user. Tokens mirror `password_reset_tokens` — sha256 of the token only, single use, 24 hours (a day, not an hour: a registration mail may be opened in the evening).

**A new user column has to be added to the auth middleware's SELECT too.** `email_verified_at` was written by the verify endpoint and `/api/auth/me` still answered `emailVerified:false`, because `middleware/auth.js` loads the user with an explicit column list. The end-to-end test caught it; a UI-only check would not have.

## Captcha: Cloudflare Turnstile

**Captcha is Cloudflare Turnstile, and it is off until two keys exist.** `services/turnstile.js` verifies a token against `challenges.cloudflare.com/turnstile/v0/siteverify`; `/register` and `/forgot-password` call it. The design decision that matters: **`isEnabled()` keys off `TURNSTILE_SECRET_KEY`, and when that is unset verification returns `{ok:true, skipped:true}`** — so the code ships and runs exactly as before until the owner pastes the keys into `.env` and restarts. The public sitekey reaches the browser through `GET /api/auth/config` rather than being baked into `tnved_checker.html`, which is what makes turning the captcha on a one-line `.env` edit instead of an edit and redeploy of the page.

Five things worth knowing before touching it:

- **Turnstile does not require the domain to be proxied through Cloudflare.** The DNS records here are DNS-only and that is fine; only the Cloudflare account matters. Do not "enable the proxy" on this account of the captcha.
- **The token is single-use, so verify it last.** In `/register` the captcha check sits *after* field validation and *before* `bcrypt` — validating first means a typo'd password does not burn the token and force the user to solve again; verifying before bcrypt means a bot does not cost a hash.
- **In `/forgot-password` the check happens after the response is already sent**, alongside the rate-limit check, for the reason documented there: that endpoint answers `{ok:true}` identically and immediately for every address so it cannot be used to enumerate accounts. A failed captcha therefore just means no mail, never a different answer.
- **Failure of the verification request itself is treated as a failure (fail closed).** An attacker cannot make our outbound call fail, so the only real cost is a Cloudflare outage blocking signups — which is logged and visible, unlike a captcha that silently lets everyone through whenever a third party is down.
- **`success: true` is not the end of the check.** The siteverify reply carries `hostname` and `action`, and both are compared: the sitekey is public, so a token minted on someone else's page with the same key, or on the neighbouring form, would otherwise be accepted. Each widget sets `action` (`register` / `forgot-password`) and the allowed hostnames are derived from `APP_ORIGIN`. Both comparisons are guarded on the field being present, so a reply that omits one cannot cause a false rejection. Note that the **test keys report `hostname: "example.com"` and no `action`** — so with test keys in place the hostname check rejects everything, which is correct and is how that code path was proven (`turnstile: hostname mismatch: example.com` in the journal).
- **A captcha cannot be solved by your test harness, and that is the point.** With the real key, Managed mode showed «Подтвердите, что вы человек» to the automated browser and Playwright could not click inside Cloudflare's iframe. Do not read that as a defect — verify the negative paths (absent, forged, replayed token) automatically, exercise `hostname`/`action` with test keys, and leave one real registration to a human.
- **Render the widget only for the view that is open.** The first version rendered both at init, which starts two challenges inside `display:none` blocks and risks the token expiring (300 s) before the form is submitted. `tsRenderVisible()` runs after the script loads, because by then the user may already have opened a form while the script was still loading.
- **The widget renders into a shadow DOM.** A test that counts `iframe` elements under the container finds zero and looks like a failure; check `turnstile.getResponse()` or the container's size instead. Render is explicit (`render=explicit`) because the auth views live in `display:none` blocks and an auto-rendered widget there comes out with zero size.
- **The Cloudflare script is loaded when a guest is shown a form, not when the page opens (01.10.2026).** `initTurnstile()` (page) is started by `showAuthView()` for the login, register and forgot views — not for «loading», reset or verify — and guards itself with `tsStarted`; a person with a valid session never loads it. Until then every page open fetched `challenges.cloudflare.com/turnstile/v0/api.js` (85 KB, behind a 302) and sent the visitor's IP and browser details to Cloudflare, including the logged-in users who see no captcha — about a fifth of the post-login transfer on a phone. `turnstile-lazy.test.js` holds it: guest — one load, widgets for register (`register`) and forgot (`forgot-password`); logged-in — none until logout; reset link — none. `server/dash/index.html` already loaded the script only when the server asked for the captcha (`tsRender`), only its config request (`/api/auth/config`, a few bytes) is eager.

Cloudflare publishes test keys that make the whole path checkable without the owner's account: sitekey `1x00000000000000000000AA` with secret `1x0000000000000000000000000000000AA` always passes, `2x…AB`/`2x…AA` always fails, `3x…AA` returns `timeout-or-duplicate`. One caveat found by using them: **the "always passes" secret accepts any non-empty string, not only the dummy token**, so it cannot be used to prove that forgeries are rejected — the `2x` key proves that.

## Account enumeration

**Account enumeration: a decision, not an oversight (17.09.2026).** Login spends a bcrypt comparison on every path — unknown and disabled addresses compare against a dummy hash of the same cost — so neither the answer nor its timing says whether an address exists (`tests/login-enumeration.test.js`). Registration still answers `409 email already exists` on purpose: it sits behind Turnstile and a per-IP limit, and «Такой email уже зарегистрирован» is worth more to a real user than hiding it would be. Closing it would mean answering «check your mail» to everyone and mailing the existing owner instead — do not half-do that, and do not "fix" login back to an early return.

**One mailbox, one trial (21.09.2026).** `user+a@…`, `user+b@…` and, at Gmail, `u.ser@…` all reach the same inbox and all pass email verification, so one person could mint any number of three-day trials — each with its own assistant quota and its own 800-position daily limit on `/api/engine`, five of them covering the whole base under the 300-position alert. Self-registration now compares the canonical form (no `+tag`; for `gmail.com`/`googlemail.com` no dots) against the same expression over `users.email` and answers the existing `409`; the address itself is stored as typed, and an administrator can still create any address. The SQL expression and `canonicalEmail()` in `routes/auth.js` must change together.

**A locked address asks for a captcha instead of refusing (21.09.2026).** Twenty failures an hour per address, from any IP, used to close that address outright — which let anyone who knows an address (the administrator's included) keep its owner out with twenty requests an hour. With Turnstile configured the answer is now `429 captcha_required`: the page renders a widget in the login form (`tsRender('login')`, action `login`, only on demand — an ordinary login never sees a captcha) and resends with the token; a second, hard ceiling of 100 failures an hour still refuses. The answer is the same for an address that does not exist. Without a Turnstile secret the old refusal stands.

## One window, two people: a view must be cleared on the way out, not just hidden

`#appWrap` and `#authScreen` are two divs of one page, and logging out only ever set `display:none` on the first. Everything the previous user had on screen — the admin table of all accounts, their search results, their own address in the user bar — stayed in the DOM, so a person who registered in the same window right afterwards saw it. Reported on 12.09.2026 by exactly that route: the owner logged out of the admin account, registered as an ordinary user and got the full user list.

**The data was never re-served.** `routes/admin.js` mounts `router.use(requireAdmin)` and a live probe with the new user's own session returned `403 {"error":"forbidden"}` for `GET` and `POST /api/admin/users`. That is what makes this a client-side leak rather than an authorisation hole — and it is also why it is easy to miss: every server-side check passes.

Two fixes, and the split between them is the point. `resetAppView()` empties the elements one user fills and the next must not inherit (`result`, `resultSummary`, `adminResult`, `userBar`, `accountPanel`, `calcPrintArea`, `pageLookup`, `speciesResult`, `#inp`, the verify bar) and resets `searchMode`/`currentPage`; it is called both from `doLogout()` **and** at the top of `showApp()`, because a session can also end without anyone pressing «Выйти». And `setSearchMode()` now refuses `'admin'` for a non-admin, falling back to `'code'` — the server would answer 403 anyway, but the mode renders its markup before the answer arrives. **Add a new element that holds per-user content and add it to `resetAppView()` in the same edit**; nothing else in the file will notice that you didn't.

**Browser storage is per-user content too (21.09.2026).** The search history lived in `localStorage` under one key for the whole browser and nothing cleared it, so the next person to sign in on that computer saw the previous user's last six queries — what goods a broker is working on. The value now carries its owner (`{u, list}`; a foreign or old-format value reads as empty and is overwritten by the first query) and `doLogout()` removes the key. The assistant's conversation was already right (`sessionStorage`, keyed by user, `aiForget()` on logout). **A new `localStorage`/`sessionStorage` key is either not about the user (`ca-theme`) or is tagged with its owner and removed on logout.**

## Changing the password from the account menu (24.09.2026)

`POST /api/auth/change-password` (`routes/auth.js`) takes `{current, password}` from a signed-in user: the current password is required, so an open tab on someone else's computer is not enough to take the account over. The new password is 8–200 characters and must differ from the current one (`same password`); a wrong current password answers 403 `wrong current password`. Ten attempts per account per hour (`makeRateLimiter`, keyed by the user id, counted after the format checks), then 429. On success the hash is replaced (bcrypt cost 12), unused reset tokens are spent, and `endUserSessions(id, 'password_reset')` ends **every** session of the account including the dashboard's — the others are told «Пароль был изменён — войдите заново»; the current one survives because the route writes its `userId` back and saves the session after the update. The same route is under the Origin check like every other POST. The form is `openChangePasswordModal()` in `checker.js`, opened from the account menu; test — `tests/account.test.js` (the session store is stubbed there, so «the current session survives» is checked against the route's logic, not PostgreSQL).

Administrators also get `dashUrl` in the login response and `/api/auth/me` (the first entry of `DASH_ORIGIN`, only for `role = 'admin'`, null otherwise) — the account menu links to the dashboard with it.

## Two-factor login for administrators (01.10.2026)

**An administrator can require a one-time code at login** — TOTP (RFC 6238: HMAC-SHA1, 6 digits, 30 s), the codes of Google Authenticator, Microsoft Authenticator, 1Password and the like. It is opt-in, from the account menu («Двухфакторный вход», administrators only — the routes answer 403 to anyone else), and once on it applies to both hosts: the site and `dash.*` share `/api/auth/login`. **Enrolment** (`POST /api/auth/totp/setup` → `/enable`): the server makes a 160-bit secret, keeps it in the session *encrypted* until the first correct code, and only then writes it to `users.totp_secret` — AES-256-GCM under a key derived from `SESSION_SECRET` (`services/totp.js`), so a copy of the database, such as the nightly dump on the owner's machine, does not yield the second factor without the server's `.env`. The QR code is drawn on the server as an SVG `data:` image (`server/src/vendor/qrcode-generator.js`, MIT, vendored so the deploy needs no `npm install`; CSP allows `img-src data:`), next to the key for manual entry. Eight **recovery codes** (`ABCD-EFGH`, no look-alike letters) are shown once and stored as SHA-256 hashes; each opens one login. **Login**: after the correct password, an account with the second factor gets `401 totp_required` and no session; a wrong code is `401 totp_invalid`, counts as a failed login (the same limits and captcha as a wrong password) and has its own per-account limit: a wrong code means the password was right, so 10 wrong codes in an hour close the login with 429 — even with the right code — until the window ends (`totpFailures`), and the first wrong code in an hour sends administrators «Верный пароль, неверный код второго фактора» with the account, IP and browser (`totpAlerts`); a code is accepted within ±1 step and never twice — the step of the last accepted code is written by a conditional UPDATE (`totp_last_step`), and a recovery code is removed the same way, so two logins with one code cannot both pass. The login form (page and dashboard — guest code, page names only) shows the code field only when the server asks; six digits are sent as `totp`, anything else as `recovery`. Every administrator login already goes to Telegram (it now says «с кодом второго фактора» or «по коду восстановления — осталось N»); enabling, disabling and recovery use go to the audit log and Telegram as well. **Turning it off** takes the password and a code (or a recovery code) — an open tab alone is not enough. **Lost phone and codes**: on the server, `cd /opt/tnved/server && sudo -u tnved node scripts/totp-off.js <email>` (audit row and Telegram message). A password reset does not log in, so it is no way around the second factor. Columns — migration `0019_totp.sql`; `middleware/auth.js` reads `totp_enabled_at` (`/api/auth/me` and the login answer carry `totpEnabled`). Named in `privacy.html`. `tests/totp.test.js` covers the RFC vectors, the storage, the routes and, with a browser, enrolment from the menu and login with the code field.

## Notice of a new edition of the terms (01.10.2026)

**The law (ч. 5 ст. 114 Цифрового кодекса)** lets the provider change the user agreement only after notifying the user «любым доступным способом» and fixing a period of **at least one month**; whoever refuses before the date ends the agreement and gets the unused part of the payment back. The terms promise the notice «на сайте или по электронной почте». The site channel is `services/termsNotice.js`: a constant `NOTICE` (`effective`, `url` — a path on our own site, `text`) that git history keeps with its date, overridable by `TERMS_NOTICE` in `.env` (the same JSON; an empty value switches it off). `current()` returns it until the **Bishkek** day of `effective`, then `null` — the block disappears by itself and the «Принимаю» window (`TERMS_VERSION`) takes over. It reaches a guest in `GET /api/auth/config` and a signed-in user in the login answer and `GET /api/auth/me` (`termsNotice`). The page shows it in `#authNotice` (login, register, forgot, reset and verify views — not in «loading», so a signed-in user's screen never flashes it, and a signed-in user does not even ask for the guest config) and in `#appNotice` at the top of the main column, with a × that hides it until the next login and writes **nothing** to browser storage. Both blocks are built from DOM nodes (`textContent`), the link is accepted only as `/…` and not `//…`, so text from the server can never become markup. `resetAppView()` empties `#appNotice`.

**The record.** When a signed-in user is sent the notice, `recordShown()` writes `terms_notice` (`via: 'banner'`, email, `effective`, `url`) to `admin_audit_log` once per session and, by `insert … where not exists`, once per user and date — the answer to «whom did we warn, and when» (`privacy.html` names it next to the terms record; kept three years like the log). The other channel, `scripts/notify-terms.js` (email, `via: 'scripts/notify-terms.js'`), is independent: seeing the block does not count as a letter. **Limits of the site channel:** it reaches whoever opens the site before the day; someone who does not will meet only the «Принимаю» window. On 01.10.2026 the owner chose the site channel and **no mass mailing** (6 of 17 users had signed in within 14 days, 10 within 15–60 days, 1 never) — a conscious residual risk, written in `docs/launch.md`. `tests/terms-notice.test.js` holds the date logic, the routes, the record and the page; `a11y.test.js` scans every view with the block on.

## Personal data, terms of use and the privacy policy

**Payment records (22.09.2026).** Recording a payment in the admin panel stores the payer's address, amount, period, plan and method in `payments` (migration `0013`) and keeps the row after the account is deleted, as the audit log does; `privacy.html` says so in «Какие данные» («Записи об оплатах») and states that the payment itself happens outside the service, so no card data is received. The routes are admin-only (`requireAdmin`), every field is validated (uuid, amount, currency code, 1–24 months, plan from the list, dates), and the action goes to `admin_audit_log` (`payment`, `delete_payment`, `expense_add`, `expense_delete`). `tests/payments.test.js`.

**What the policy lists and for how long (22.09.2026).** «Какие данные» now also names the account's own fields (role, plan, subscription term, dates of registration, verification, last login and activity — all visible in the admin panel and the dashboard), the technical Nginx log and the service journal; «Где и сколько» gives every period: account and assistant log until deletion, backups 14 + 30 days, the terms record and the admin audit log three years after the account ends, payment records until the tax limitation period runs out, deleted on 1 January of the eighth year after the payment year (Налоговый кодекс КР от 18.01.2022 № 3, registry 3-39, edition 57656 of 06.08.2026: ст. 98 ч. 2 — accounting documents are kept for at least the limitation period; ст. 68 — six years from the day after the payment deadline, three for patent payers; the latest deadline for a year is 1 April of the next — ст. 242 profit tax by the single declaration, which is due by 1 April; ст. 426 single tax by the 20th of the following month — so a 2026 payment may go on 01.01.2034, and «no longer than six years» from the payment, as the first wording said, would have been too early), Nginx log 15 days, journal 30 days (`docs/backend-ops.md`, «Logs and their retention»). **The periods are enforced by `services/retention.js`** (started in `index.js`, then every 24 h): `delete from admin_audit_log where purge_after < now` and `delete from payments where created_at < date_trunc('year', now) - 7 years`. `purge_after` (migration `0014`) is set by the delete route to `now() + 3 years` on every row whose `target_user_id` is the account, just before the delete nulls that column — after it, rows such as `set_subscription` or `disable_user` carry no address and could not be traced to the account. The migration gave the rows orphaned by the eleven deletions of 11–12.09.2026 a date from the deletion with the same address, or from the last deletion (error under a day). Expense rows get no date (they are the administrator's, not a user's); a `delete_payment` row about an already-deleted user gets none either (`ponytail:` note in the file). `tests/retention.test.js`.

**Processor agreements (ст. 86 Цифрового кодекса), checked 22.09.2026 on the providers' own pages.** Ст. 86 ч. 4 wants a contract with every processor naming the period, purpose, data types and subjects, written instructions, access limits, correction/deletion procedure and record-keeping — what a GDPR-style DPA contains. **Google Cloud**: the Cloud Data Processing Addendum «is incorporated into the Agreement(s)» — no signature; Cloud Vision API and Document AI are listed under «Google Cloud Platform Services Summary → AI/ML Services» (cloud.google.com/terms/services), not under Premium Software, so it covers both. **Cloudflare** (Turnstile, Email Routing): Customer DPA v6.4, effective 03.04.2026, «forms part of the Main Agreement», self-serve included. **Resend**: DPA last updated 27.08.2026, «legally binding upon Customer entering into the Agreement», Plus Five Five, Inc. **Hetzner: not automatic** — concluded by the customer with a checkbox at `accounts.hetzner.com/account/dpa` after naming the data types and the circle of data subjects (docs.hetzner.com, «Data privacy FAQ»); whether the owner's account has one is visible only there; **the owner concluded it on 23.09.2026** with the Appendix 1 recommended here — all five data types plus a free line for the assistant's questions and answers, and both categories of people (users, including unconfirmed registrations, and the administrators). The owner sent the two PDFs on 23.09.2026 (DPA v1.1 of 10.02.2025, TOMs v1.2 of 17.02.2026), and three things in them matter here. **Appendix 1 is what the customer fills**: types of data (personal master, communication, master contract, log, contract invoicing and payment data — all five apply to us) and data subjects (customers and prospective customers of the Client = the service's users; associates of the Client = the administrators). **Appendix 3 names the subcontractor for a Finnish server** — Hetzner Finland Oy, Tuusula, for building and technical support — with «If you have chosen a server location within the EU, your data will only be processed within the EU»; `privacy.html` names it since 23.09.2026, and § 3 of the DPA repeats that processing stays in the EU/EEA and any third-country transfer needs the customer's prior consent (§ 7: 14 days to object to a new subcontractor). **The TOMs split responsibility by product, and ours is a cloud server** (confirmed from the metadata service: instance-id 163898599, hel1-dc2): Hetzner covers the building, power, cooling, fire, network, DDoS detection, drive erasure and destruction, host updates and separation; **the client is «completely responsible» for the VM** — updates, authorization, firewall and ports, monitoring, virus/security tests, backup and recovery plan, pseudonymization, audit-proof logging of data changes, and **encryption of data and of backups at rest**. The first eight we do (`backend-ops.md`); the encryption we do not — the disk has no crypt layer and `pg_dump -Fc` writes plain files, which is the one gap these documents expose. **DeepSeek: none**, and its API caches what it receives — «Context Caching on Disk ... enabled by default», cleared «usually within a few hours to a few days» (api-docs.deepseek.com/guides/kv_cache), which `privacy.html` states since 23.09.2026 — the Open Platform Terms (Hangzhou DeepSeek AI Co., released 22.04.2026, effective 29.04.2026) neither include nor reference a DPA and describe the service as «neutral, basic model technology services»; the policy discloses the transfer and rests it on the user agreement (ст. 89 ч. 4 п. 4), but a processor contract under ст. 86 cannot be had from them. **Gmail** is a consumer account: Google offers a processing addendum for Workspace, not for a personal mailbox. The last two are the owner's decisions (another model provider with a DPA; a Workspace mailbox or forwarding elsewhere).

**Personal data and the terms of use are governed by the Цифровой кодекс КР от 31.07.2025 № 178, not by Закон № 58 (18.09.2026).** Закон «Об информации персонального характера» от 14.04.2008 № 58 is «Утратил силу» in the registry: Закон № 179 of the same date introduced the Code, in force since 06.02.2026 (registry cards 4-3703, 230029899, 230029914; chapter 11 is personal data, chapter 14 digital services, chapter 23 AI). Read the Code before writing any legal text for this site; three of its rules shaped what exists now. **Consent is not a formality to add «на всякий случай»**: ч. 3 п. 3 ст. 79 makes a consent void when it was requested while another basis applies, and every processing here has one — the user agreement (ст. 79 ч. 1 п. 1), legitimate interest (п. 5), a legal duty (п. 2). Cross-border transfer rests on ст. 89 ч. 4 п. 4 (performing a contract the person is party to), which does not depend on the regulator's adequacy list. **The list exists, but not in the registry** (corrected 22.09.2026 — on 18.09 it was searched only on cbd.minjust.gov.kg and recorded as «not found»): ч. 1 has the regulator publish it on its own site, and `dpa.gov.kg` shows it as a map «Перечень государств, на территории которых обеспечивается адекватный уровень защиты» — the data sits inline in the page as JSON (`CountryCode`, `Status`: `high` = «Соответствует», `medium` = «Не соответствует», `low` = «Неизвестно»). On 22.09.2026 all 194 foreign states were `low` (set 20.02.2026) and only KG `high`, so ч. 2 covers none of the destinations and the policy says so, with the date of the check that ч. 3 requires. Re-check the map when a new destination is added or the policy is re-edited. The same site publishes the model processor contract («Типовая форма договора между владельцем персональных записей и обработчиком») that ч. 4 п. 6 refers to; it cannot be signed with Google, DeepSeek or Hetzner, so п. 4 stays the basis. There is no duty to register: the «реестр владельцев записей» of ст. 90 ч. 4 is where the regulator enters incidents, inspections and penalties. So the third footer document is not a consent but the section `privacy.html#transfer`, and the footer link says «Трансграничная передача персональных данных». **Using the service needs a user agreement, and its acceptance must be recorded** (ст. 114): `terms.html` is the agreement; registration accepts it (the line under «Создать аккаунт» links it and the policy — ст. 73 wants the processing information before collection); accounts from before get a blocking «Принимаю / Выйти» window after login (`#termsGate`, `showTermsGate()` in the page).
