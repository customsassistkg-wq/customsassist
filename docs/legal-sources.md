### Verifying a code list against a Kyrgyz act, in practice

The exemption lists (`ART297_PERECHEN_LISTS`, `ART298_LISTS`, `ART299_CODES`, `LS_CODES`, `MED_CODES`, `MAT_CODES`, …) are transcriptions of annexes to ПКМ КР, and the 05.09.2026 sweep found the same three failure modes in all of them, worth checking for first:

- **A whole annex silently rewritten.** Annex 5 of ПКМ №131 (goods for people with disabilities) was reissued by ПКМ №664 от 14.10.2025 and grew to 141 codes; the file still had 28. Always re-derive the list from the current edition rather than diffing what you remember.
- **Multi-code cells glued into one key.** A cell reading «7216, 7604» became the key `72167604`, which matches nothing. Keys longer than 10 digits are only one signature, and **not the reliable one**: on 17.09.2026 the sport list of ПКМ № 709 still held `39183921` («3918, 3921»), `73264805` and `95048477` («7326; 4805; 9504; 8477») — 8 digits — and `8806218806` plus a stub `22` from «8806 21, 8806 22», which is exactly 10 digits and looks like a real code. The stub was the worst of them: two-way prefix matching made `22` hit every code of chapter 22, so every beverage got a VAT-exemption card for drones. **The check that catches all of it is a set comparison with the act:** split every code cell on `,` and `;`, strip spaces and «из», and require the base's keys to equal that set in both directions. The act's own numbering (1..N without gaps) proves the table was read whole.
- **An annex that no longer exists.** П.23 ч.1 ст.297 in the file points at "Приложение 11" of ПКМ №131, and the current text has neither the annex nor a single reference to it. When a basis cannot be found, mark the entry (`unver:true`) and say so on the card instead of deleting it or leaving it unqualified.

Extraction tips: parse the annex tables with `wordtable.py`-style tolerant parsing, pick the code column as the first cell that is almost entirely digits, and validate every extracted code against the official ЕТТ prefix set — that alone rejects the glue artifacts. Codes in these acts are written with spaces (`8507 80 000 0`), sometimes with an odd grouping (`0105 11 1100`), and sometimes prefixed «из» for partial inclusion.

### Verifying legal text against primary sources

`cbd.minjust.gov.kg` is a React SPA — don't try to scrape it as static HTML. It has an undocumented JSON API instead:
- `POST /api/v1/GetDocuments` with `{"number":..., "dateAdoptedFrom":..., "dateAdoptedTo":...}` to find a document's `documentCode` and current `lastEdition` id.
- `GET /api/v1/GetEdition?editionId=<id>&lang=ru` returns the full text (`contentRu`, a Word-export HTML blob) and its date (`nameRus`).
- The public document URL pattern is `https://cbd.minjust.gov.kg/<documentCode>/edition/<editionId>/ru`.
- **Edition ids are not chronological and `lastEdition` on the card can be empty** (23.09.2026, Налоговый кодекс, card `112340` = the same code the base cites as `3-39`): its eleven editions are 1286440/1286441/1286442 for 2022–2023 and then 2264 … 57656 for 2024–2026, so «max id» silently returned the 03.04.2023 text. Pick the edition by the date in `nameRus`, and quote that date with the edition id.
- `GetDocuments` **ignores every text field** (`name`, `text`, `query`, `searchText`, `title`, `keyword` all return the same default listing); only `number` with `dateAdoptedFrom/To` filters. To find an act by subject, walk `documentReferences` of the act it implements (the Tax Code card lists 306 referencing acts with `nameRu`) or its amending acts, then read the text.
- `GET /api/v1/GetDocument?documentCode=<code>&lang=ru` (no POST, no Cyrillic body) returns the document card, including `editions` — **every** redaction with its id and date — and `documentReferences`, which names the amending acts. This is how you find out that a text has been amended: a Постановление and its Приложение are separate documents, and the annex can have three editions while the parent act still shows one. Checking only the parent act's date is how the НКС set stayed two redactions behind. `GetEdition`'s `nameRus` is the edition's date, not the document's title.
- The registry's `status` field can be stale: ПКМ КР №649 от 08.10.2025 still reads "Не вступил в силу" almost a year after its publication, although its own text says it enters into force 15 days after official publication. Read the act's closing paragraph rather than trusting the status label.
- **Annexes on docs.eaeunion.org come as a `.zip` of `.docx`**, linked from the document card as "Приложения … скачать в word". That is far better material than the PDF: the tables are real cell data. Parse them without extra libraries — a `.docx` is a zip whose `word/document.xml` yields tables by iterating `w:tbl` → `w:tr` → `w:tc` and concatenating `w:t` text (`scratchpad/docx.py` in the 05.09.2026 session did exactly this for the 7,922-row EAEU–UAE schedule). Use it whenever a перечень is attached to an EEC decision.
- **Parse those chapter PDFs with `page.extract_text(extraction_mode="layout")`.** The default flat extraction merges the four columns (код / наименование / доп. ед. изм. / ставка) into one stream, which forces a pile of heuristics — the footnote glued to the rate (`1563С)` = rate 15, footnote 63), a wrapped `, но не менее 0,7 евро за 1 кг` landing outside the row, code cross-references inside names, one code appearing several times per chapter. Layout mode preserves the columns, so a row splits cleanly on runs of 2+ spaces and no heuristic is needed. It also finds what the flat text hides: switching to it took rate verification from 12,886 of 13,451 codes to all 13,292 and immediately exposed 14 more wrong rates. Do this first for any per-chapter ЕЭК PDF.
- **The authoritative current ТН ВЭД/ЕТТ text** is the per-chapter PDF set on `https://eec.eaeunion.org/comission/department/catr/ett/` (`.../ru.2022/ru.<NN>_2022_<DD.MM.YYYY>.pdf`, or `/upload/files/catr/ett/ru.<NN>_2022.pdf` for chapters never amended since 2022). The date in the filename is the publication date of that chapter — quote it as the source of any statement about what codes currently exist. Two parsing traps: rows added by later amendments are printed inline, prefixed with `+`, *inside* the previous row's text, so a line-start-anchored regex misses them (scan the whole flattened text for code patterns instead); and an abolished heading appears as a bare `[8803]` marker, which is a useful signal in its own right.
- The WAF blocks any POST body containing raw (UTF-8) Cyrillic bytes regardless of field name — encode the JSON body with `ensure_ascii=True` (`\uXXXX` escapes) to get through.
- The WAF also blocks plain `GET /api/v1/GetEdition` requests that look like a bare script (no browser-like headers) — add `User-Agent` and `Referer: https://cbd.minjust.gov.kg/<documentCode>/edition/<editionId>/ru` to get a 200 instead of 403.
- For EAEU-level acts (Решения Коллегии/Совета ЕЭК), prefer `docs.eaeunion.org` — do not guess a URL by pattern-matching a neighboring document's numbering; two similarly-numbered documents there can point to completely unrelated acts.
- For EAEU Commission department-level technical/sanitary annexes (e.g. Единые санитарные требования under Решение №299) that aren't single consolidated acts, check `eec.eaeunion.org/comission/department/<dept>/regulation/...` (e.g. `depsanmer` for sanitary measures) — these pages link directly to per-section PDFs at `eec.eaeunion.org/upload/files/<dept>/.../раздел N ЕСТ.pdf`-style URLs (URL-encode the Cyrillic filename). No special headers needed here, unlike cbd.minjust.gov.kg. Fetch with `curl`/Bash and extract text with the `pypdf` package (`PdfReader(path).pages[i].extract_text()`), which is already available in this environment — don't rely on WebFetch's summarizing model for a legal code table, since digit-level transcription errors there are invisible until they cause a wrong lookup.
- `cbd.minjust.gov.kg`'s `GetDocuments` search-by-number can silently return the wrong act: Kyrgyz act numbering is not unique across act types within the same year (a «Постановление» and a «Распоряжение» — or a presidential «Указ» — can share the same number), so a number+date match still needs its `vid`/`organ`/`nameRu` fields checked against what you're actually looking for before you trust it — don't assume a hit is correct just because the number and rough date line up.
- `GetDocuments`'s full-text search (`searchByTextRu`) appears to cap at a small batch of results (~10-17) even when the response's own `totalResultsCount` reports far more, and adding `length`/`pageSize`/`start` params doesn't change this — so don't rely on requesting "more" results; narrow the search phrase itself (longer, more distinctive substrings from the act's actual wording) until the specific act you want lands inside that small returned batch.
- A `GetDocuments` search that finds nothing for a very recently signed act (within roughly the last one to two weeks) is not proof the act doesn't exist — the registry appears to lag real-world signing by that long before indexing. Say so explicitly ("not yet indexed, unconfirmed") rather than treating an empty result as a negative finding.
- **The daily watcher does this first** (`server/scripts/watch-sources.js`, since 23.09.2026, `docs/backend-ops.md` «Дозор источников»): it reads gov.kg and the registry (Cabinet постановления only — `refTypeId: '0050'`, `authoritiesId: '0040.0011'`, the classifier codes visible on any ПКМ card; without them the twelve-record cap fills with laws and orders), the ГТС quota counter and the base's own dates, and mails the administrators what is new or expiring. Read its letter before starting an audit; run it by hand with `--days 60` for a wider sweep. Two facts it depends on: gov.kg serves its leaf certificate without the RapidSSL TLS RSA CA G1 intermediate (kept in `server/certs/`, added to Node's roots for that request), and the registry answers 429 to rapid requests (1.5 s between days, three attempts).
- **Before calling a fresh Kyrgyz act «not yet published», check the Cabinet's own site**: `https://www.gov.kg/ru/npa/c/provisions` lists Cabinet постановления with their **publication date** (the column the registry lacks) within a day or two of signing, and each item page (`/ru/npa/s/<id>`) carries the text and the annexes as PDF. On 23.09.2026 ПКМ № 614 of 14.09.2026 was there with publication date 16.09.2026 while `GetDocuments` still returned nothing for it — and the publication date is what fixes «по истечении N дней» start dates. The registry stays the citation of record once it indexes the act; until then the gov.kg item page is an official `docUrl`.
- `docs.eaeunion.org`'s own search/portal poorly indexes older EAEU Council/Board decisions generally — this isn't limited to the pre-2013 acts noted above; a 2020 decision has also come up unfindable there. Treat any docs.eaeunion.org "not found" as inconclusive rather than as confirmation the act lacks a portal page, and don't burn excessive effort re-trying the same search phrasing once eec.eaeunion.org and independent cross-checked secondary sources have already been exhausted.
- **The current text of an EAEU list is often published by ЕЭК, not by the legal portal.** `docs.eaeunion.org` carries the act as signed; for a list that has been amended many times, look for a consolidated publication on `eec.eaeunion.org` first. Two that matter here: the Единый перечень of Решение №30 has one consolidated PDF *per section* linked from `https://eec.eaeunion.org/comission/department/catr/nontariff/ep.new.php` (files like `/upload/files/catr/EP.pdf/2.3_137.pdf`), and the ЕАЭС–Сербия exclusion list has a single consolidated file on the same site. **The filename does not reliably give the section number** — section 2.12 (наркотические средства) lives in `2.13_45_2026.pdf` — so take the number from the heading inside the PDF itself. Parse these with `extraction_mode="layout"` and derive the code column's left and right bounds from the table header row; without a right bound, Basel-convention codes (`А1030`, `B3040`) and years from the prose land in the code set.
- **The consolidated text of an EAEU list lives on the responsible department's page, not on the legal portal.** Beyond the Единый перечень of Решение №30 (department `catr`), the sanitary list of Решение КТС №299 is published whole as `eec.eaeunion.org/upload/files/depsanmer/Санмеры/Единый перечень.pdf`, linked from `.../depsanmer/regulation/sanitarnye-mery.php` — its header lists every amending decision, and it carries both Раздел I (numbered items with their ТН ВЭД group sets) and Раздел II (a per-group code table). A previous revision recorded that ЕЭК "does not publish" this text; it does. Before writing "no consolidated text exists", open the department's own regulation page.
- **A dispute over whether a code still exists is settled by the official per-chapter ЕТТ publication, never by comparing tariff aggregators.** `4412 32 100 0` sat unresolved for a session because kodtnved.ru and tws.by disagreed; the ЕЭК chapter 44 PDF settles it in one line (HS2022 split 4412 32 into 4412 33 and 4412 34, so the code does not exist). Check the chapter PDF first and skip the aggregators.
- **An `editionId` in an existing citation goes stale silently.** `DOC_SOURCES.law52` pointed at edition 1289610 (09.08.2023) of Закон КР № 52, while `GetDocument` for documentCode 111908 lists a newer one — 40641 (06.11.2025, Закон КР № 253) — which is exactly the redaction that rewrote articles 41, 42 and 44 the calculator cites. The act's number and name in the card were right the whole time; only the pinned edition was old. When you consult an act, re-read its `editions` array and re-pin the last id.

- **A cbd.minjust.gov.kg `documentCode` in an existing citation can be wrong even when the act name looks right.** `7-21561` was cited here as ПКМ КР №267 от 20.05.2022 about certification; it is actually ПКМ №263 of the same date about pay scales. Kyrgyz acts also split into several registry documents: ПКМ №267 is `7-21576`, its Приложение 2 (the перечень) is `43-141`, and the two procedures attached to it are `50-407` and `50-408`. Search by number and date, then read `nameRus` of every hit before trusting one — and expect the annex you want to be its own document. Note that an audit record and the `DOC_SOURCES` constant behind the same card are two separate places: the `sert` record was corrected on 05.09.2026 while `DOC_SOURCES.sert267` still pointed at `7-21561` until 09.09.2026, so the card kept linking readers to the wrong act. When you fix a citation, grep for the URL as well as for the prose.
- The registry's `status` can say «Утратил силу» while `terminationHeaderRu` and `terminationData` are empty, i.e. without naming the repealing act or a date. Treat that as a flag to re-check, not as proof: the ТР law on building materials is marked repealed while ПКМ №267's перечень in its 22.05.2024 redaction still refers to its annex. Keep the data and say the status is unconfirmed rather than deleting positions.
- **A decision's rates and code lists are usually in its annexes, not in the decision.** Each document page on `docs.eaeunion.org` attaches the decision in every Union language plus an `*_att.zip` of the annexes; a rate table read only from the main `.docx` will come back empty. Pick the Russian file by the letters that Russian does *not* have (`ә қ ң ө ұ ү һ і ў ғ`) plus the Armenian Unicode block, not by heading words — every translation opens with the same words. This matters beyond convenience: **the official Kyrgyz translation of Решение Коллегии ЕЭК №12 от 09.02.2021 omits code 7306 40 200 9**, which the Russian original and the Kazakh and Armenian translations all carry, so a check run against the wrong file reports a phantom discrepancy in the DB.
- **A legacy `.doc` annex still yields its numbers.** Some decisions attach their annex as Word 97 (`Прил. к реш. КЕЭК.doc` inside the `skachat-v-word.zip`), which `zipfile` cannot open and whose PDF is often a scan. Decode the whole file as UTF-16LE and keep the printable runs: codes and figures come out exactly, and vertically merged cells show up as missing values in a row — which is itself information, since the merged value belongs to the group. This is how the 2026 and 2027 tariff-quota tables were read.

  Two follow-on traps. **Filtering the decoded runs by "almost all characters are Cyrillic" silently drops rows**: in the Word 97 annex to Решение Коллегии ЕЭК от 11.01.2022 № 6 that filter threw away position 4 of the перечень (сжиженный природный газ, 2711 11 000 0), because it shared a line with binary junk. Count the positions against the numbering in the text, never against the number of surviving lines. **And the Russian original is not always where the filename suggests**: for Решение Коллегии ЕЭК от 16.04.2019 № 61 the `_doc.pdf` is a scan, the `_doc.docx` is the Armenian translation, and the Russian text is inside `_att.zip`. Beyond losing codes, translations can lose structure — the Kyrgyz version of that decision merges subparagraphs «б» and «в» and omits «г» entirely.

  **An empty cell in a quota table is usually a merged cell, and the value belongs to the row where the merge *starts*.** Tariff-quota annexes give one volume to a group of positions by merging the country column vertically. Read as plain text — `.docx` via `w:t`, Word 97 via UTF-16 — the continuation cells come out empty, and on 16.09.2026 that had produced five wrong values per year in `QUOTA_DB` for 2026 and 2027: the top row of a merge recorded as «не выделено», a continuation recorded as 0, and the Vietnam rice row written up as «квота не установлена». The worst of them was Kyrgyzstan's chicken-leg quota (0207 14 200 1), where the calculator told the user the quota could not be used at all. In `.docx`, read `<w:vMerge w:val="restart"/>` / `<w:vMerge/>` on each `w:tc`. In Word 97 the flags live in the table properties: search the stream for sprm `0xD608` (bytes `08 D6`), then `cb` (2 bytes), `itcMac` (1), `(itcMac+1)×2` bytes of cell boundaries and `itcMac×20` bytes of TC records, whose first word carries `fVertMerge` (0x20) and `fVertRestart` (0x40). The records come out in table-row order, so they align with the rows of the text. A scan cannot settle a merge that crosses a page break — the flags can: the «выше не поименованные» row on a new page continues Kazakhstan's and Kyrgyzstan's cells but not Armenia's.
- **Preferential rate schedules live under `eec.eaeunion.org/comission/department/catr/ttr/Preferences/<country>/`** — one consolidated PDF per country (Vietnam, Iran, Serbia, Mongolia), reachable from `freetrade.php`. Most rows say «ставка ЕТТ», and **those rows must be kept**: an earlier version of this note said the opposite («only the rows with a different rate belong in the file»), and it was wrong in the dangerous direction. The list is not "codes the agreement covers" — its title says «перечень **отдельных** товаров», and the deciding act sets 0% for everything *outside* it (п.2 of Решение Коллегии ЕЭК №36 for Vietnam, №1 for Iran, №113 for the UAE; Serbia's №122 frees everything outside its exclusion list). Drop the «ставка ЕТТ» rows and a code that is on the list at the ЕТТ rate becomes indistinguishable from one that is off it at 0%. Read the decision's own п.2 before deciding what a list means — Mongolia's №74 is the other kind: only listed goods get a preference and everything else stays at ЕТТ. The same п.2 holds a second rule worth transcribing literally: «если сумма пошлин по ЕТТ ниже … применяется ставка ЕТТ» (UAE, Iran, Mongolia) — a card once rendered it as «не ниже», the reverse. Two parsing traps from the full lists: the acts write some codes with **eight** digits (`8802 40 00`, `8806 29 00`), so a 4/6/9/10-only pattern welds the row onto its neighbour; and flat `extract_text()` detaches the last digit of a ten-digit code, so cross-check the layout parse against a second extraction by code *set*, not by row count. Watch for rows written «из <код>»: the Vietnam list carries 39 of them, and one (`из 9006 59 000 9`) explicitly *excludes* `9006 59 000 1`, which the file had been offering the preference for.
- **Finding an older decision by number**: the portal's year sections are not numbered consecutively by year. Коллегия ЕЭК → Решения: 2012 → 277, 2013 → 251, 2014 → 254, 2015 → 292, 2016 → 305, 2017 → 315, 2018 → 253, 2019 → 335, 2020 → 247, 2021 → 379, 2022 → 399, 2023 → 414, 2024 → 429, 2025 → 446, 2026 → 463. Совет ЕЭК → Решения: 2025 → 447, 2026 → 461. Page a section with `?PAGEN_1=<n>`. Link labels in the older sections omit the space — «Решение Коллегии ЕЭК №178», not «№ 178» — so a regex that requires one silently finds nothing.

  **Beyond the last page the pager lies — and it lies in two different ways.** The documented tell used to be «stop on a repeated page hash»; on the 2026 sections (463 and 461) that fails, because the markup carries something variable and the seven pages hash differently while serving the same listing. The reliable signal is the other one: **the set of decision numbers stops growing.** Deduplicate by decision number and check the run is unbroken — the 16.09.2026 sweep came out as 121 Коллегия decisions numbered 1..121 with no gaps, which is what proves the sweep complete.

**Beyond the last page the pager lies.** `?PAGEN_1=<n>` with n past the real page count returns the *first* page's content rather than an empty list, so a loop that stops on "no results" never stops. A Коллегия year section holds 100 documents per page and three to four real pages; the tell is that the set of decision numbers stops growing. Sweeping all fourteen sections this way is the only reliable completeness check for "does an act of this kind exist" — it is what found the ТР ЕАЭС 045/2017 перечень and confirmed that Решение № 136 от 05.09.2023 repealed the earlier tractor list. Listing pages carry the *full* title of every document, so the sweep can be done on the listing text alone, without opening cards; search both for the regulation's designation («ТР ЕАЭС 045/2017») and for a reference to the base decision («от 13 мая 2014 г. № 70»), because an amending act's title usually contains only one of the two.

**The per-regulation pages under `eec.eaeunion.org/comission/department/deptexreg/tr/` are an index, not an authority — confirm every decision by its portal title.** `TR_general.php` lists all *adopted* regulations (53 on 16.09.2026), `TRVsily.php` only those *in force*; the difference is the list of regulations whose entry into force is conditional, and the condition sits in the adopting Council decision itself, not on the page (041/2017 waits for amendments tied to its chemical-substance register, 039/2016 waits for 041, 048/2019 for a Council decision on energy labels, 053/2026 enters force in Kyrgyzstan four years after the other member states). Three misfilings were found on one sweep: a decision on ТР ТС 007 dated a year late, a standards-list amendment filed under ТР ТС 019's product list, and Решение Коллегии № 85 от 23.09.2025 — which moves the Kyrgyz transition dates for ТР ТС 013 — placed on the page of ТР ЕАЭС 047. Adopting decisions from 2016-2019 come as scanned PDFs with no text layer; the Russian `.docx` is inside `*_att.zip`, while the loose `.docx` files on the card are the Armenian, Kazakh and Kyrgyz translations. The 18.09.2026 sweep found four more links on these pages that open unrelated documents (amendments № 126 and № 63 to the ТР ТС 004 list, № 35 to ТР ТС 005, the ТР ТС 030 list) — take the decision number from the page, then find the card in the portal's year section.

**A document file becomes Markdown with `anydoc` before anything else reads it.** `anydoc <file>` (the `@firecrawl/anydoc` CLI, installed globally on this machine on 22.09.2026 at the owner's request — `npm i -g @firecrawl/anydoc`) converts `.doc`, `.docx`, `.rtf`, `.odt`, `.xls`/`.xlsx`, `.ppt`/`.pptx`, `.epub`, `.csv` and any PDF with a text layer into GitHub-Flavoured Markdown locally and in milliseconds, tables as GFM tables, Cyrillic intact (checked 22.09.2026 on a `.xlsx`, a `.pdf` and a Cyrillic CSV). Reach for it first when an act or an annex arrives as a file: it is far cheaper than rendering PDF pages into the context window and it saves the Word COM round-trip when all that is needed is the text. Its limits are the reason the rest of this section still exists — a scanned page has no text layer and the file exits 3 («pages need OCR»), and a GFM table flattens merged cells, so a list whose meaning sits in the layout (a form in the section's heading row, a status in a cell's fill colour, a two-column PDF without ruling lines) is still parsed the hard way below. `--ocr hosted` sends the file to Firecrawl Parse over the network: acceptable for a published act, never for anything of a user's.

**Reading every перечень annex on this machine.** Most annexes inside `*_att.zip` are Word 97 `.doc`, some `.rtf`, the oldest only `*_att.pdf`; zip entry names are cp866 unless the UTF-8 flag is set. Microsoft Word is installed and scriptable from PowerShell (`New-Object -ComObject Word.Application`; `Documents.Open(path, $false, $true)` then `SaveAs2(out, 16)`) — that turns all three into `.docx` whose tables parse by `w:tbl`/`w:tr`/`w:tc`, and `ExportAsFixedFormat(out, 17)` renders a page to PDF for a visual check of a layout built with tabs rather than a table (the ТР ЕАЭС 038/2016 list, where only the picture shows which form belongs to RB-1). In `w:t` extraction treat `w:br` and `w:tab` as spaces, or words glue together («фильтрыи»). Three traps of the tables themselves: the form often sits only in a section's heading row and the sub-rows leave it blank; one row's codes continue in the next row with an empty name; and two positions are sometimes written in one cell with their codes interleaved (ТР ЕАЭС 036, 046). **Compare a list by the code set of each position and by the per-code form, not by number** — the file numbers sub-positions its own way.
- A code extracted from an official PDF sometimes has fewer digits than the file's own DB entry (e.g. source says "8421 39 200", DB has `8421392000`; source says "8716 39 800", DB has `8716398000`) — don't assume this is a PDF-extraction artifact (a dropped trailing zero) without checking. Confirm one way or the other by (a) checking whether the shorter form recurs multiple times in continuous prose across independent documents (a real, deliberately-shortened conventional reference) vs. appearing once inside a table cell (more likely a layout-driven truncation), and (b) checking whether the longer, fully-qualified code actually exists as a real current tariff line — search this file's own `ETT_DB` first, then a tariff aggregator (alta.ru, tks.ru, kodtnved.ru, tws.by). If the long code is real and in active use, keep it; if no such code exists anywhere, truncate the DB entry to the shorter, confirmed subheading-level code instead of leaving an unreachable one in place.

### Parsing a two-column ЕЭК list PDF that has no ruling lines

The перечень преференциальных товаров was parsed by word coordinates, and four of the rules generalise to any such file:

- **Take the column boundary from the header table's rectangles.** The body has no lines, but the repeated page header is drawn with rects; their extent also gives the y below which the body starts.
- **Row separation is a line-spacing question, not a content one.** Lines inside one entry are 13.8 pt apart and entries are 19.8 pt apart — a clean bimodal histogram. Any content rule fails here, because a continuation of the exclusion list («0703, 0704, 0705…») also starts with a digit.
- **An entry continues across a page break** whenever the previous entry's code cell has an unbalanced «(кроме …» or the new line's code cell is empty. Without that, this 157-row list came out as 175 rows.
- **Word's justification writes space glyphs with zero advance**, so the text layer of «Мясо» really is «М я с о» and *every* text extractor reproduces it. Rebuild the line from character coordinates, dropping space glyphs and inserting a space where the advance is large. **Take the threshold from the advance histogram, not from the font size**: it is bimodal at ≤0.25 pt inside a word and ≥2.0 pt for a real space, and a threshold of 0.22 × 12 pt = 2.64 pt ate the real spaces in compressed lines, where a space advances 2.52 pt.
- **A superscript footnote marker sits ~1.4 pt above its own line** and lands in a bucket of its own, which is then discarded as empty. Bucket only the body-size characters into lines and attach the small-size ones to the nearest line; doing it the naive way found the footnote on one row out of three.

**Council listing pages do not put the title in the link.** `docs.eaeunion.org/documents/<section>/` renders «Решение Совета ЕЭК № NN» as the link text and the actual title in a sibling `DocSearchResult_Item__Text` block, alongside the adoption, publication and entry-into-force dates. A sweep that reads only the link text finds nothing — unlike the Коллегия sections described above, where the full title *is* the link.

### The EEC register of unilateral member-state measures is parsed by cell colour

**Since 18.09.2026 only the Kyrgyz Republic's rows are kept** (52 of 225, owner's decision: the base answers for Kyrgyzstan, and other states' national measures do not go into it). The card is titled «Односторонние меры Кыргызской Республики (реестр ЕЭК)», takes its `data-dir` from the measures themselves (ввоз/вывоз), and every active Kyrgyz measure is also in `BAN_DB`, so it is a record with terms and protocols, not the only warning. What follows describes the register as it was parsed in full. `UNIMEAS_DB`/`findUniMeasure` hold the ЕЭК's consolidated register of measures member states apply **unilaterally** under arts. 29 and 47 of the Treaty — temporary export/import bans, quotas and licensing regimes. 217 measures of five states for 2024-2026, 48 of them in force at the parsed date. It is a different thing from the Union-wide Единый перечень: a Kazakh export ban does not restrict import into Kyrgyzstan, it closes the purchase there, so the card is deliberately not red and does not rise to the top. Expired measures are kept and flagged, for the same reason as trigger measures: these bans come in waves and recur.

**ЕЭК republishes the file roughly every two weeks and the medialibrary path changes with each upload**, so the pinned URL points at the parsed edition, not at "the latest" — `UNIMEAS_ASOF` carries the register's own as-of date and the card says so. **The hosting page is `eec.eaeunion.org/comission/department/catr/nontariff/interim.php`** («Временные меры, затрагивающие внешнюю торговлю товарами, введенные государствами-членами… в одностороннем порядке») — the 11.09.2026 note that it was not discoverable was wrong; a web search restricted to eec.eaeunion.org found it on 18.09.2026 after the pinned URL began answering 404. Take the current file from that page. **To update between editions, diff the acts, not the rows**: collect every «от ДД.ММ.ГГГГ № N» the new edition cites and compare with the bases in `UNIMEAS_DB` — on 18.09.2026 that isolated the ten new or changed measures of a 24-page edition without re-parsing the colours. **The register copies misprints from the notifications**: it names the Russian import ban on radio equipment Постановление № 448 of 29.04.2026, while publication.pravo.gov.ru (the official Russian portal, `GET /api/Documents?Number=<n>` answers JSON) has it as № 488 — № 448 is a different act. Check a Russian act's number there before quoting it; the Kyrgyz measures in the register are worth checking against cbd.minjust.gov.kg the same way, and they also pin the start date that the act only defines as «по истечении N дней».

Four things about parsing it generalise to any such register:

- **The status is encoded in the cell's fill colour, not in its text.** Each measure's «Срок действия» cell is filled green (in force) or peach (expired) — a legend printed in every page header. Flat text extraction cannot see it at all. The same rect also gives the row's y-range, which solves the real problem of a table whose rows are half a page tall and break across pages.
- **Row boundaries come from the «№» column, not from that coloured band.** The band is a merged cell and is shared in both directions: three Belarus measures share one term and one basis, while Kazakhstan's 2025 measure № 4 is split into road and rail transport with different terms under one number. Splitting by bands alone yields 211 rows instead of 217 and silently welds the three Belarus measures into one.
- **The register's own numbering is the completeness proof.** Numbers run downwards within each (country, year) pair; requiring each of the fifteen groups to form an unbroken run from its maximum to 1 passes in full. Count the source's rows, never your parser's.
- **An exclusion is recognised by nesting, not by position.** The code column mixes «из 7302», ranges («8404 – 8415»), parenthesised exclusions and trailing «за исключением» lists, sometimes several in one cell. A code after «кроме»/«за исключением» is an exclusion **only if it is nested inside one of the inclusions already collected from that same cell**; otherwise the parser returns to inclusion mode. That single rule handles «4401, за исключением 4401 31 000 0, 4403, 4404» (4403 is an inclusion again) and, with a check for the word «позиции», «7206 (кроме железа товарной позиции 7203)» too. The first version switched to exclusion mode for the whole cell and turned «2710 12 (за исключением …)» into **zero inclusions** — the measure vanished entirely.

At runtime an exclusion suppresses a hit only when the query is at least as specific as the exclusion: for a broader code the measure still applies to part of the goods. Each card line names the code or range it matched on, because the goods column is long and gets truncated — a car code matching a Belarus measure titled «медицинские материалы и изделия» looks like a parser bug until the line says it matched on «8701 – 8705», which the register really does list.
